# Запуск, обновление и перенос БД

Сверено 16.11.2026 с compose.yaml, скриптами запуска/восстановления и манифестом снимка. Рабочая БД — billing_next, PostgreSQL 16; активный каталог миграций backend содержит V1–V38. Версию конкретной работающей БД проверять отдельно по flyway_schema_history.

## Что переносится через Git

Код хранится в main. Переносимый снимок — [billing-next-snapshot.dump](billing-next-snapshot.dump), метаданные и SHA-256 — [billing-next-snapshot.json](billing-next-snapshot.json).

Снимок остаётся на V28; при запуске нового backend Flyway применяет V29 (отмена заявок и восстановление остатков), V30 (аудит перемещения КТК между вагонами накладных) V31 (исходная и целевая накладные в истории переноса) и V32 (признак необходимости возврата в строках автовывоза и начисление без возвратной поставки). Перед обновлением существующей базы нужна свежая резервная копия. Изменения редактора накладных после V31 не добавляют миграций; V32 относится к начислению услуги по автовывозу без возврата КТК. Существующим строкам назначается return_required=true, автоматических начислений миграция не создаёт. V33 добавляет периоды хранения и расширяет историю КТК; восстанавливает связи из существующих операций с учётом отмен, неоднозначности помечает для проверки. Перед применением нужна свежая резервная копия. V34 заменяет шаблонные UUID старых демонстрационных данных случайными UUID v4 вместе со ссылками; подробности ниже. V35 добавляет общий календарь MVP и источник автоматических дат; существующие бизнес-записи не меняет. V36 переименовывает поля периода хранения arrival_* → receiving_* и departure_* → shipping_* с сохранением данных и связей. V37 добавляет статусы строк КТК и точные ссылки периода на строки документов. V38 удаляет поля проверки и версии периода хранения; предварительно требует разрешить проблемные периоды. Более новый снимок БД не опубликован.

Текущий снимок экспортирован 10.11.2026 в 10:02 МСК. Манифест фиксирует успешную проверку восстановления с совпадением 45 таблиц и 6 последовательностей. Это результат проверки при экспорте, а не новая проверка при каждом чтении документа. Снимок содержит и справочники, и документы на момент экспорта.

Git не синхронизирует работающие PostgreSQL двух компьютеров. Получение нового файла dump не меняет локальную БД. .env, роли PostgreSQL, локальные резервные копии и последующие изменения данных в снимок автоматически не входят.

Исторический billing-snapshot.dump относится к прежней схеме V1–V44. Он ещё хранится в репозитории, но **не используется для текущего развёртывания**. Локальные initial/before/test дампы также не заменяют переносимый снимок.

## Новый компьютер: Windows

Нужны Git и работающий Docker Desktop с Linux containers и Compose v2. Отдельная установка Java, Node.js и PostgreSQL для запуска через Docker не требуется. Порты 3001/8081/5433 должны быть свободны.

Выполнять по одной команде; при ошибке остановиться:

```powershell
git clone --branch main --single-branch https://github.com/airafka/bil.git bil-next
cd bil-next
Copy-Item .env.example .env
powershell -NoProfile -ExecutionPolicy Bypass -File .\restore-snapshot.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File .\start.ps1
```

**Сначала восстановление, затем приложение.** Если backend запустить раньше, Flyway создаст объекты, и restore-snapshot.ps1 откажется заменять их.

[restore-snapshot.ps1](../restore-snapshot.ps1) проверяет SHA-256, имя billing_next, отсутствие работающих backend/frontend и пользовательских объектов БД. Затем восстанавливает одной транзакцией. Скрипт не очищает существующую базу. Для нового клона при уже существующем Compose billing-next сначала разобраться с окружением: одно имя проекта использует те же контейнеры и volume.

Настройки — [.env.example](../.env.example). Порты меняются через FRONTEND_PORT/BACKEND_PORT/DB_PORT. Пароль и имя пользователя можно настроить до первого создания volume; последующая правка .env сама по себе не меняет пароль уже созданной роли. .env не публикуется.

## Обычный запуск и остановка

Из корня репозитория:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\start.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File .\stop.ps1
```

Это отдельные действия: start запускает с пересборкой, stop останавливает. БД остаётся в billing-next_postgres-data. Автоматического восстановления dump при запуске нет.

Проверка при стандартных портах:

```powershell
. .\scripts\docker-command.ps1
$billingDocker = Resolve-BillingDocker
& $billingDocker compose -p billing-next ps
Invoke-RestMethod http://localhost:8081/actuator/health
(Invoke-WebRequest -UseBasicParsing http://localhost:3001).StatusCode
```

Ожидается backend UP, frontend HTTP 200. Compose ждёт готовности БД перед backend, затем backend перед frontend. Скрипты находят Docker через PATH или стандартные пути установки.

## Обновление кода на втором компьютере

1. Проверить ветку, HEAD, origin и git status. Сохранить незакоммиченные изменения.
2. Выполнить git fetch origin main и изучить разницу с локальной версией. Общая ветка — main.
3. Если появились новые активные миграции, до запуска обновлённого backend сделать свежую резервную копию.
4. При совместимой истории выполнить git merge --ff-only origin/main.
5. Запустить start.ps1 и проверить приложение.

Если старый клон отслеживал другую ветку, сначала настроить получение main и безопасно переключиться на неё после сохранения работы. Не пытаться исправлять расхождение истории принудительной отправкой.

При обычном обновлении сохраняется локальная БД. Flyway применяет новые миграции из **backend/src/main/resources/db/baseline**. Старый каталог db/migration не подключён в application.yml. Применённые миграции не редактировать.

## Резервная копия перед изменениями

Из корня проекта, после проверки назначения контейнеров. Пример для стандартных billing_next / billing; при других настройках подставить проверенные имена:

```powershell
$ErrorActionPreference = 'Stop'
. .\scripts\docker-command.ps1
$billingDocker = Resolve-BillingDocker
$backupName = 'billing-next-before-change-' + (Get-Date -Format 'yyyyMMdd-HHmmss-fff') + '.dump'
$backupDir = Join-Path (Get-Location) 'backups'
New-Item -ItemType Directory -Path $backupDir -Force | Out-Null
$backupPath = Join-Path $backupDir $backupName
& $billingDocker compose -p billing-next exec -T db pg_dump -U billing -d billing_next -Fc -f "/tmp/$backupName"
if ($LASTEXITCODE -ne 0) { throw 'pg_dump завершился ошибкой' }
& $billingDocker compose -p billing-next exec -T db pg_restore --list "/tmp/$backupName" | Out-Null
if ($LASTEXITCODE -ne 0) { throw 'Оглавление дампа не читается' }
& $billingDocker compose -p billing-next cp "db:/tmp/$backupName" $backupPath
if ($LASTEXITCODE -ne 0) { throw 'Не удалось сохранить локальную копию' }
Get-FileHash -LiteralPath $backupPath -Algorithm SHA256
```

Дамп передаётся файлом: не перенаправлять бинарный stdout pg_dump через текстовый PowerShell pipeline. Проверка оглавления и SHA-256 не заменяет проверку восстановления; перед существенным изменением данных восстановить копию в отдельную тестовую БД и проверить результат. Резервные копии не публиковать автоматически.

## Перенос новых данных между компьютерами

Новый переносимый снимок создаётся только по отдельному запросу. Обновлять dump и JSON-манифест вместе, проверив восстановление и содержимое таблиц/последовательностей на изолированной БД.

Если целевая billing_next уже заполнена, restore-snapshot.ps1 не предназначен для её замены. Порядок отдельной операции переноса:

1. Сделать свежую резервную копию целевой БД.
2. Восстановить новый снимок в отдельную БД, проверить схему, данные и работу совместимого backend.
3. Остановить запись приложения и выполнить контролируемое переключение с сохранением прежней БД для отката.
4. Проверить приложение после переключения.

Замена снимком не объединяет изменения двух БД. Сначала определить, какая копия данных является актуальной. Не удалять рабочий volume ради импорта.

## Тестовые сценарии

Изменяющие проверки выполняются на отдельной БД, с backend, подключённым именно к ней, и свободным портом. Одного другого URL недостаточно для изоляции.

Исторические scripts содержат старые порты, жёсткие пути, имена контейнеров и одноразовые операции. Перед запуском читать код; массовые seed/cleanup/renumber не повторять автоматически. Временные отчёты и тестовые дампы не считать частью поставки приложения.

## Идентификаторы демонстрационных данных

[V34](../backend/src/main/resources/db/baseline/V34__randomize_demo_uuids.sql) однократно заменяет UUID старых seed-данных вида xxxxxxxx-0000-0000-0000-000000xxxxxx и xxxxxxxx-0000-4000-8000-000000xxxxxx на случайные UUID v4. Уже случайные UUID сохраняются, в том числе содержащие повторяющиеся цифры. Номера документов, коды КТК/вагонов, даты, суммы, статусы и количество строк не меняются. Новые записи приложения уже используют случайные UUID.

Для каждого старого UUID создаётся одно соответствие: меняются первичные ключи, UUID-ссылки (включая ссылки без внешнего ключа), UUID-токены служебных ключей и текстовых/JSON-архивов. Замена выполняется одной транзакцией под блокировками; внешние ключи пересоздаются с исходными определениями и проверяются. Временная карта соответствий не остаётся в бизнес-схеме. Служебная таблица Flyway исключена. При ошибке вся замена откатывается.

Перед обновлением остановить запись приложения и сделать свежую резервную копию; проверить её восстановление в отдельную БД. Старые ссылки и открытые формы с заменёнными ID нужно открыть заново из списка. На разных локальных БД новые UUID генерируются независимо; Git не синхронизирует их. Исторические seed/renumber-скрипты не запускать повторно. Опубликованный снимок V28 не менялся: после восстановления эту замену выполнит V34.

Проверка [scripts/demo-uuid-migration-check.cjs](../scripts/demo-uuid-migration-check.cjs) требует заранее восстановленную **отдельную billing_uuid_test на V33**, контейнер billing-next-db-1 и доступный Docker (при необходимости задать DOCKER_EXE). Сравнивает все строки до/после с учётом карты UUID, проверяет сохранение случайных ID, JSON, ключей операций, циклических связей, определений ограничений и повторный запуск без изменений. Тестовые записи и обе пробные миграции откатываются. После этого запуск backend с DB_NAME=billing_uuid_test и отдельным портом проверяет штатное применение через Flyway; только затем обновляется рабочая БД.

## Рабочая дата MVP (V35)

[V35](../backend/src/main/resources/db/baseline/V35__application_business_date.sql) создаёт application_clock с единственной строкой id=1, business_date (NULL означает системную дату), version и реальным временем changed_at. Функции billing_now()/billing_today() применяются к автоматическим датам бизнес-таблиц; DEFAULT сохраняет прежние типы и соглашение UTC для timestamp без часового пояса. Миграция не обновляет существующие строки и не включает фиксированную дату. Технические даты Flyway и самой настройки остаются реальными. При восстановлении опубликованного снимка V28 применяется цепочка до V38; снимок не обновлён.

Выбор общий для экземпляра БД, сохраняется после перезапуска и входит в резервную копию. «Сегодня» записывает NULL и возвращает автоматическую смену дня. Время суток берётся с системных часов PostgreSQL, отображается по Москве; на локальном Docker это часы компьютера. Полные правила — в [backend](../BACKEND_ALIGNMENT.md#рабочая-дата-и-время).

Перед применением V35 сделать свежую резервную копию. Проверка [application-clock-check.cjs](../scripts/application-clock-check.cjs) допускает запись только в восстановленную billing_clock_test с backend billing-next-clock-test на 8199: режим capture на V34 сохраняет отпечатки всех бизнес-строк, обычный запуск после V35 сравнивает их и проверяет операции. Режим recheck повторяет сценарий на уже мигрированной тестовой БД без повторной проверки миграции; нужны действующий тариф и демонстрационный состав. Проверяются время, конфликты, високосный день, хранение/отмена, начисление/счёт/оплата и сохранение даты после перезапуска. Сценарий оставляет тестовые документы и возвращает системный режим.

[application-clock-ui.cjs](../scripts/application-clock-ui.cjs) использует тот же backend, его фикстуру и frontend на 3199; FRONTEND_URL тестового backend должен быть http://localhost:3199. Проверяет ввод, стрелки, пересчёт хранения, перезагрузку, «Сегодня», Escape и размеры окна. Нужны Chrome и Docker (при необходимости DOCKER_EXE). Не запускать изменяющие проверки на billing_next.

## Названия полей хранения (V36)

[V36](../backend/src/main/resources/db/baseline/V36__storage_receiving_shipping_columns.sql) переименовывает в container_storage_period пять колонок: arrival_history_id → receiving_history_id, arrival_at → receiving_at, arrival_owner_id → receiving_owner_id, departure_history_id → shipping_history_id и departure_at → shipping_at. Также переименованы связанные именованные ограничения и индекс storage_period_receiving_idx. Значения, типы, уникальность, внешние ключи и проверки последовательности дат сохраняются. Старые миграции не изменены; перед применением нужна свежая резервная копия.

Это изменение имён БД: существующие поля ответа API отчёта (arrivalAt/departureAt и остальные) и типы событий истории ARRIVAL/DEPARTURE сохраняются. Backend и схема должны обновляться вместе. Пояснения колонок в просмотрщике БД соответствуют новым именам.

Проверка [storage-column-rename-check.cjs](../scripts/storage-column-rename-check.cjs) читает только отдельную billing_storage_rename_test. Режим capture на восстановленной V35 сохраняет контрольные суммы всех бизнес-таблиц и определения ограничений/индексов; обычный запуск после применения V36 сравнивает их с учётом новых имён. До сравнения не выполнять изменяющие сценарии. Жизненный цикл проверяется отдельно сценарием storage-period-check.cjs на изолированной БД с актуальной схемой.

## Строки заданий КТК (V37)

[V37](../backend/src/main/resources/db/baseline/V37__container_task_status_and_storage_rows.sql) добавляет nullable status с CHECK UPLOADED/FINISHED в receiving_order_container, shipping_order_container и waybill_container. Существующие активные строки получают статус по связанной заявке: CONFIRMED → UPLOADED, COMPLETED → FINISHED; черновики, отменённые заявки и свободные накладные — NULL. Для ЖД-приёма источником служит строка накладной.

В container_storage_period добавлены receiving_order_container_id, waybill_container_id и shipping_order_container_id. Составные внешние ключи связывают тот же КТК и заявку; приём допускает одну альтернативу авто/ЖД, вывоз связывается со строкой shipping_order_container. Существующие ссылки на заявки и историю сохраняются. Перенос выбирает только однозначные совпадения; для отменённого ЖД-приёма использует накладные из order_cancellation.details. Неразрешимые случаи получают признак проверки, без подстановки случайной строки. Даты, статусы периодов и бизнес-документы не переписываются, новые факты и начисления миграция не создаёт. Перед обновлением нужна свежая резервная копия; backend и схема обновляются вместе.

Проверка [container-task-migration-check.cjs](../scripts/container-task-migration-check.cjs) использует только billing_container_tasks_test: capture на V36 сохраняет все бизнес-записи, запуск после V37 проверяет сохранность прежних полей и новые статусы/ссылки. Сравнение рассчитано на исходную БД с однозначными связями, до запуска изменяющих сценариев. [container-task-check.cjs](../scripts/container-task-check.cjs) проверяет эту БД, контейнер billing-next-container-tasks-test и порт 8194 либо billing_storage_fields_test / billing-next-storage-fields-test / 8198 при STORAGE_TEST_DB=billing_storage_fields_test; проверяет авто/ЖД, статусы, ссылки, ограничения, атомарный откат, повторные операции, отмены и повторное использование накладной. Для календарных проверок тестовая рабочая дата должна быть не раньше 05.11.2026. Тесты оставляют фикстуры только в изолированной БД.

GET /api/container-storage-periods дополнительно возвращает receivingOrderContainerId, waybillContainerId, shippingOrderContainerId. Существующие поля ответа сохраняются. Пояснения статусов и связей в просмотрщике читаются из комментариев PostgreSQL, добавленных миграцией.

## Удаление служебных полей периода (V38)

V38 удаляет из container_storage_period needs_review, review_reason и version. Поля проверки container_owner_history остаются. Даты, статусы, история и ссылки периода на строки КТК сохраняются. Индекс единственного открытого периода и ограничения источников приёма/вывоза больше не используют признак проверки; ровно один источник приёма обязателен, источник вывоза заполнен одновременно с shipping_at.

Перед обновлением сделать свежую резервную копию. При наличии периодов с needs_review=true миграция останавливается до удаления полей: сначала требуется сверка этих данных, автоматического исправления нет. Backend и frontend обновляются вместе со схемой. Старые миграции V33/V37 сохраняются без изменения; после восстановления снимка V28 применяется вся цепочка до V38.

Проверка scripts/storage-fields-check.cjs работает только с billing_storage_fields_test: capture на V37 сохраняет контрольные суммы бизнес-таблиц и проверяет атомарный отказ для проблемного периода; запуск после V38 проверяет сохранность остальных данных, удаление трёх полей и ограничения источников. Затем STORAGE_TEST_DB=billing_storage_fields_test запускает scripts/storage-period-check.cjs через backend billing-next-storage-fields-test на 8198 и проверяет жизненный цикл, отмены, отчёт и CSV. Изменяющие проверки не запускать на billing_next.

## Просмотр БД в реальном времени

`db-viewer/` — независимый Node.js-сервис со статическим интерфейсом, без изменений основного frontend/backend. `compose.db-viewer.yaml` запускает отдельный проект `billing-db-viewer` в существующей сети `billing-next_default`; PostgreSQL приложения должен уже работать. Адрес — http://localhost:3002, привязка только к 127.0.0.1. Порт меняется через DB_VIEWER_PORT. Настройки БД берутся из того же локального .env. Из браузера доступны только GET-запросы; произвольного SQL, редактирования и удаления записей нет. Все запросы данных выполняются в READ ONLY-транзакциях, пароли в браузер не передаются.

### Первая установка и новые таблицы

1. Проверить подключение к нужной БД и сделать свежую резервную копию по разделу выше.
2. Собрать просмотрщик и установить уведомления:

```powershell
. .\scripts\docker-command.ps1
$billingDocker = Resolve-BillingDocker
& $billingDocker compose -f compose.db-viewer.yaml build
& $billingDocker compose -f compose.db-viewer.yaml run --rm --no-deps -e OBSERVER_INSTALL=yes viewer node install-observer.mjs
.\start-db-viewer.ps1
```

Каждую команду выполнять отдельно, при ошибке не продолжать. Установщик одной транзакцией создаёт служебную схему billing_observer, функцию notify_change и AFTER STATEMENT-триггеры billing_db_viewer_changes на существующих обычных/секционированных таблицах public. Сами бизнес-записи не меняются; версия Flyway не увеличивается. Это отдельный необязательный инструмент разработки, а не миграция приложения. Установка требует прав владельца таблиц, кратковременно блокирует DDL/DML; ожидание блокировки ограничено 5 секундами. Повторная установка идемпотентна. После миграций, добавляющих новые таблицы, повторить установку; таблицы без триггера обозначаются предупреждением в интерфейсе после обновления списка. Обычный запуск просмотрщика ничего в схеме не устанавливает.

Триггеры передают через LISTEN/NOTIFY только имя таблицы, вид операции и номер транзакции. PostgreSQL доставляет событие после COMMIT, ROLLBACK ничего не показывает. Одинаковые события одной таблицы/операции внутри транзакции могут объединяться; это сигнал перечитать актуальное состояние, а не построчный аудит. Сервер передаёт события браузеру через SSE. Несколько быстрых событий объединяют перечитывание без потери итогового состояния. Нет периодического опроса БД; heartbeat поддерживает соединение. После переподключения читается свежий снимок, пропущенная история событий не восстанавливается.

Интерфейс позволяет открыть две и более таблицы кнопкой «Добавить таблицу». Каждая панель показывает одну страницу своей таблицы, обычно 50 строк, и сохраняет собственные поиск, сортировку, страницу и представление. Панели можно закрывать, кроме последней; навигатор и журнал работают с активной панелью. Один поток SSE обновляет все панели, пауза и ручное обновление общие; по умолчанию первыми идут последние версии строк по xmin, затем первичный ключ. Поиск, пользовательская сортировка и выбранная страница сохраняются при обновлении и могут ограничивать видимость новой строки. Кнопка «Последние изменения» возвращает первую страницу и исходную сортировку. Все значения передаются текстом без потери точности bigint/numeric. На вкладке «Структура» колонка «Примечание» объясняет назначение атрибута: приоритет имеет комментарий PostgreSQL, затем контекстный словарь db-viewer/attribute-notes.mjs, сверенный с миграциями, BACKEND_ALIGNMENT.md, CONTAINER_STOCK.md и backend. Неизвестные поля явно обозначаются как неописанные. Словарь обновляется при изменении назначения полей; пояснения не записываются в рабочую БД. Переход по внешнему ключу открывает связанную таблицу с точным фильтром. Журнал хранит последние 100 уведомлений текущей вкладки; его очистка не меняет БД. Пауза останавливает автоматическое обновление экрана, возобновление читает актуальные данные. Запросы счётчиков и поиска сканируют таблицы и рассчитаны на объём локального MVP.

Остановка `.\stop-db-viewer.ps1` останавливает только просмотрщик. Триггеры остаются в БД; без слушателя уведомления не накапливаются. Резервные копии, сделанные после установки, включают служебную схему и триггеры. Опубликованный переносимый снимок автоматически не обновляется.

### Проверки просмотрщика

В `db-viewer/`: `npm ci`, `npm run lint`, `npm run build`, `npm test`. Build проверяет синтаксис buildless-интерфейса и сервера; Dockerfile выполняет lint/build и тесты без БД. Основной React frontend не изменяется.

`test/database.test.mjs` включает изменяющий сценарий только с `VIEWER_INTEGRATION=1` и строго `DB_NAME=billing_db_viewer_test`. Создать эту отдельную БД заранее и передать её DB_HOST/DB_PORT/DB_USER/DB_PASSWORD. Сценарий создаёт/очищает только свою viewer_test_record и проверяет COMMIT/ROLLBACK, четыре вида событий, повторную установку, запрет записи через read-only соединение, безопасные идентификаторы и точность bigint. Не направлять его на billing_next.

`test/http.test.mjs` с `VIEWER_URL=http://localhost:3002` проверяет только чтение всех таблиц, ограничение размера страницы, запрет POST, постороннего Origin и Host. Для браузерной проверки изменения записей использовать отдельный просмотрщик на тестовом порту 3197, подключённый к billing_db_viewer_test.

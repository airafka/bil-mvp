# MVP контейнерной площадки ЛКДС

Приложение оформляет поставки и вывозы КТК, ведёт накладные и историю собственников и считает дни хранения. Разработка и публикация идут в ветке **main** на GitHub. [airafka/bil-mvp](https://github.com/airafka/bil-mvp)

MVP принимает результаты TOS по каждому КТК. При подтверждении безномерного автовывоза проверяется остаток КТК у выбранного собственника. Для ЖД-вывоза указываются номера вагонов и размещённых на них КТК. [Формат пакета и виды заявок](BACKEND_ALIGNMENT.md#входящие-результаты-tos)

В V69 `container_visit` хранит идентификатор заезда, КТК и ссылки на события приёмки, вывоза и отмены приёмки. Заявки и даты доступны через эти события. Таблица `container_period` связывает заезд и собственника с начальным событием, а `container_owner` хранит текущий складской статус, собственника и ссылку на поставку. В отчёте строка «Поставка → Вывоз» раскрывает периоды собственников. CSV сохраняет 17 колонок.

Заявка на смену собственника передаёт свободные КТК от одного собственника другому. КТК должен находиться на терминале, а строка его приёмки должна иметь статус `FINISHED`. Остальные КТК той же заявки могут ещё ожидать приёмки. Дата передачи может быть прошлой, текущей или будущей, начиная со дня фактической поставки в текущем визите. Подтверждение будущей передачи сохраняет план в строке заявки. При наступлении даты приложение создаёт событие и период, затем обновляет регистр. При отзыве до даты в заявке сохраняются время и причина отзыва. Передача задним числом пересчитывает дни хранения между назначениями. Фактический вывоз до будущей передачи прекращает её. Подробности — в [правилах смены собственника](CONTAINER_STOCK.md#смена-собственника).

С V59 визит и первое назначение собственника создаются только при фактической поставке. В container_owner.receiving_order_id хранится заявка на поставку с момента резервирования, после приёмки и до следующей поставки. Номер этой заявки используется в сообщениях о складских конфликтах. Вывоз обновляет существующий визит, дата вывоза в назначениях собственников не дублируется.

С V58 удалены служебные таблицы container_movement, order_cancellation и outbound_data. Отмена выполняется без причины и архивного снимка состава; складская история, отчёт хранения и CSV сохраняются.

## Окружение

Параметры по умолчанию заданы в [compose.yaml](compose.yaml) и [.env.example](.env.example); локальный .env может менять порты.

| Компонент | Адрес / имя |
| --- | --- |
| Compose-проект | billing-mvp |
| UI | http://localhost:3021 |
| Backend / health | http://localhost:8101 / http://localhost:8101/actuator/health |
| PostgreSQL | localhost:5453, база billing_mvp, пользователь billing |
| Контейнеры | billing-mvp-frontend-1, billing-mvp-backend-1, billing-mvp-db-1 |
| Хранилище PostgreSQL | billing-mvp_postgres-data |

Выполняйте команды из корня клона airafka/bil-mvp. Путь показывает `git rev-parse --show-toplevel`, адрес репозитория — `git remote -v`. Compose создаёт сеть `billing-mvp_default` и том `billing-mvp_postgres-data` для этого клона. Все три порта доступны через loopback на этом компьютере.

Для уже настроенной копии: запустить Docker Desktop, затем выполнить .\start.ps1. Остановка — .\stop.ps1. Скрипт запуска пересобирает приложение, остановка сохраняет БД. Для нового компьютера **сначала восстановите снимок в пустую БД**, затем запускайте приложение: [пошаговая инструкция](database/README.md).

## Рабочая дата MVP

Календарь в шапке задаёт общую дату для расчётов и новых операций, включая бизнес-даты создания, складские события и расчёт дней хранения. Технический порядок записи container_owner_history.created_at не зависит от календаря; рабочее время событий хранится в occurred_at. Время суток идёт по системным часам; в локальном Docker это часы компьютера, представление — Europe/Moscow. Стрелки меняют день, «Применить» сохраняет выбранную дату, «Сегодня» возвращает следование системной дате. Выбор сохраняется в БД и действует для всех пользователей этой копии MVP после перезапуска.

В новых формах receiving, shipping и рейса дата по умолчанию берётся из рабочего календаря, время — по Москве. Ручной ввод и даты существующих документов сохраняются. Перевод календаря не переписывает документы: меняется выбор действующего собственника и видимых границ хранения. Отчёт и CSV сохраняют 17 колонок. День передачи принадлежит новому собственнику, день shipping включён; до shipping дни считаются по дату расчёта включительно. Границы вычисляются по событиям начала периодов и вывоза в заезде, исходный receiving определяется по container_visit_id. Аннулированный receiving скрыт, история сохранена. Льготное хранение и стоимость пока не рассчитываются. Источники колонок — в [CONTAINER_STOCK.md](CONTAINER_STOCK.md#текущий-отчёт), правила времени — в [backend](BACKEND_ALIGNMENT.md#рабочая-дата-и-время).

## Просмотр БД в реальном времени

Отдельный локальный интерфейс — http://localhost:3022, Compose-проект `billing-mvp-viewer`, исходники — `db-viewer/`. Показывает таблицы схемы public, строки, типы колонок, ключи и переходы по связям. Есть поиск, сортировка, страницы, полный просмотр записи, подсветка новых/изменённых строк и журнал наблюдаемых операций.

Обновление идёт по событиям PostgreSQL после COMMIT: INSERT, UPDATE, DELETE и TRUNCATE. Периодического опроса БД нет. Интерфейс доступен только на этом компьютере и не позволяет изменять данные. Основной MVP продолжает работать на порту 3021.

Обычный запуск — `.\start-db-viewer.ps1`, остановка — `.\stop-db-viewer.ps1`. Перед первым запуском нужна отдельная установка служебных уведомлений после резервного копирования: [инструкция](database/README.md#просмотр-бд-в-реальном-времени). Наблюдатель не входит в миграции бизнес-схемы Flyway.

## Редактирование накладных

В /waybills/edit-placement выбираются свободные накладные или накладные черновых поставок, включая документы без КТК. Одна карточка показывает физический вагон и все его КТК из выбранных накладных. При переносе и обмене меняется вагон, исходная накладная каждого КТК сохраняется. Проверка вместимости учитывает футовость только выбранного состава; изначально пустые связи накладных с вагонами сохраняются. Правила сохранения — в [BACKEND_ALIGNMENT.md](BACKEND_ALIGNMENT.md), отображение и пустые состояния — в [FRONTEND_STANDARD.md](FRONTEND_STANDARD.md).

## Код и проверки

- Frontend: React, TypeScript, React Router, Vite; зависимости фиксирует [package-lock.json](frontend/package-lock.json).
- Backend: Java 21, Spring Boot 4.1.0, Spring JDBC, Bean Validation.
- БД: PostgreSQL 16, Flyway. Активные миграции V1–V74 находятся в [db/baseline](backend/src/main/resources/db/baseline).
- Сборка и запуск: Docker Compose; frontend раздаёт Nginx.

[Backend Dockerfile](backend/Dockerfile) выполняет Maven package с тестами; [frontend Dockerfile](frontend/Dockerfile) — ESLint, Vitest и TypeScript/Vite build. Локально: mvn test из backend; npm ci, npm run lint, npm run test, npm run build из frontend. Для frontend dev доступен npm run dev.

При запуске backend вне Compose необходимо явно настроить DB_HOST=localhost, DB_PORT=5453, DB_NAME=billing_mvp и локальные учётные данные: значения по умолчанию в application.yml — localhost:5432, база billing. Для тестов используйте отдельную БД и свободный порт.

Проверки, меняющие данные, выполняются только в изолированной тестовой БД. Старые scripts могут содержать прежние пути и порты: перед запуском читать сценарий. Количество ранее пройденных тестов не является текущим результатом — после задачи сообщать только реально выполненные проверки.

В шапке доступна кнопка «Очистить заявки»: удаляет все операционные данные и хранение с подтверждением и автоматической резервной копией, сохраняя справочники и настройки. Объём и ограничения — в [инструкции](database/README.md#очистка-заявок-и-хранения).

## Границы MVP

Для испытаний TOS и Datareon отправьте JSON на `POST /datareon/event`. Кнопка выполнения доступна для номерных заявок. Накладные создаются локально. Внешняя шина настраивается отдельно.

Git синхронизирует код и опубликованный файл снимка, но не работающие базы двух компьютеров. Порядок публикации кода — в [AGENTS.md](AGENTS.md), порядок работы с данными — в [database/README.md](database/README.md).

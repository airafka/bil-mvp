# MVP биллинга контейнерной площадки ЛКДС

Локальное приложение для оформления услуг контейнерной площадки: поставка КТК, вывоз, возврат, учёт собственников, начисления и счета на оплату. Репозиторий — [airafka/bil](https://github.com/airafka/bil), общая ветка — **main**. Название локальной папки bil-next не является названием ветки.

Учёт КТК с V55 разделён на container_visit (физический receiving → shipping), container_ownership_period (собственники) и container_owner (четыре складских состояния без собственника). Связь с визитом называется container_visit_id. История, UUID прежних периодов, отчёт и CSV из 17 колонок сохраняются через обычные представления совместимости. Источник receiving определяется прямой связью с визитом. В отчёте хранения каждый визит показан строкой «Поставка → Вывоз»; стрелка раскрывает периоды собственников под общими заголовками той же таблицы. CSV сохраняет прежний плоский формат.

С V56 подтверждение передачи сразу записывает собственника и effective_date в container_ownership_period. Шедулера нет: текущий собственник и отчёт определяются по рабочей дате при чтении. С V57 разрешена передача задним числом внутри текущего визита: дата не раньше фактического receiving, КТК сейчас находится в остатках. Новая запись может вставляться между существующими передачами; следующие назначения сохраняются, исторические дни и CSV пересчитываются. До будущей даты новая запись и будущая граница не показываются в отчёте. Shipping до передачи или отмена receiving прекращают будущую передачу; повторный receiving не наследует её. Правила — в [CONTAINER_STOCK.md](CONTAINER_STOCK.md). Опубликованный снимок V28 не обновлён.

## Рабочая дата MVP

Календарь в шапке задаёт общую дату для расчётов и новых операций, включая бизнес-даты создания, складские события, начисления и оплату. Технический порядок записи container_owner_history.created_at не зависит от календаря; рабочее время событий хранится в occurred_at. Время суток идёт по системным часам; в локальном Docker это часы компьютера, представление — Europe/Moscow. Стрелки меняют день, «Применить» сохраняет выбранную дату, «Сегодня» возвращает следование системной дате. Выбор сохраняется в БД и действует для всех пользователей этой копии MVP после перезапуска.

В новых формах receiving, shipping и рейса дата по умолчанию берётся из рабочего календаря, время — по Москве. Ручной ввод и даты существующих документов сохраняются. Перевод календаря не переписывает документы: меняется выбор действующего собственника и видимых границ хранения. Отчёт и CSV сохраняют 17 колонок. День передачи принадлежит новому собственнику, день shipping включён; до shipping дни считаются по дату расчёта включительно. Границы вычисляются по датированным назначениям и визиту, исходный receiving определяется по container_visit_id. Аннулированный receiving скрыт, история сохранена. Льготное хранение и стоимость пока не рассчитываются. Источники колонок — в [CONTAINER_STOCK.md](CONTAINER_STOCK.md#текущий-отчёт), правила времени — в [backend](BACKEND_ALIGNMENT.md#рабочая-дата-и-время).

## Просмотр БД в реальном времени

Отдельный локальный интерфейс — http://localhost:3002, Compose-проект `billing-db-viewer`, исходники — `db-viewer/`. Показывает таблицы схемы public, строки, типы колонок, ключи и переходы по связям. Есть поиск, сортировка, страницы, полный просмотр записи, подсветка новых/изменённых строк и журнал наблюдаемых операций.

Обновление идёт по событиям PostgreSQL после COMMIT: INSERT, UPDATE, DELETE и TRUNCATE. Периодического опроса БД нет. Интерфейс доступен только на этом компьютере и не позволяет изменять данные. Основной MVP продолжает работать на порту 3001.

Обычный запуск — `.\start-db-viewer.ps1`, остановка — `.\stop-db-viewer.ps1`. Перед первым запуском нужна отдельная установка служебных уведомлений после резервного копирования: [инструкция](database/README.md#просмотр-бд-в-реальном-времени). Наблюдатель не входит в миграции бизнес-схемы Flyway.

## Услуги и разделы

В рабочей БД на дату сверки три услуги:

- «Комплексная услуга по приему контейнера в составе поезда».
- «Комплексная услуга по приему контейнера при повагонной отправке».
- «Комплексная услуга по приему контейнера, прибывшего автотранспортом».

Первые две выбираются при создании ЖД-услуги независимо от количества КТК. Автоуслуга создаётся при оформлении возврата на другую пару клиент/договор; это не отдельный вариант первоначального ЖД-мастера. Подробности расчёта — в [бизнес-логике](BACKEND_ALIGNMENT.md).

| Заявки на смену собственника | /service-orders |
| Рейсы | /routes |

В разделе «Заявки на вывоз - Авто» обеих ЖД-услуг действие «Возврат не нужен» позволяет выбрать КТК без оформленного возврата. Для них услуга начисляется при выполнении автовывоза; если вывоз уже выполнен — сразу при сохранении выбора. Остальные КТК сохраняют начисление по возврату. Подробности — в [бизнес-логике](BACKEND_ALIGNMENT.md).

## Редактирование накладных

В /waybills/edit-placement выбираются свободные накладные или накладные черновых поставок, включая документы без КТК. Одна карточка показывает физический вагон и все его КТК из выбранных накладных. При переносе и обмене меняется вагон, исходная накладная каждого КТК сохраняется. Проверка вместимости учитывает футовость только выбранного состава; изначально пустые связи накладных с вагонами сохраняются. Правила сохранения — в [BACKEND_ALIGNMENT.md](BACKEND_ALIGNMENT.md), отображение и пустые состояния — в [FRONTEND_STANDARD.md](FRONTEND_STANDARD.md).

## Код и проверки

- Frontend: React, TypeScript, React Router, Vite; зависимости фиксирует [package-lock.json](frontend/package-lock.json).
- Backend: Java 21, Spring Boot 4.1.0, Spring JDBC, Bean Validation.
- БД: PostgreSQL 16, Flyway; активный каталог миграций — [db/baseline](backend/src/main/resources/db/baseline), V1–V56.
- Сборка и запуск: Docker Compose; frontend раздаёт Nginx.

[Backend Dockerfile](backend/Dockerfile) выполняет Maven package с тестами; [frontend Dockerfile](frontend/Dockerfile) — ESLint, Vitest и TypeScript/Vite build. Локально: mvn test из backend; npm ci, npm run lint, npm run test, npm run build из frontend. Для frontend dev доступен npm run dev.

При запуске backend вне Compose необходимо явно настроить DB_HOST=localhost, DB_PORT=5433, DB_NAME=billing_next и локальные учётные данные: значения по умолчанию в application.yml — localhost:5432, база billing. Для тестов используйте отдельную БД и свободный порт.

Проверки, меняющие данные, выполняются только в изолированной тестовой БД. Старые scripts могут содержать прежние пути и порты: перед запуском читать сценарий. Количество ранее пройденных тестов не является текущим результатом — после задачи сообщать только реально выполненные проверки.

## Границы MVP

Интеграции с ЭТРАН, TOS, Datareon и 1С не подключены. Накладные создаются локально, складские события фиксируются ручным выполнением заявок. Оплата счёта — локальная отметка, без банковского обмена. Данные генератора демонстрационные.

Git синхронизирует код и опубликованный файл снимка, но не работающие базы двух компьютеров. Порядок публикации кода — в [AGENTS.md](AGENTS.md), порядок работы с данными — в [database/README.md](database/README.md).

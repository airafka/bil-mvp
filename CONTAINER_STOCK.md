# Собственники и учёт КТК

В V68 период хранения открывается фактической приёмкой или сменой собственника в конкретном заезде. Будущая передача хранится в строке заявки. С 00:01 МСК фоновая задача проводит наступившие передачи и обновляет собственника в регистре и черновых вывозах.

## Роли и источники

Клиент услуги, грузоотправитель/получатель и собственник КТК — разные роли. Собственник не выводится сервером только из клиента заявки.

| Данные | Источник |
| --- | --- |
| Исходное текстовое обозначение собственника накладной | waybill_container.owner |
| Собственник поставки по умолчанию | receiving_order.default_container_owner_id |
| Выбранный собственник отдельного КТК ЖД-поставки | waybill_container.owner_container_id |
| Собственник строки автопоставки | receiving_order_container.owner_container_id |
| Текущий собственник | container_owner.client_id → client.id; API читает через container_owner_current |
| Прежний и новый собственники в заявке на передачу | service_order.old_client_owner_id и service_order.new_client_owner_id |
| Складское состояние физического КТК | container_owner |
| Физический receiving → shipping | container_visit |
| Зафиксированный собственник вывоза | shipping_order_container.container_owner_id |
| История изменений / события | container_owner_history |
| Периоды фактического хранения | Вычисляются по container_visit и датированным container_period |

В поставке поле собственника по умолчанию обязательно; явный собственник строки имеет приоритет при создании. Черновик допускает индивидуальное изменение. Изменение общего собственника в сохранённой поставке обновляет её строки.


## Жизненный цикл

| Операция | Условие | Результат |
| --- | --- | --- |
| Подтверждение поставки через рейс | КТК отсутствует в регистре или ранее выбыл | EXPECTED, client_id выбранного собственника и receiving_order_id в регистре; событие резервирования. Визит и назначение собственника не создаются |
| Выполнение поставки | EXPECTED от этой поставки | ON_TERMINAL, событие UNLOAD_FINISH; создаются container_visit и первое container_period |
| Подтверждение вывоза через рейс | КТК свободен: ON_TERMINAL | RESERVED_OUT; собственник вывоза фиксируется из регистра |
| Выполнение вывоза | RESERVED_OUT от этого shipping | DEPARTED; закрываются визит и последний период |

UNLOAD_FINISH и LOAD_FINISH поступают через POST /datareon/event. Ручное выполнение транспортной заявки также фиксирует событие. При выполнении поставки сохраняется собственник, записанный в регистр при подтверждении поставки. При резервировании и фактическом вывозе сохраняется собственник регистра на рабочую дату.

container_owner содержит текущую запись физического КТК, а не отдельную запись на каждую перевозку. В остатки входят ON_TERMINAL и RESERVED_OUT. EXPECTED и DEPARTED сохраняются в общем регистре и истории, но не означают свободный КТК для вывоза.

Складская операция и запись собственника в черновик вывоза блокируют затронутые строки КТК в порядке UUID PostgreSQL. Блокировка действует до завершения транзакции. Изменение статуса заявки, регистра и события выполняется транзакционно. Повторное выполнение защищено состоянием заявки и складскими проверками; отдельного журнала container_movement нет.

## Отмена заявок и рейсов

Транспортная заявка может перейти из DRAFT, ACCEPTED или DONE в REJECTED. Повторная отмена возвращает текущий результат без повторного изменения остатков. Возврата отменённой заявки в работу нет: оформляется новая. Причина не запрашивается и не сохраняется; отдельного журнала отмен и архива состава нет.

| Отменяемая операция | Проверка | Изменение регистра |
| --- | --- | --- |
| Черновик поставки/вывоза | Черновой статус заявки | Остатки не меняются |
| Подтверждённая поставка | EXPECTED принадлежит этой поставке | DEPARTED; восстанавливаются прежний собственник и ссылка на предыдущую поставку |
| Выполненная поставка | ON_TERMINAL принадлежит этой поставке | То же восстановление; КТК исключается из физических остатков |
| Подтверждённый вывоз | RESERVED_OUT принадлежит этому вывозу | ON_TERMINAL; снимается резерв и восстанавливается предыдущий действующий вывоз, если он был |
| Выполненный вывоз | DEPARTED принадлежит этому вывозу | ON_TERMINAL; КТК снова в свободных остатках |

Если до самой первой поставки записи собственника не было, после её отмены запись сохраняется в DEPARTED, с текущим собственником и пустой ссылкой на предыдущую поставку. Отмена вывоза сохраняет текущего собственника. Для документов, подтверждённых по прежним правилам, это может быть собственник, сменившийся во время резерва.

Отмена выполненной поставки запрещена, если КТК зарезервирован для вывоза, уже вывезен или прошёл более позднюю поставку. Отмена выполненного вывоза запрещена после резервирования следующего прихода, приёмки или последующего вывоза. Проверяется не только статус, но и принадлежность текущей операции заявке. Сначала отменяются последующие операции. Ошибка содержит номера КТК и связанной транспортной заявки; конфликты состава собираются вместе, без частичного изменения остатков.

Резерв поставки хранится в container_owner.receiving_order_id, резерв вывоза — в container_owner.shipping_order_id; события сохраняются в истории; отдельной container_stock_reservation нет. При отмене поставки прежний собственник берётся из old_client_id единственного события RESERVE_RECEIVING этой заявки и КТК; если он NULL, остаётся текущий собственник. При отмене вывоза текущий собственник сохраняется. Предыдущую заявку того же типа выбирает previous_stock_order: последнее записанное событие до резервирования отменяемой заявки, с исключением REJECTED-документов. До фактической поставки связь с receiving берётся из container_owner.receiving_order_id, после выполнения — через container_visit; для свободного КТК регистр сохраняет последний действующий вывоз. Номер и дата создания документа не определяют порядок резервирования. Состав заявки должен точно совпадать с историей резервирования; при отсутствующей, повторной или неоднозначно упорядоченной истории отмена блокируется с STOCK_HISTORY_REQUIRED. Собственник не выводится из клиента заявки.

Для порядка используется существующее container_owner_history.created_at: при новой записи триггер блокирует КТК и выбирает максимум системного времени UTC и времени предыдущей записи плюс микросекунда. Поэтому порядок строго возрастает даже при переводе календаря назад; если старая запись датирована будущим, новые технические отметки следуют за ней. Старые даты не переписываются. Рабочие даты по-прежнему находятся в occurred_at: от них зависят хранение, складское движение и отображаемое время события. Проверки бизнес-последовательности сохранены. Перед удалением таблицы миграция проверяет уникальность старых времён и соответствие истории сохранённым резервам; неоднозначность останавливает миграцию.

История переходов сохраняется, обратный переход отмечается cancellation=true. Карточка отменённой заявки читается из её текущих таблиц без архивного снимка. После освобождения накладной детализация отменённой ЖД-поставки может отсутствовать; это согласованное поведение. Накладные отменённой ЖД-поставки освобождаются для новой заявки.

Отмена рейса отменяет все его заявки одной транзакцией. Ошибка в любом документе откатывает весь пакет. При поштучной отмене рейс сохраняет оставшиеся заявки: он завершается, когда все активные заявки выполнены, и получает REJECTED, когда отменены все. [Отмена заявок и рейсов](BACKEND_ALIGNMENT.md#отмена-заявок-и-рейсов)

## Сопоставление с dev_back

Образец для переноса — исходники из архива `backend-stage (1).zip` репозитория `airafka/dev_back` на коммите `08343f2`. Ниже приведены точки подключения учёта хранения для контейнерной площадки. Транспортные заявки и рейсы MVP используют коды DRAFT, ACCEPTED, DONE и REJECTED из dev_back.

| Операция | Реализация в dev_back | Что использует учёт хранения в MVP |
| --- | --- | --- |
| Подтверждение поставки и вывоза | `ContainerStatusService.reserveForReceivingOrder / reserveForShippingOrder`, проверки состава и владельцев в сервисах заявок | Резервирование под блокировкой КТК. Новая поставка заменяет receiving_order_id и сохраняет предыдущий вывоз. Номерной вывоз фиксирует собственника из регистра. Заезд начинается при фактической выгрузке. |
| Результат TOS | `TosReceivingResultAction`, `TosShipmentResultAction`, `ContainerStatusService.markReceived / markShipped` | Принимать результат отдельной строки по `_order` и `_id`. В той же транзакции обновить складской статус КТК, историю и его заезд по `eventDateTime`. Когда готовы все строки, завершить документ. Повтор сохраняет первую границу периода. |
| Передача собственника | `ServiceOrderService.accept`, `ServiceOrderContainerService.saveSelected`, `ContainerOwnerService.validateForAcceptance / changeOwner` | Черновик допускает пустой состав. При подтверждении повторно проверить владельца и доступность под блокировкой. Передачу привязать к дате и фактически принятому КТК в том же заезде. Будущую передачу сохранить как план, при наступлении даты записать историю и открыть период. |
| Отмена | `ContainerStatusService.cancelReceivingOrder / cancelShippingOrder`; `RouteService.reject` | По истории восстановить ссылку на предыдущую действующую заявку того же типа. Отмена приёмки исключает заезд из отчёта, отмена вывоза открывает тот же заезд. Для частично выполненной заявки различать выполненные строки и резервы. Отмену рейса проводить одной транзакцией. |

### Какие данные передать разработчикам

- В `container_owner` источником складской доступности служит `status`. В состояниях `EXPECTED` и `ON_TERMINAL` поле `shipping_order_id` может указывать на вывоз предыдущего заезда. В состояниях `RESERVED_OUT` и `DEPARTED` оно указывает на соответствующий вывоз, если он был. Дату вывоза для отчёта читать из события конкретного заезда.
- В `container_owner_history` сохранить прежнего и нового собственников, статусы, источник операции и последовательность записей. Добавить время действия `occurred_at`. В `dev_back` обычная смена собственника может записываться с пустыми складскими статусами. При подключении хранения нужно явно определить вид такой операции и восстановить её принадлежность к заезду по проверяемым данным. При отсутствии надёжного источника времени или заезда вынести запись на сверку.
- В `container_visit` создать один заезд при первом `ARRIVAL` данного КТК по поставке. При `DEPARTURE` записать в тот же заезд ссылку на событие вывоза. В `container_period` открыть период при приёмке и при фактической смене собственника. День передачи включается в хранение обоих собственников, день вывоза — в хранение последнего. У каждого заезда свои границы, даже при повторной поставке того же КТК.
- В основной системе точки интеграции, роли, статусы и собственные миграции уже существуют. Для переноса следует адаптировать обработчики складских переходов и выполнить отдельную миграцию данных основной системы. SQL проекта описывает схему и историю Flyway этого MVP.

### Ошибки и приёмка

Общие складские отказы сохраняют причину из dev_back. Например, повторный резерв поставки возвращает HTTP 400 и `errorMessage` вида `ContainerStatus.ReceivingAlreadyReserved: [номер поставки; КТК1, КТК2]`. Контейнеры отсортированы в пределах одной причины и заявки. Для отсутствующего остатка номер заявки пуст. Исходный `errorCode` передаётся для именованных ошибок, например `AccessDenied` и ошибок дублирования состава. Поля `code` и `detail` используются клиентом MVP. [Правила конфликтов КТК и вагонов](backend/src/main/java/ru/billing/app/containerstock/ContainerStockPolicy.java)

Правила хранения проверяются дополнительно: строка должна относиться к переданной заявке и физическому КТК, события одного КТК должны допускать последовательное открытие и закрытие заезда, передача должна относиться к собственнику на указанную дату. Проверки выполняются до фиксации операции. Общая причина отказа в подтверждении пустого состава передачи — `Service order must contain equipment`. Обработка сообщений TOS описана отдельно. [Входящие результаты TOS](BACKEND_ALIGNMENT.md#входящие-результаты-tos)

Приёмочный сценарий запускается командой `node scripts/stock-alignment-check.cjs <имя-тестового-backend>` на отдельном backend Docker-проекта `billing-mvp` с тестовой БД. Он использует обычные API, проверяет причины отказов, частичную приёмку, датированную передачу, дни хранения, второй заезд, отмену и результат TOS для безномерного автовывоза. [Сценарий](scripts/stock-alignment-check.cjs)

## Собственник вывоза

Ручной выбор КТК в вывозе автоматически подставляет собственника из регистра. ЗПУ, класс опасности и порожность ручного вывоза задаются отдельно.

В DRAFT сохранённый собственник строки следует за регистром. Создание и редактирование строки читают собственника под блокировкой КТК, поэтому параллельная передача учитывается и при сохранении черновика. В открытой карточке черновика рабочая дата определяет отображаемого собственника. При подтверждении собственник записывается в вывоз и фиксируется: последующие CHANGE_OWNER и LOAD_FINISH не переписывают его в ACCEPTED/DONE. Текущий собственник регистра поэтому может отличаться от исторического собственника подтверждённого вывоза.

## Смена собственника

В одной заявке все КТК переходят от одного прежнего собственника (`old_client_owner_id`) к одному новому (`new_client_owner_id`). Они должны различаться. Прежний собственник определяется по назначениям на дату передачи. Например, если 18 сентября КТК перешёл от А к Б, при оформлении 20 сентября передачи от 17 сентября прежним собственником будет А.

Подобрать и подтвердить можно свободный КТК в состоянии ON_TERMINAL. Строка КТК в авто- или ЖД-поставке текущего визита должна иметь статус FINISHED. Заявка может ещё находиться в ACCEPTED. Нижняя граница даты передачи — день фактической приёмки этого КТК в текущем визите включительно. Поставка должна уже состояться по рабочему календарю. Допускаются прошлые, текущие и будущие даты. После повторной поставки нижней границей становится день приёмки в новом визите.

КТК из другого черновика смены собственника исключается из подбора. Резервирование под вывоз (RESERVED_OUT) также закрывает подбор и подтверждение новой передачи. Подтверждённая передача со строкой PLANNED блокирует вывоз этого КТК. В номерном авто- и ЖД-вывозе сервер проверяет конкретные КТК при подтверждении рейса. При конфликте весь рейс остаётся черновиком, резервы и история сохраняют прежнее состояние. В безномерном автовывозе рейс подтверждают по обычному остатку. Сервер проверяет передачу при обработке LOAD_FINISH под блокировкой выбранного КТК, до записи фактического вывоза. Оператор видит номер КТК и номер заявки на смену собственника. Для отмены нужно открыть ожидающую заявку и нажать «Отменить заявку». Черновики, отозванные и уже проведённые передачи допускают вывоз при выполнении остальных складских проверок.

Для таблицы состава периоды берутся из `active_container_period` по `container_visit_id`. Для каждой записи `visitPeriods` API возвращает тип и номер заявки (`orderType`, `orderNumber`) и точный момент начала периода (`occurredAt`) из `container_owner_history.occurred_at`. Для поставки это фактическая приёмка КТК, для смены собственника — момент действия передачи. Поле `date` содержит календарный день этого события по Москве. `orderId` ведёт к заявке, `ownerName` содержит имя собственника периода. Подтверждённые передачи распределяются по статусу связанной строки: PLANNED или APPLIED. Аннулированные визиты и отменённые передачи исключаются.

Выбор закрепляет визит. При подтверждении сервер блокирует заявку и КТК и повторно проверяет поставку, складское состояние, визит и прежнего собственника на указанную дату. В черновике нового собственника, дату и состав можно изменить за одно сохранение. Если хотя бы один КТК не подходит, изменения откатываются целиком.

При подтверждении строка заявки сохраняет заезд, прежнего и нового собственников и момент передачи. Сразу создаются событие OWNER_CHANGE в container_owner_history и период нового собственника в container_period. Начало периода определяется по `container_owner_history.occurred_at` события, указанного в `start_container_owner_history_id`. Момент хранится в UTC. Полночь 30 ноября в Москве соответствует 29 ноября 21:00 UTC. При нескольких передачах в один день учитывается порядок событий внутри дня.

В черновике флажок «Дата будущая» включает отложенную передачу. При снятом флажке можно выбрать сегодня или более раннюю дату. Подтверждение фиксирует состав и дату. Для сегодняшней или прошедшей даты операция сразу меняет остаток, переводит заявку в DONE и разрешает отправку одного сообщения со всеми КТК через outbound_data.

Для будущей даты подтверждение сохраняет SCHEDULED и создаёт сообщение с пустым ready_at. По одному заезду допускается несколько подтверждённых передач. Например, при поставке А и передачах Б с 26-го и В с 29-го в container_period сразу видны три строки. До 26-го в container_owner остаётся А. Отчёт включает действующие периоды по дату расчёта и включает день передачи в хранение обоих собственников.

С 00:01 МСК планировщик раз в минуту проверяет наступившие даты по рабочему календарю. Он обрабатывает каждую заявку целиком под блокировкой её КТК. Обновление текущего собственника, статус DONE и разрешение отправки (ready_at) фиксируются одной транзакцией. При недоступности получателя очередь сохраняет пакет для повтора.

Ожидающую заявку можно окончательно отменить. Если от неё зависит последующая подтверждённая передача, сначала отменяют последующую. При отмене поставки зависимые будущие передачи аннулируются целиком. Их периоды и история сохраняются для аудита и исключаются из отчётов. Для новой передачи создают новую заявку.

Проверки V57: scripts/backdated-ownership/seed.cjs на отдельной V56 создаёт А16 → Б18 и сохраняет отчёт/CSV/аудит; после миграции scenarios.cjs проверяет вставку В17, неизменность исходных событий, подбор по дате, будущие передачи, календарь назад/вперёд, перенос даты, отмены, повторный receiving, отказ устаревшего выбора, атомарность пакета и параллельное подтверждение. extra.cjs проверяет 2/4 дня, исторического собственника в подборе и простой backend. Только контейнеры billing-backdate-check-*, БД billing_backdate_check, сеть billing-backdate-check, backend 127.0.0.1:8255; перед изменениями проверяются подключения и изоляция. Проверки scripts/dated-ownership относятся к переходу V55 → V56; более ранние сценарии — к прежним версиям.

## Состав и редактирование

При ручном создании заявки по умолчанию одна строка КТК. В ручных черновиках авто-поставки/вывоза и ЖД-вывоза можно добавлять номерные КТК. В ЖД-вывозе добавление идёт в уже выбранный вагон.

Состав ЖД-поставки задаётся накладными. Подтверждённые и выполненные заявки также не допускают добавления. Метаданные и новые строки сохраняются совместно; ошибочный состав откатывает пакет.

В ЖД-поставке собственник меняется в строке КТК или массовым выбором. Массовый выбор накладной/вагона включает свёрнутые строки. Это редактирование собственника поставки, а не выполнение CHANGE_OWNER в регистре. Подробности интерфейса — в [FRONTEND_STANDARD.md](FRONTEND_STANDARD.md).


## История в карточке КТК

В справочнике КТК нажмите на номер контейнера. В карточке `/containers/{id}` видны его реквизиты и история со ссылками на заявки. Номер КТК в остатках тоже открывает карточку. Ссылка «История» в остатках открывает полный журнал с резервами и отменами.

Выборка карточки повторяет `ContainerOwnerHistoryService.getPage` и `ContainerOwnerHistoryPredicate` из `dev_back`. Для поставки и вывоза заявка должна иметь текущий статус `DONE`, а состояние КТК после события — `ON_TERMINAL` или `DEPARTED`. Черновики, подтверждённые и отменённые транспортные заявки исключены. Отмена ранее завершённой заявки убирает из карточки её прежние строки и номер заявки из вариантов фильтра. Полный журнал остатков сохраняет эти события. При частичной обработке событие уже влияет на остатки и хранение и появляется в карточке при завершении всей заявки. Для смены собственника достаточно фактической записи истории этого КТК. Запланированная будущая передача появится после её проведения.

`GET /api/containers/{id}/card` возвращает реквизиты, страницу истории и значения фильтров для этого КТК. Номер и тип заявки, прежний и новый собственники сочетаются с диапазоном дат записи. Каждый список учитывает остальные фильтры по всей выборке до разбиения на страницы. Обе границы диапазона включены по UTC. В карточке и регистре время событий отображается в UTC. «Дата записи» — техническое время `created_at`, по которому отсортирована история. «Дата операции» — время действия `occurred_at`, в том числе время конкретного КТК из пакета TOS.

На отдельной тестовой базе [проверка карточки КТК](scripts/container-card-history-check.cjs) воспроизводит частичную и полную приёмку, смену собственника, завершение и отмену вывоза. Она сверяет строки карточки, варианты фильтров и полный журнал остатков.

## Тип события истории КТК (V49)

Таблица `container_owner_history` хранит идентификаторы события, КТК и заявки, тип заявки, прежнего и нового собственников, состояния, время действия и реквизиты записи. V49 удалила operation_type, V51 — cancellation. Обычный container_owner_history_view возвращает оба признака по history_operation_type(order_type,old_status,new_status). cancellation=true только для CANCEL_ARRIVAL, CANCEL_DEPARTURE, CANCEL_RECEIVING_RESERVATION и CANCEL_SHIPPING_RESERVATION; для остальных допустимых событий false. V50 удаляет terminal_area_id и time_source полностью, без замены вычисляемыми колонками. В системе одна контейнерная площадка, её повторение в истории и отчёте не требуется. Даты occurred_at/created_at, собственники, отмены, связи и смысл событий сохраняются. Новых хранимых колонок и материализованных представлений нет.

Функция использует только вид заявки и два складских статуса. Собственники не участвуют в вычислении; cancellation является результатом вычисления и отдельно не задаётся. Допустимы 13 сочетаний, соответствующие девяти типам событий:

| order_type | old_status | new_status | Вычисляемый operation_type |
| --- | --- | --- | --- |
| RECEIVING_ORDER | NULL или DEPARTED | EXPECTED | RESERVE_RECEIVING |
| RECEIVING_ORDER | EXPECTED | ON_TERMINAL | ARRIVAL |
| RECEIVING_ORDER | EXPECTED | DEPARTED | CANCEL_RECEIVING_RESERVATION |
| RECEIVING_ORDER | ON_TERMINAL | DEPARTED | CANCEL_ARRIVAL |
| SHIPPING_ORDER | ON_TERMINAL | RESERVED_OUT | RESERVE_SHIPPING |
| SHIPPING_ORDER | RESERVED_OUT | DEPARTED | DEPARTURE |
| SHIPPING_ORDER | RESERVED_OUT | ON_TERMINAL | CANCEL_SHIPPING_RESERVATION |
| SHIPPING_ORDER | DEPARTED | ON_TERMINAL | CANCEL_DEPARTURE |
| SERVICE_ORDER | EXPECTED / ON_TERMINAL / RESERVED_OUT / DEPARTED | тот же статус | OWNER_CHANGE |

Таблица охватывает события всех версий. С V62 новое событие OWNER_CHANGE создаётся при подтверждении передачи свободного КТК в состоянии ON_TERMINAL. Исторические события в других состояниях по-прежнему распознаются.

Для SERVICE_ORDER правило соответствует нынешнему MVP, где поддерживается только CHANGE_OWNER. Новые виды услуг или переходы требуют отдельного изменения контракта и миграции. Неизвестный тип заявки/статус или неподдерживаемое сочетание дают NULL; history_transition_known запрещает такую запись. До V51 history_cancellation_matches_transition запрещал противоречивый сохранённый флажок отмены; с V51 физического флажка и этого ограничения нет. LEGACY/UNKNOWN не подставляются автоматически. Перед удалением поля миграция сверяет каждую старую запись: вычисление должно в точности совпасть с сохранённым типом и признаком отмены. Любое расхождение останавливает V49 одной транзакцией; история не исправляется автоматически.

Backend записывает исходные реквизиты события, затем читает вычисленный тип из VIEW для обработки хранения. Признак отмены не передаётся в запись отдельным аргументом. Отдельная Java-формула удалена. Восстановление предыдущих заявок, проверки границ и источников и API истории используют тот же VIEW. Отчёт читает order_type непосредственно из событий границ; тип операции истории при этом не пересчитывается отдельной Java-формулой. Защита связанного события сохраняет неизменность исходных статусов и вида заявки, поэтому его вычисляемый смысл также нельзя подменить. Технический порядок created_at и бизнес-время occurred_at не меняются.

Проверки V49: [history-operation-check.cjs](scripts/history-operation-check.cjs). capture на V48 и verify на V49 сравнивают все остальные бизнес-поля и последовательности, полную историю с вычисленным типом, исходные поставки и полный активный отчёт. api-capture/api-verify сравнивают побайтно историю каждого КТК с резервированиями и без них, отчёт API и полный CSV. ## Учёт вагонов

При создании ЖД-поставки можно выбрать собственника вагонов по умолчанию. В черновике его можно уточнить для отдельного вагона накладной. Подтверждение ставит вагоны в ожидание, выполнение поставки переводит их в свободный остаток (`ON_TERMINAL`). Номерной вывоз резервирует вагон при подтверждении и списывает при выполнении. Отмена возвращает предыдущее состояние. Если по вагону уже прошёл другой документ, сначала нужно отменить последующую операцию.

## Статусы строк КТК

V37 добавляет status в receiving_order_container (автопоставка), waybill_container (ЖД-поставка) и shipping_order_container (вывоз). Допустимы только NULL — статус не установлен, UPLOADED — подтверждено, FINISHED — выполнено. Подтверждение рейса переводит строки его заявок в `UPLOADED`. Сервер обрабатывает результат по паре «заявка + физический КТК». Строка переходит в `FINISHED`, и только у этого КТК меняются остаток, история и заезд. При интеграционном пакете бизнес-время берётся из `eventDateTime`, при ручном выполнении — из рабочего календаря. См. [входящие результаты TOS](BACKEND_ALIGNMENT.md#входящие-результаты-tos).

Ручной результат номерного документа передаётся через `POST /api/receiving-orders/{id}/events` с телом `{"eventCode":"UNLOAD_FINISH","containerId":"<UUID КТК>"}`. Для вывоза используется `POST /api/shipping-orders/{id}/events` и `LOAD_FINISH`. Кнопка вызывает тот же обработчик без `containerId`: сервер применяет результаты к оставшимся строкам в одной транзакции. Повтор принятого результата сохраняет уже записанные дату и события. КТК вне состава заявки отклоняется. Пакеты, поступившие отдельными запросами, фиксируются независимо.

Пока есть незавершённые строки, заявка остаётся `ACCEPTED`. Когда все строки получили `FINISHED`, сервер завершает заявку, обновляет статус рейса. При отмене частично выполненной заявки снимаются резервы ожидающих КТК и отменяются факты только выполненных строк. Проверки последующих операций выполняются для всего пакета отмены.

При отмене подтверждённой или выполненной заявки status её строк сбрасывается в NULL. Отмена остаётся в статусе заявки и отдельной истории, CANCELED в перечисление строк не добавлен. При отмене ЖД-поставки сброс происходит до освобождения накладных; их повторное использование создаёт новый период с исходной строкой waybill_container и новым контекстом заявки. Ранее отменённый период и его история сохраняются.

## Фактическая поставка и собственники (V59)

Рабочая дата определяется по времени события в Europe/Moscow. Ссылки регистра, заезда и периода имеют следующие назначения.

| Таблица | Поля и связи |
| --- | --- |
| container_visit | `id`, `container_id`, `receiving_container_owner_history_id`, `shipping_container_owner_history_id`, `cancellation_container_owner_history_id`. Начальное событие обязательно. |
| container_period | `id`, `container_visit_id`, `client_id`, `start_container_owner_history_id`, `service_order_id`. По ссылке на событие доступны `occurred_at` и заявка. По заявке действующего заезда и КТК определяется строка приёмки, а `service_order_container.container_period_id` указывает на период смены собственника. |
| container_owner | прежние id/container_id и аудит; receiving_order_id, shipping_order_id, status EXPECTED/ON_TERMINAL/RESERVED_OUT/DEPARTED, version. receiving_order_id указывает на текущую поставку в ожидании и после приёмки. Обязательное поле client_id ссылается на client.id и хранит текущего собственника |

Подтверждение поставки создаёт только состояние EXPECTED и receiving_order_id в container_owner, а также событие RESERVE_RECEIVING в истории. Собственник ожидаемой поставки хранится в container_owner.client_id; событие резервирования сохраняет его для аудита и отмены. Это ещё не хранение. Только фактическое выполнение (UNLOAD_FINISH / ARRIVAL) создаёт container_visit с обязательной ссылкой receiving_container_owner_history_id на событие приёмки, а также первый фактический период со ссылкой на ARRIVAL. В регистре сохраняется receiving_order_id. По этой ссылке берётся номер поставки для уведомления, если складское состояние КТК блокирует другую заявку. Уникальность события `ARRIVAL` по паре «заявка поставки + КТК» и уникальная ссылка на него в заезде защищают от повторного открытия. В представлении container_owner_current его идентификатор вычисляется после фактической приёмки.

Представление `container_visit_facts` берёт идентификаторы заявок из `order_id` событий приёмки и вывоза, а даты — из `occurred_at` по `Europe/Moscow`. Для поставки `visit_receiving_tasks` находит строки по заявке и КТК в текущем авто- или ЖД-составе. При действующем заезде должна существовать ровно одна завершённая строка. Для вывоза используется уникальная строка `shipping_order_container` по заявке и КТК. После повторного использования ЖД-накладной строка относится к новой заявке. В отменённом заезде остаются исходная заявка, КТК и события приёмки и отмены. Заполненная ссылка `cancellation_container_owner_history_id` означает, что поставка отменена. У КТК может быть только один заезд с пустыми ссылками на вывоз и отмену. Отмена вывоза очищает ссылку на вывоз и снова открывает тот же заезд.

Подтверждение передачи записывает период в существующем заезде. При фактическом вывозе обновляется тот же container_visit; новая строка назначения не создаётся, дата вывоза в container_period не записывается. Следующая передача определяет конец предыдущего периода, вывоз завершает последний с включением дня вывоза. В container_owner.shipping_order_id хранится текущий либо последний действующий вывоз. Для первого заезда до начала вывоза ссылка пуста. Повторная поставка создаёт новый визит только при её фактическом выполнении.

Отмена ожидания поставки не создаёт и не аннулирует визитов или назначений: снимается резерв, по истории восстанавливаются прежний собственник и ссылка на предыдущую действующую поставку. Если такой поставки не было, receiving_order_id остаётся пустым. Отмена выполненной поставки аннулирует её визит и назначения, сохраняя их и историю; новый OUTSIDE_STORAGE не создаётся. Восстановленный собственник записывается в container_owner.client_id и событие отмены; датированная актуализация учитывает это событие. Отмена вывоза очищает фактические реквизиты вывоза существующего визита, поэтому последний интервал снова вычисляется без конца. Отменённую транспортную заявку нельзя подтвердить повторно: создаётся новая. Накладную отменённой поставки можно использовать в новой заявке.

V68 сверяет прежние записи с фактическими событиями и строками документов, затем переносит планы и отзывы в строки заявок. Если исторические `EXPECTED` или `OUTSIDE_STORAGE` нельзя однозначно представить фактическим периодом, миграция выводит идентификатор записи и останавливается. [Порядок переноса](database/README.md#фактические-периоды-хранения-v68)

container_storage_period — обычный VIEW с прежними семью колонками; конец вычисляется через следующую запись в визите либо shipping. container_storage_period_at(date) исключает будущие начала и скрывает будущие окончания; его используют отчёт API/CSV и container_storage_period_view. Статус OPEN/CLOSED/CANCELLED вычисляется только для совместимости. container_storage_period_origin и storage_arrival_history/storage_receiving_order читают прямую связь с визитом. В `container_owner_history_view` поле `container_period_id` вычисляется. Для приёмки и смены собственника это период, который открывает само событие. Для ожидания поставки и его отмены значение пустое. Для остальных операций учитываются заезд и периоды, известные к моменту записи, и фактическое время операции. Передача задним числом сохраняет ссылку прежнего резерва на исходный период. При отмене вывоза после аннулирования повторной поставки ссылка ведёт в период прежнего заезда.

V56 проверяет совпадение прежних полных интервалов перед переводом ожидающих заявок в назначения. Утраченные при прежнем переводе EXPECTED → STORAGE назначения восстанавливаются из истории без изменения самих событий. Существующие SCHEDULED материализуются с закреплёнными в V55 визитом/собственником; расхождение останавливает миграцию. При календаре раньше имеющихся событий текущий собственник закономерно меняется на выбранную дату. Перед выпуском отчёт/CSV проверяются на восстановленной копии; миграция транзакционная.

Ограничения БД проверяют принадлежность строк документов, непрерывность периодов, соответствие дат и собственника событиям, единственный незавершённый визит и складское состояние. Дата и источник назначения неизменяемы; удаление назначений запрещено. Операции выполняются одной транзакцией с блокировкой физических КТК в стабильном порядке. version увеличивается при переходе состояния; гарантия от конкуренции основана на блокировках, а не на версии из клиента.

## Периоды хранения КТК

История КТК возвращает containerPeriodId и previousContainerPeriodId для перехода в отчёт. Основной адрес отчёта — /api/container-periods. Прежний адрес /api/container-storage-periods поддерживает те же фильтры, визиты и экспорт.

Раздел /container-storage и GET /api/container-periods сохраняют прежние поля API, фильтры, UUID, точное время событий и 17 колонок CSV без фильтра периода хранения. Собственник берётся из начального события и совпадает с `container_period.client_id` по проверке целостности. Вся цепочка отменённого receiving скрывается из отчёта.

В таблице хранения и CSV время начала и окончания периода отображается в UTC. Фильтры `arrivalFrom` и `arrivalTo` выбирают даты начала по UTC. Дни вычисляются по occurred_at точных событий границ в Europe/Moscow и ограничиваются рабочей датой либо asOf. Дни приёмки, передачи и вывоза входят в хранение. При приёмке 15 сентября, передаче 17 сентября и вывозе 20 сентября визит длится 6 дней. У прежнего собственника 3 дня, у нового — 4. При нескольких передачах за одни московские сутки каждый период владения включает этот день. Будущая передача не показывает ни нового собственника, ни будущий конец прежнего периода до даты расчёта. Дату начала даёт `occurred_at` начального события. Конец определяется по событиям заезда. Льготные дни и стоимость хранения здесь не рассчитываются.

### Текущий отчёт

UI группирует отчёт по container_visit: основная строка «Поставка → Вывоз», дочерние строки — собственники и передачи в той же таблице под общими заголовками. В основной строке показаны общее число дней, даты и ссылки на receiving/shipping, клиент/собственник, транспорт, перевозчик/отправитель/получатель и груз обеих сторон. Длительность визита считается от приёмки до вывоза или даты расчёта включительно. Каждая дата учитывается в визите один раз. Во вложенных строках — собственник, дни, начало/конец и документы границ. Повторные receiving не объединяются по номеру КТК.

GET /api/container-periods/visits принимает query, periodId, asOf, page, size и необязательный период хранения. Параметр month задаёт календарный месяц в формате ГГГГ-ММ. Для диапазона используются storedFrom и storedTo. Обе границы включены. Номер КТК и период можно задавать независимо. Визит подходит, если хотя бы один день от фактической приёмки до вывоза приходится на выбранный период. Для открытого визита последним днём считается дата расчёта. Дни определяются по Москве. Выбор периода сохраняет полные даты, дни и цепочку собственников визита на дату расчёта. Сначала выбирается страница целых визитов, затем все их видимые периоды с прежними реквизитами; счётчик — число визитов. Внутри визита порядок: occurred_at, технический created_at, id события. Сортировка визитов — дата receiving по убыванию, затем container_visit.id. periodId выбирает визит целиком, UI раскрывает его и выделяет период. Чтение выполняется на одном снимке транзакции; не изменяет БД. Будущие границы и отменённые receiving скрываются по прежним правилам. Группировка визитов не добавляет таблиц; группировка появилась в V58.

При выборе месяца или диапазона backend возвращает `storageDaysInPeriod` в каждой строке визита и собственника. Для каждого собственника это число московских календарных дней пересечения его хранения с фильтром. Если дата передачи попала в фильтр, за неё начисляется по одному дню прежнему и новому собственникам. У открытого визита расчёт ограничен рабочей датой. Периоды с нулевым пересечением видны, их дни за весь срок сохраняются в `storageDays`. В строке визита показано пересечение календарных дат самого заезда с фильтром.

Прежний GET /api/container-periods сохраняет формат и фильтры. Выгрузка CSV поддерживает те же month, storedFrom и storedTo для отбора целых визитов. Параметр visitPeriodId выгружает визит целиком при переходе из истории. При выборе периода CSV добавляет «Дней хранения в периоде» после «Дней хранения». Без выбора периода порядок 17 колонок следующий:

1. Номер КТК.
2. Собственник КТК — собственник периода, new_client_id точного события начала.
3. Дней хранения.
4. Начало периода.
5. Событие — «Поставка» или «Смена собственника».
6. Заявка — номер заявки начала со ссылкой в UI.
7. Конец периода.
8. Событие — «Вывоз» или «Смена собственника».
9. Заявка — номер заявки окончания со ссылкой в UI.
10. Клиент/Собственник поставки.
11. Транспорт поставки — «Авто» или «ЖД».
12. Грузоперевозчик/грузоотправитель поставки.
13. Груз поставки.
14. Клиент/Собственник вывоза.
15. Транспорт вывоза — «Авто» или «ЖД».
16. Грузоперевозчик/грузополучатель вывоза.
17. Груз вывоза.

Даты берутся из occurred_at точных start_history_id/end_history_id, типы — по order_type, номера — по order_id. Номера отображаются без знака №. В API сохранены прежние id, containerId, containerName, ownerName, arrivalAt, departureAt, status, storageDays и реквизиты startOrder*/endOrder*. Статус используется для фильтрации прежнего API; отдельной колонки статуса в отчёте нет. Начальный и конечный блоки содержат одинаково названные колонки «Событие», «Заявка», расположенные непосредственно после соответствующей даты. У открытого периода три поля окончания пусты.

Поставка — исходная заявка физического заезда, найденная по точной цепочке через storage_arrival_history(p.id). Она сохраняется общей для периодов после смен собственника; последняя поставка по дате и текущий собственник регистра не подставляются. Клиент берётся из receiving_order.client_id, собственник КТК — из receiving_order_container.owner_container_id либо waybill_container.owner_container_id, с резервным значением default_container_owner_id заявки. В колонке показаны два значения через « / », даже если совпадают; собственник поставки может отличаться от собственника периода. Транспорт — receiving_order.transport_type. Для авто перевозчик берётся из route.client_related_entity_id рейса заявки; для ЖД грузоотправитель — организация по receiving_order.shipper_id. Груз автопоставки читается из receiving_order_container_item конкретного КТК, ЖД-поставки — из waybill_product его исходной накладной. Используется справочное etsng_code.code, которое в MVP может содержать код и подпись; несколько грузов объединяются через «; » без дублей. Несколько грузов не размножают строки отчёта.

Вывоз определяется только точным end_history_id с order_type=SHIPPING_ORDER. Его клиент — shipping_order.client_id, собственник — сохранённый shipping_order_container.container_owner_id того же физического КТК. Транспорт — shipping_order.transport_type. Для авто перевозчик берётся из рейса вывоза; для ЖД грузополучатель — из client_related_entity по shipping_order.consignee_id. Груз вывоза читается отдельно из shipping_order_container_item, не копируется из поставки. При открытом периоде или окончании сменой собственника весь блок вывоза пуст. Отмена вывоза снова открывает последний период и очищает его реквизиты вывоза; отмена приёма скрывает всю цепочку, сохраняя историю. Отсутствующий груз/перевозчик/отправитель/получатель остаётся пустым, не выводится из другого документа.

Новые поля API: receivingClientName, receivingOwnerName, arrivalTransport, arrivalParty, arrivalCargo, shippingClientName, shippingOwnerName, departureTransport, departureParty, departureCargo. В транспортных полях сохраняются VEHICLE/RAILWAY; UI и CSV показывают «Авто»/«ЖД». Границы и дни рассчитываются по прежним правилам выше. Сортировка — дата начала по убыванию, затем id. clientId сохраняет смысл клиента исходной поставки; query, periodId, статусы, диапазон дат начала и asOf сохраняются. asOf по умолчанию billing_today(), не позже рабочей даты; более поздние начала исключаются. Описание плоской выборки относится к прежнему endpoint; группировка UI описана выше. Обычные VIEW не изменены.

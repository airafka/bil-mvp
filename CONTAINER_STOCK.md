# Собственники и учёт КТК

Складские правила сверены с кодом 10.11.2026; учёт периодов хранения добавлен 16.11.2026. Основные реализации: [ContainerStockService](backend/src/main/java/ru/billing/app/containerstock/ContainerStockService.java), [OwnershipOrderService](backend/src/main/java/ru/billing/app/containerstock/OwnershipOrderService.java), [ReturnReceivingService](backend/src/main/java/ru/billing/app/comprehensiveserviceorder/ReturnReceivingService.java).

## Роли и источники

Клиент услуги, грузоотправитель/получатель и собственник КТК — разные роли. Собственник не выводится сервером только из клиента заявки.

| Данные | Источник |
| --- | --- |
| Исходное текстовое обозначение собственника накладной | waybill_container.owner |
| Собственник поставки по умолчанию | receiving_order.default_container_owner_id |
| Выбранный собственник отдельного КТК ЖД-поставки | waybill_container.owner_container_id |
| Собственник строки автопоставки | receiving_order_container.owner_container_id |
| Текущий собственник и состояние физического КТК | container_owner |
| Зафиксированный собственник вывоза | shipping_order_container.owner_container_id |
| История изменений / события | container_owner_history / container_movement |
| Периоды фактического хранения | container_storage_period |

В поставке поле собственника по умолчанию обязательно; явный собственник строки имеет приоритет при создании. Черновик допускает индивидуальное изменение. Изменение общего собственника в сохранённой поставке обновляет её строки. В мастере услуги индивидуальные значения сохраняются отдельно и передаются при создании.

В мастере комплексной услуги выбор клиента предварительно заполняет поле собственника этим клиентом. Это удобство формы с возможностью ручного изменения, а не правило определения владельца в регистре. Смена клиента в этом мастере снова подставляет нового клиента; выбор договора не сбрасывает ручного собственника.

## Жизненный цикл

| Операция | Условие | Результат |
| --- | --- | --- |
| Подтверждение поставки через рейс | КТК отсутствует в регистре или ранее выбыл | EXPECTED; собственник из строки поставки |
| Выполнение поставки | EXPECTED от этой поставки | ON_TERMINAL, событие UNLOAD_FINISH |
| Подтверждение вывоза через рейс | КТК свободен: ON_TERMINAL | RESERVED_OUT; собственник вывоза фиксируется из регистра |
| Выполнение вывоза | RESERVED_OUT от этого вывоза | DEPARTED, событие LOAD_FINISH |

UNLOAD_FINISH и LOAD_FINISH фиксируются ручным выполнением транспортных заявок, без подключения TOS. Вывоз меняет состояние КТК, но не назначает нового собственника регистра. При выполнении поставки также сохраняется собственник, уже установленный в регистре при её подтверждении или последующей смене собственника.

container_owner содержит текущую запись физического КТК, а не отдельную запись на каждую перевозку. В остатки входят ON_TERMINAL и RESERVED_OUT. EXPECTED и DEPARTED сохраняются в общем регистре и истории, но не означают свободный КТК для вывоза.

Операции блокируют строки КТК; изменение статуса заявки, регистра и события выполняется транзакционно. Повторная фиксация одного события для заявки/КТК не создаёт дубль container_movement.

## Отмена заявок и рейсов

Транспортная заявка может перейти из DRAFT, CONFIRMED или COMPLETED в CANCELLED. Повторная отмена возвращает текущий результат без повторного изменения остатков. Возврата отменённой заявки в работу нет: оформляется новая. Причина обязательна, исходный статус и время сохраняются в order_cancellation.

| Отменяемая операция | Проверка | Изменение регистра |
| --- | --- | --- |
| Черновик поставки/вывоза | Нет активных зависимых документов услуги | Остатки не меняются |
| Подтверждённая поставка | EXPECTED принадлежит этой поставке | DEPARTED; восстанавливаются прежний собственник и ссылка на предыдущую поставку |
| Выполненная поставка | ON_TERMINAL принадлежит этой поставке | То же восстановление; КТК исключается из физических остатков |
| Подтверждённый вывоз | RESERVED_OUT принадлежит этому вывозу | ON_TERMINAL; снимается резерв, восстанавливается ссылка на предыдущий вывоз |
| Выполненный вывоз | DEPARTED принадлежит этому вывозу | ON_TERMINAL; КТК снова в свободных остатках |

Если до самой первой поставки записи собственника не было, после её отмены запись сохраняется в DEPARTED, с текущим собственником и пустой ссылкой на предыдущую поставку. Отмена вывоза сохраняет **текущего** собственника, включая смену собственника после подтверждения вывоза.

Отмена выполненной поставки запрещена, если КТК зарезервирован для вывоза, уже вывезен или прошёл более позднюю поставку. Отмена выполненного вывоза запрещена после резервирования следующего прихода, приёмки или последующего вывоза. Проверяется не только статус, но и принадлежность текущей операции заявке. Сначала отменяются последующие операции. Ошибка содержит номера КТК и связанной транспортной заявки; конфликты состава собираются вместе, без частичного изменения остатков.

До резервирования container_stock_reservation сохраняет прежнего собственника и ссылки на поставку/вывоз. V29 восстанавливает эти снимки для прежних операций из существующей истории; для документа без достаточной истории отмена блокируется и требует сверки остатков. Отсутствующий собственник никогда не выводится из клиента заявки.

История переходов сохраняется, обратный переход отмечается cancellation=true. Складские события отменённой заявки получают active=false. В карточке отменённой заявки используется неизменяемый снимок состава из order_cancellation: последующее переиспользование накладной не переписывает её историю. Накладные отменённой ЖД-поставки освобождаются для новой заявки. Отменённый вывоз/возврат освобождает распределение КТК, позволяя создать замену. Отметка «Возврат не нужен» не меняет складские переходы; при отмене выполненного автовывоза созданное по ней начисление снимается по правилам BACKEND_ALIGNMENT.md. У вывоза-замены возврат требуется по умолчанию.

Отмена рейса отменяет все его заявки одной транзакцией. Ошибка в любом документе откатывает весь пакет. При поштучной отмене рейс сохраняет оставшиеся заявки: он завершается, когда все активные заявки выполнены, и получает CANCELLED, когда отменены все. Проверки зависимых документов услуги и счетов описаны в [BACKEND_ALIGNMENT.md](BACKEND_ALIGNMENT.md).

Проверки полномочий основной системы не переносятся в приложение без авторизации. Начисления и счета MVP требуют дополнительных проверок отмены, которых нет в этой части dev_back. Это соответствие складских правил в локальном сценарии, а не копия всей интеграционной системы.

Проверки MVP: [правила переходов](backend/src/test/java/ru/billing/app/containerstock/ContainerStockPolicyTest.java), [сценарии API на изолированной БД](scripts/order-cancellation-check.cjs), [проверка интерфейса](scripts/order-cancellation-ui.cjs). ## Собственник вывоза

Ручной выбор КТК в вывозе автоматически подставляет собственника из регистра. ЗПУ, класс опасности и порожность ручного вывоза задаются отдельно. Автоматически созданный вывоз комплексной услуги переносит доступные данные исходной поставки/накладной.

Только DRAFT актуализируется при смене собственника в регистре. При подтверждении собственник записывается в вывоз и фиксируется: последующие CHANGE_OWNER и LOAD_FINISH не переписывают его в CONFIRMED/COMPLETED. Текущий собственник регистра поэтому может отличаться от исторического собственника подтверждённого вывоза.

## Собственник возврата

Для возврата исходному клиенту:

- При DRAFT исходного вывоза сервер берёт индивидуального собственника из исходной ЖД-поставки/накладной, с резервным значением её default. Это позволяет оформить ранний возврат до появления КТК в регистре.
- При CONFIRMED/COMPLETED исходного вывоза берётся сохранённый собственник вывоза.
- Если собственника нельзя определить, создание отклоняется; клиент услуги не используется как скрытая подстановка.

При возврате другому клиенту нужен явный ownerClientId. Форма предварительно выбирает нового клиента возврата, но позволяет назначить любого собственника из справочника. Выбранное значение применяется к выбранным КТК новых возвратных поставок, не изменяя исходные документы.

В черновике возвратной поставки собственника можно изменить. При её подтверждении в регистр попадёт выбранное значение. Наличие возврата не означает автоматического прихода: исходный вывоз сначала должен быть выполнен, затем возврат проходит подтверждение и выполнение.

## Смена собственника

service_order — самостоятельная заявка с service=CHANGE_OWNER. Статусы: DRAFT и DONE. При создании и подтверждении обязателен хотя бы один КТК из регистра. Нельзя одновременно выбрать его в другую черновую заявку на смену собственника.

При выборе проверяется отличие текущего собственника от нового. Подтверждение блокирует КТК, перепроверяет наличие собственника и обновляет регистр, историю и черновые вывозы в одной транзакции. Складской статус КТК сохраняется. Подтверждённые вывозы сохраняют собственника своего подтверждения. Выполненная заявка на смену собственника недоступна для редактирования и повторного выполнения.

Ограничение текущего accept: он не сравнивает собственника с его значением на момент выбора и повторно не проверяет отличие от нового. Старое описание такой повторной проверки было шире фактической реализации; изменение алгоритма требует отдельной доработки.

## Состав и редактирование

При ручном создании заявки по умолчанию одна строка КТК. В ручных черновиках авто-поставки/вывоза и ЖД-вывоза можно добавлять номерные КТК. В ЖД-вывозе добавление идёт в уже выбранный вагон.

Прямое добавление запрещено для ЖД-поставки по накладным, заявок комплексной услуги и связанных возвратов: их состав управляется источником. Подтверждённые и выполненные заявки также не допускают добавления. Метаданные и новые строки сохраняются совместно; ошибочный состав откатывает пакет.

В КП-ЖД собственник меняется в строке КТК или массовым выбором. Массовый выбор накладной/вагона включает свёрнутые строки. Это редактирование собственника поставки, а не выполнение CHANGE_OWNER в регистре. Подробности интерфейса — в [FRONTEND_STANDARD.md](FRONTEND_STANDARD.md).


## Статусы строк КТК

V37 добавляет status в receiving_order_container (автопоставка), waybill_container (ЖД-поставка) и shipping_order_container (вывоз). Допустимы только NULL — статус не установлен, UPLOADED — подтверждено, FINISHED — выполнено. Подтверждение рейса переводит строки его заявок в UPLOADED; выполнение заявки переводит её строки в FINISHED. В MVP это имитация задания внешней системе: интеграция ещё не подключена, отдельного выполнения одного КТК через интерфейс нет.

ContainerTaskRows проверяет исходный статус и однозначность строки по КТК. Только FINISHED может стать источником фактического приёма/вывоза и периода хранения. Статус строки, остатки, история, период, начисления и статус заявки меняются в одной транзакции; ошибка любой строки откатывает всю операцию. Повторное выполнение не создаёт повторных фактов.

При отмене подтверждённой или выполненной заявки status её строк сбрасывается в NULL. Отмена остаётся в статусе заявки и отдельной истории, CANCELED в перечисление строк не добавлен. При отмене ЖД-поставки сброс происходит до освобождения накладных; их повторное использование создаёт новый период с исходной строкой waybill_container и новым контекстом заявки. Ранее отменённый период и его история сохраняются.

## Периоды хранения КТК

Раздел /container-storage и GET /api/container-storage-periods показывают одну строку на непрерывное пребывание КТК на площадке. Основная реализация — [ContainerStorageService](backend/src/main/java/ru/billing/app/containerstock/ContainerStorageService.java), [отчёт](backend/src/main/java/ru/billing/app/containerstock/ContainerStorageController.java), схема и первоначальное восстановление — [V33](backend/src/main/resources/db/baseline/V33__container_storage_periods.sql).

container_storage_period хранит КТК/площадку, поставку/вывоз, receiving_at/shipping_at, клиента и собственника при приёме, снимок груза и порожности, статус OPEN/CLOSED/CANCELLED. Поля периода needs_review, review_reason и version удалены V38. receiving_history_id и shipping_history_id ссылаются на факты в container_owner_history. Обратная ссылка storage_period_id объединяет историю периода, включая снятие резерва, отменённые вывозы и смену собственника. Источник приёма — ровно одна из ссылок receiving_order_container_id (авто) и waybill_container_id (ЖД); источник вывоза — shipping_order_container_id. receiving_order_id сохраняет исходную заявку поставки. shipping_order_id удалён из периода миграцией V40: заявка вывоза определяется через shipping_order_container_id → shipping_order_container.shipping_order_id. Составные внешние ключи проверяют совпадение физического КТК, для автопоставки также исходной заявки. Отмена вывоза находит закрытый период по его строке КТК; API отчёта по-прежнему возвращает вычисленные shippingOrderId и shippingOrderNumber. При отмене вывоза его ссылка на строку очищается вместе с окончанием периода; при отмене приёма исходная ссылка остаётся. V37 отмечала старые неразрешимые связи для проверки. V38 требует предварительно разрешить такие периоды и сохраняет обязательность точного источника приёма и вывоза. Новые периоды без однозначной выполненной строки не создаются.

История хранит operation_type, occurred_at, time_source, terminal_area_id и storage_period_id вместе с КТК, заявкой, прежним/новым собственником и состоянием. V39 удаляет target_history_id, source_system, source_operation_key, reason, needs_review и review_reason. Отмена определяется по cancellation, operation_type, прежнему/новому состоянию и ссылке на заявку; причина остаётся в order_cancellation и карточке заявки. Исходные события сохраняются. Повторное выполнение и отмена защищены проверками статусов, принадлежности операции, блокировками заявок/КТК и транзакциями. Время container_movement берётся по ID созданной записи истории, без поиска по удалённому ключу источника. Для новых операций MVP occurred_at — рабочая дата MVP и системное время ручного выполнения после блокировки КТК; плановые даты заявки не используются как фактические. Внешние события TOS и частичное выполнение заявки не добавлены.

| Действие | Изменение периода |
| --- | --- |
| Подтверждение поставки | Период не создаётся |
| Выполнение поставки | Создаётся OPEN с фактом приёма |
| Резервирование под вывоз, смена собственника | Начало и длительность хранения не меняются |
| Выполнение вывоза | Записывается окончание, статус CLOSED |
| Отмена подтверждённой поставки | Периода нет; сохраняется отмена резервирования |
| Отмена подтверждённого вывоза | Период остаётся OPEN; резерв снимается |
| Отмена выполненной поставки | Период становится CANCELLED, начало и история сохраняются |
| Отмена выполненного вывоза | Тот же период становится OPEN; поля окончания очищаются, исходный вывоз и его отмена остаются в истории |
| Повторный фактический заезд | Новый период с другим id |

Существующие проверки последовательности операций, зависимых заявок, рейсов и счетов сохраняются. Нельзя автоматически открыть старый период после следующего заезда или аннулировать приём с действующим вывозом. Изменение заявки, остатков, истории, периода и начислений выполняется атомарно. Дополнительно выполнение вывоза/отмена факта блокируются при отсутствии однозначного периода; проблемные старые данные не исправляются догадкой. Повторное выполнение/отмена не создаёт повторного периода или события.

Количество дней не хранится и не увеличивается ежедневным заданием. Для открытого периода: дата расчёта минус дата прибытия плюс 1. Для закрытого — минимум даты расчёта и даты вывоза минус дата прибытия плюс 1. Используются календарные даты Europe/Moscow; приём/вывоз в один день дают 1 день. По умолчанию дата расчёта — billing_today(), то есть дата общего календаря MVP. Явная asOf не может быть позже рабочей даты. Переключение календаря пересчитывает длительность без записи в период; периоды с прибытием позже даты расчёта не показываются. Дата расчёта не меняет текущее состояние документов и признак «В стоке». Аннулированные периоды не получают действующего количества дней. Льготные дни и стоимость не рассчитываются. Период идентифицируется по id; согласованность операций обеспечивают транзакции и блокировки записей.

V33 однократно воспроизводит старую историю с учётом резервов и отмен. Время берётся из соответствующего container_movement, при его отсутствии — из created_at истории (UTC); источник показан в отчёте. Дубли приёмов, вывозы без однозначного приёма и расхождения с остатками требуют проверки. В V33 неоднозначные открытые периоды исключались из уникального индекса. Перед V38 такие периоды должны быть разобраны: миграция отклоняется при наличии needs_review=true, не стирая сведения о проблеме. После V38 уникальность открытого периода по КТК/площадке действует для всех строк. Перед V39 также должны быть разобраны записи истории с needs_review=true: миграция останавливается, не удаляя сведения о проблеме. После V39 поля проверки истории и endpoint /issues удалены. Отдельного интерфейса ручного исправления дат и разрешения неоднозначностей пока нет.

Грузоотправитель берётся из receiving_order.consignor, грузополучатель — из shipping_order.consignee_id. Перевозчики для автопоставки и автовывоза берутся из соответствующих route.client_related_entity_id; они не заменяются грузоотправителем или грузополучателем.

Для отображения клиента/собственника вывоза отчёт читает клиента shipping_order и собственника точной строки по shipping_order_container_id; текущий собственник регистра не подставляется вместо сохранённого собственника вывоза.

Груз берётся только из состава соответствующей поставки и сохраняется при приёме. Справочное поле ЕТСНГ в MVP содержит код и наименование вместе (например, «011005 — Пшеница»); эта строка сохраняется в снимке. В таблице хранения отображается только наименование, без кода. Адрес грузополучателя не хранится и не придумывается для отчёта. При восстановлении ранее отменённой ЖД-поставки состав накладной уже мог быть отвязан: отсутствующие сведения о грузе остаются пустыми. Новые периоды сохраняют снимок до возможного освобождения накладной.

Проверки с записью: [жизненный цикл и дни](scripts/storage-period-check.cjs), [восстановление истории](scripts/storage-migration-check.cjs). Они жёстко проверяют отдельные billing_storage_test (либо billing_storage_fields_test через STORAGE_TEST_DB) / billing_storage_replay_test; второй сценарий создаёт новую копию и отказывается заменять существующую. [UI-проверка](scripts/storage-period-ui.cjs) использует тестовые порты 3196/8196 и фикстуру первого сценария. Сценарии не предназначены для рабочей billing_next.

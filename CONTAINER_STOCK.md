# Собственники и учёт КТК

Сверено с кодом 10.11.2026. Основные реализации: [ContainerStockService](backend/src/main/java/ru/billing/app/containerstock/ContainerStockService.java), [OwnershipOrderService](backend/src/main/java/ru/billing/app/containerstock/OwnershipOrderService.java), [ReturnReceivingService](backend/src/main/java/ru/billing/app/comprehensiveserviceorder/ReturnReceivingService.java).

## Роли и источники

Клиент услуги, грузоотправитель/получатель и собственник КТК — разные роли. Собственник не выводится сервером только из клиента заявки.

| Данные | Источник |
| --- | --- |
| Исходное текстовое обозначение собственника накладной | waybill_container.owner |
| Собственник поставки по умолчанию | receiving_order.default_container_owner_id |
| Выбранный собственник отдельного КТК ЖД-поставки | waybill_container.owner_container_id |
| Собственник строки автопоставки | receiving_order_container.owner_container_id |
| Текущий собственник и состояние физического КТК | container_owner |
| Зафиксированный собственник вывоза | shipping_order_container.owner_container_id |
| История изменений / события | container_owner_history / container_movement |

В поставке поле собственника по умолчанию обязательно; явный собственник строки имеет приоритет при создании. Черновик допускает индивидуальное изменение. Изменение общего собственника в сохранённой поставке обновляет её строки. В мастере услуги индивидуальные значения сохраняются отдельно и передаются при создании.

В мастере комплексной услуги выбор клиента предварительно заполняет поле собственника этим клиентом. Это удобство формы с возможностью ручного изменения, а не правило определения владельца в регистре. Смена клиента в этом мастере снова подставляет нового клиента; выбор договора не сбрасывает ручного собственника.

## Жизненный цикл

| Операция | Условие | Результат |
| --- | --- | --- |
| Подтверждение поставки через рейс | КТК отсутствует в регистре или ранее выбыл | EXPECTED; собственник из строки поставки |
| Выполнение поставки | EXPECTED от этой поставки | ON_TERMINAL, событие UNLOAD_FINISH |
| Подтверждение вывоза через рейс | КТК свободен: ON_TERMINAL | RESERVED_OUT; собственник вывоза фиксируется из регистра |
| Выполнение вывоза | RESERVED_OUT от этого вывоза | DEPARTED, событие LOAD_FINISH |

UNLOAD_FINISH и LOAD_FINISH фиксируются ручным выполнением транспортных заявок, без подключения TOS. Вывоз меняет состояние КТК, но не назначает нового собственника регистра. При выполнении поставки также сохраняется собственник, уже установленный в регистре при её подтверждении или последующей смене собственника.

container_owner содержит текущую запись физического КТК, а не отдельную запись на каждую перевозку. В остатки входят ON_TERMINAL и RESERVED_OUT. EXPECTED и DEPARTED сохраняются в общем регистре и истории, но не означают свободный КТК для вывоза.

Операции блокируют строки КТК; изменение статуса заявки, регистра и события выполняется транзакционно. Повторная фиксация одного события для заявки/КТК не создаёт дубль container_movement.

## Собственник вывоза

Ручной выбор КТК в вывозе автоматически подставляет собственника из регистра. ЗПУ, класс опасности и порожность ручного вывоза задаются отдельно. Автоматически созданный вывоз комплексной услуги переносит доступные данные исходной поставки/накладной.

Только DRAFT актуализируется при смене собственника в регистре. При подтверждении собственник записывается в вывоз и фиксируется: последующие CHANGE_OWNER и LOAD_FINISH не переписывают его в CONFIRMED/COMPLETED. Текущий собственник регистра поэтому может отличаться от исторического собственника подтверждённого вывоза.

## Собственник возврата

Для возврата исходному клиенту:

- При DRAFT исходного вывоза сервер берёт индивидуального собственника из исходной ЖД-поставки/накладной, с резервным значением её default. Это позволяет оформить ранний возврат до появления КТК в регистре.
- При CONFIRMED/COMPLETED исходного вывоза берётся сохранённый собственник вывоза.
- Если собственника нельзя определить, создание отклоняется; клиент услуги не используется как скрытая подстановка.

При возврате другому клиенту нужен явный ownerClientId. Форма предварительно выбирает нового клиента возврата, но позволяет назначить любого собственника из справочника. Выбранное значение применяется к выбранным КТК новых возвратных поставок, не изменяя исходные документы.

В черновике возвратной поставки собственника можно изменить. При её подтверждении в регистр попадёт выбранное значение. Наличие возврата не означает автоматического прихода: исходный вывоз сначала должен быть выполнен, затем возврат проходит подтверждение и выполнение.

## Смена собственника

service_order — самостоятельная заявка с service=CHANGE_OWNER. Статусы: DRAFT и DONE. При создании и подтверждении обязателен хотя бы один КТК из регистра. Нельзя одновременно выбрать его в другую черновую заявку на смену собственника.

При выборе проверяется отличие текущего собственника от нового. Подтверждение блокирует КТК, перепроверяет наличие собственника и обновляет регистр, историю и черновые вывозы в одной транзакции. Складской статус КТК сохраняется. Подтверждённые вывозы сохраняют собственника своего подтверждения. Выполненная заявка на смену собственника недоступна для редактирования и повторного выполнения.

Ограничение текущего accept: он не сравнивает собственника с его значением на момент выбора и повторно не проверяет отличие от нового. Старое описание такой повторной проверки было шире фактической реализации; изменение алгоритма требует отдельной доработки.

## Состав и редактирование

При ручном создании заявки по умолчанию одна строка КТК. В ручных черновиках авто-поставки/вывоза и ЖД-вывоза можно добавлять номерные КТК. В ЖД-вывозе добавление идёт в уже выбранный вагон.

Прямое добавление запрещено для ЖД-поставки по накладным, заявок комплексной услуги и связанных возвратов: их состав управляется источником. Подтверждённые и выполненные заявки также не допускают добавления. Метаданные и новые строки сохраняются совместно; ошибочный состав откатывает пакет.

В КП-ЖД собственник меняется в строке КТК или массовым выбором. Массовый выбор накладной/вагона включает свёрнутые строки. Это редактирование собственника поставки, а не выполнение CHANGE_OWNER в регистре. Подробности интерфейса — в [FRONTEND_STANDARD.md](FRONTEND_STANDARD.md).

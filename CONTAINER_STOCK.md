# Собственники и учёт КТК

Складские правила и восстановление при отмене сверены с кодом 17.11.2026 (V43); хранение по собственникам действует с V42. Основные реализации: [ContainerStockService](backend/src/main/java/ru/billing/app/containerstock/ContainerStockService.java), [OwnershipOrderService](backend/src/main/java/ru/billing/app/containerstock/OwnershipOrderService.java), [ReturnReceivingService](backend/src/main/java/ru/billing/app/comprehensiveserviceorder/ReturnReceivingService.java).

## Роли и источники

Клиент услуги, грузоотправитель/получатель и собственник КТК — разные роли. Собственник не выводится сервером только из клиента заявки.

| Данные | Источник |
| --- | --- |
| Исходное текстовое обозначение собственника накладной | waybill_container.owner |
| Собственник поставки по умолчанию | receiving_order.default_container_owner_id |
| Выбранный собственник отдельного КТК ЖД-поставки | waybill_container.owner_container_id |
| Собственник строки автопоставки | receiving_order_container.owner_container_id |
| Текущий собственник и состояние физического КТК | container_owner |
| Зафиксированный собственник вывоза | shipping_order_container.owner_container_id |
| История изменений / события | container_owner_history / container_movement |
| Периоды фактического хранения | container_storage_period |

В поставке поле собственника по умолчанию обязательно; явный собственник строки имеет приоритет при создании. Черновик допускает индивидуальное изменение. Изменение общего собственника в сохранённой поставке обновляет её строки. В мастере услуги индивидуальные значения сохраняются отдельно и передаются при создании.

В мастере комплексной услуги выбор клиента предварительно заполняет поле собственника этим клиентом. Это удобство формы с возможностью ручного изменения, а не правило определения владельца в регистре. Смена клиента в этом мастере снова подставляет нового клиента; выбор договора не сбрасывает ручного собственника.

## Жизненный цикл

| Операция | Условие | Результат |
| --- | --- | --- |
| Подтверждение поставки через рейс | КТК отсутствует в регистре или ранее выбыл | EXPECTED; собственник из строки поставки |
| Выполнение поставки | EXPECTED от этой поставки | ON_TERMINAL, событие UNLOAD_FINISH |
| Подтверждение вывоза через рейс | КТК свободен: ON_TERMINAL | RESERVED_OUT; собственник вывоза фиксируется из регистра |
| Выполнение вывоза | Закрывается последний OPEN, сохраняется ссылка на точное событие DEPARTURE |

UNLOAD_FINISH и LOAD_FINISH фиксируются ручным выполнением транспортных заявок, без подключения TOS. Вывоз меняет состояние КТК, но не назначает нового собственника регистра. При выполнении поставки также сохраняется собственник, уже установленный в регистре при её подтверждении или последующей смене собственника.

container_owner содержит текущую запись физического КТК, а не отдельную запись на каждую перевозку. В остатки входят ON_TERMINAL и RESERVED_OUT. EXPECTED и DEPARTED сохраняются в общем регистре и истории, но не означают свободный КТК для вывоза.

Операции блокируют строки КТК; изменение статуса заявки, регистра и события выполняется транзакционно. Повторная фиксация одного события для заявки/КТК не создаёт дубль container_movement.

## Отмена заявок и рейсов

Транспортная заявка может перейти из DRAFT, CONFIRMED или COMPLETED в CANCELLED. Повторная отмена возвращает текущий результат без повторного изменения остатков. Возврата отменённой заявки в работу нет: оформляется новая. Причина обязательна, исходный статус и время сохраняются в order_cancellation.

| Отменяемая операция | Проверка | Изменение регистра |
| --- | --- | --- |
| Черновик поставки/вывоза | Нет активных зависимых документов услуги | Остатки не меняются |
| Подтверждённая поставка | EXPECTED принадлежит этой поставке | DEPARTED; восстанавливаются прежний собственник и ссылка на предыдущую поставку |
| Выполненная поставка | ON_TERMINAL принадлежит этой поставке | То же восстановление; КТК исключается из физических остатков |
| Подтверждённый вывоз | RESERVED_OUT принадлежит этому вывозу | ON_TERMINAL; снимается резерв, восстанавливается ссылка на предыдущий вывоз |
| Выполненный вывоз | DEPARTED принадлежит этому вывозу | ON_TERMINAL; КТК снова в свободных остатках |

Если до самой первой поставки записи собственника не было, после её отмены запись сохраняется в DEPARTED, с текущим собственником и пустой ссылкой на предыдущую поставку. Отмена вывоза сохраняет **текущего** собственника, включая смену собственника после подтверждения вывоза.

Отмена выполненной поставки запрещена, если КТК зарезервирован для вывоза, уже вывезен или прошёл более позднюю поставку. Отмена выполненного вывоза запрещена после резервирования следующего прихода, приёмки или последующего вывоза. Проверяется не только статус, но и принадлежность текущей операции заявке. Сначала отменяются последующие операции. Ошибка содержит номера КТК и связанной транспортной заявки; конфликты состава собираются вместе, без частичного изменения остатков.

С V43 резервирование хранится в container_owner и container_owner_history; таблица container_stock_reservation удалена, новые колонки не добавлены. При отмене поставки прежний собственник берётся из old_client_id единственного события RESERVE_RECEIVING этой заявки и КТК; если он NULL, остаётся текущий собственник. При отмене вывоза текущий собственник сохраняется. Предыдущую заявку того же типа выбирает previous_stock_order: последнее записанное событие до резервирования отменяемой заявки, с исключением CANCELLED-документов. Другой тип связи в регистре не меняется. Номер и дата создания документа не определяют порядок резервирования. Состав заявки должен точно совпадать с историей резервирования; при отсутствующей, повторной или неоднозначно упорядоченной истории отмена блокируется с STOCK_HISTORY_REQUIRED. Собственник не выводится из клиента заявки.

Для порядка используется существующее container_owner_history.created_at: при новой записи триггер блокирует КТК и выбирает максимум системного времени UTC и времени предыдущей записи плюс микросекунда. Поэтому порядок строго возрастает даже при переводе календаря назад; если старая запись датирована будущим, новые технические отметки следуют за ней. Старые даты не переписываются. Рабочие даты по-прежнему находятся в occurred_at: от них зависят хранение, складское движение и отображаемое время события. Проверки бизнес-последовательности сохранены. Перед удалением таблицы миграция проверяет уникальность старых времён и соответствие истории сохранённым резервам; неоднозначность останавливает миграцию.

История переходов сохраняется, обратный переход отмечается cancellation=true. Складские события отменённой заявки получают active=false. В карточке отменённой заявки используется неизменяемый снимок состава из order_cancellation: последующее переиспользование накладной не переписывает её историю. Накладные отменённой ЖД-поставки освобождаются для новой заявки. Отменённый вывоз/возврат освобождает распределение КТК, позволяя создать замену. Отметка «Возврат не нужен» не меняет складские переходы; при отмене выполненного автовывоза созданное по ней начисление снимается по правилам BACKEND_ALIGNMENT.md. У вывоза-замены возврат требуется по умолчанию.

Отмена рейса отменяет все его заявки одной транзакцией. Ошибка в любом документе откатывает весь пакет. При поштучной отмене рейс сохраняет оставшиеся заявки: он завершается, когда все активные заявки выполнены, и получает CANCELLED, когда отменены все. Проверки зависимых документов услуги и счетов описаны в [BACKEND_ALIGNMENT.md](BACKEND_ALIGNMENT.md).

## Собственник вывоза

Ручной выбор КТК в вывозе автоматически подставляет собственника из регистра. ЗПУ, класс опасности и порожность ручного вывоза задаются отдельно. Автоматически созданный вывоз комплексной услуги переносит доступные данные исходной поставки/накладной.

Только DRAFT актуализируется при смене собственника в регистре. При подтверждении собственник записывается в вывоз и фиксируется: последующие CHANGE_OWNER и LOAD_FINISH не переписывают его в CONFIRMED/COMPLETED. Текущий собственник регистра поэтому может отличаться от исторического собственника подтверждённого вывоза.

## Собственник возврата

Для возврата исходному клиенту:

- При DRAFT исходного вывоза сервер берёт индивидуального собственника из исходной ЖД-поставки/накладной, с резервным значением её default. Это позволяет оформить ранний возврат до появления КТК в регистре.
- При CONFIRMED/COMPLETED исходного вывоза берётся сохранённый собственник вывоза.
- Если собственника нельзя определить, создание отклоняется; клиент услуги не используется как скрытая подстановка.

При возврате другому клиенту нужен явный ownerClientId. Форма предварительно выбирает нового клиента возврата, но позволяет назначить любого собственника из справочника. Выбранное значение применяется к выбранным КТК новых возвратных поставок, не изменяя исходные документы.

В черновике возвратной поставки собственника можно изменить. При её подтверждении в регистр попадёт выбранное значение. Наличие возврата не означает автоматического прихода: исходный вывоз сначала должен быть выполнен, затем возврат проходит подтверждение и выполнение.

## Смена собственника

service_order — самостоятельная заявка с service=CHANGE_OWNER. Статусы: DRAFT и DONE. При создании и подтверждении обязателен хотя бы один КТК из регистра. Нельзя одновременно выбрать его в другую черновую заявку на смену собственника.

При выборе проверяется отличие текущего собственника от нового. Подтверждение блокирует КТК, перепроверяет наличие собственника и обновляет регистр, историю и черновые вывозы в одной транзакции. Складской статус КТК сохраняется. Подтверждённые вывозы сохраняют собственника своего подтверждения. Выполненная заявка на смену собственника недоступна для редактирования и повторного выполнения.

Выполнение повторно проверяет отличие текущего собственника от нового; совпадение отклоняется. Сравнения со снимком собственника на момент выбора нет. Для КТК на площадке смена собственника разделяет период хранения по правилам ниже; складское состояние сохраняется.

## Состав и редактирование

При ручном создании заявки по умолчанию одна строка КТК. В ручных черновиках авто-поставки/вывоза и ЖД-вывоза можно добавлять номерные КТК. В ЖД-вывозе добавление идёт в уже выбранный вагон.

Прямое добавление запрещено для ЖД-поставки по накладным, заявок комплексной услуги и связанных возвратов: их состав управляется источником. Подтверждённые и выполненные заявки также не допускают добавления. Метаданные и новые строки сохраняются совместно; ошибочный состав откатывает пакет.

В КП-ЖД собственник меняется в строке КТК или массовым выбором. Массовый выбор накладной/вагона включает свёрнутые строки. Это редактирование собственника поставки, а не выполнение CHANGE_OWNER в регистре. Подробности интерфейса — в [FRONTEND_STANDARD.md](FRONTEND_STANDARD.md).


## Тип события истории КТК (V49)

В физической container_owner_history с V51 14 полей: id, container_id, old_client_id, new_client_id, old_status, new_status, order_id, order_type, created_at, created_by, updated_at, updated_by, occurred_at, storage_period_id. V49 удалила operation_type, V51 — cancellation. Обычный container_owner_history_view возвращает оба признака по history_operation_type(order_type,old_status,new_status). cancellation=true только для CANCEL_ARRIVAL, CANCEL_DEPARTURE, CANCEL_RECEIVING_RESERVATION и CANCEL_SHIPPING_RESERVATION; для остальных допустимых событий false. V50 удаляет terminal_area_id и time_source полностью, без замены вычисляемыми колонками. В системе одна контейнерная площадка, её повторение в истории и отчёте не требуется. Даты occurred_at/created_at, собственники, отмены, связи и смысл событий сохраняются. Новых хранимых колонок и материализованных представлений нет.

Функция использует только вид заявки и два складских статуса. Собственники не участвуют в вычислении; cancellation является результатом вычисления и отдельно не задаётся. Допустимы 13 сочетаний, соответствующие девяти типам событий:

| order_type | old_status | new_status | Вычисляемый operation_type |
| --- | --- | --- | --- |
| RECEIVING_ORDER | NULL или DEPARTED | EXPECTED | RESERVE_RECEIVING |
| RECEIVING_ORDER | EXPECTED | ON_TERMINAL | ARRIVAL |
| RECEIVING_ORDER | EXPECTED | DEPARTED | CANCEL_RECEIVING_RESERVATION |
| RECEIVING_ORDER | ON_TERMINAL | DEPARTED | CANCEL_ARRIVAL |
| SHIPPING_ORDER | ON_TERMINAL | RESERVED_OUT | RESERVE_SHIPPING |
| SHIPPING_ORDER | RESERVED_OUT | DEPARTED | DEPARTURE |
| SHIPPING_ORDER | RESERVED_OUT | ON_TERMINAL | CANCEL_SHIPPING_RESERVATION |
| SHIPPING_ORDER | DEPARTED | ON_TERMINAL | CANCEL_DEPARTURE |
| SERVICE_ORDER | EXPECTED / ON_TERMINAL / RESERVED_OUT / DEPARTED | тот же статус | OWNER_CHANGE |

Для SERVICE_ORDER правило соответствует нынешнему MVP, где поддерживается только CHANGE_OWNER. Новые виды услуг или переходы требуют отдельного изменения контракта и миграции. Неизвестный тип заявки/статус или неподдерживаемое сочетание дают NULL; history_transition_known запрещает такую запись. До V51 history_cancellation_matches_transition запрещал противоречивый сохранённый флажок отмены; с V51 физического флажка и этого ограничения нет. LEGACY/UNKNOWN не подставляются автоматически. Перед удалением поля миграция сверяет каждую старую запись: вычисление должно в точности совпасть с сохранённым типом и признаком отмены. Любое расхождение останавливает V49 одной транзакцией; история не исправляется автоматически.

Backend записывает исходные реквизиты события, затем читает вычисленный тип из VIEW для обработки хранения. Признак отмены не передаётся в запись отдельным аргументом. Отдельная Java-формула удалена. Восстановление предыдущих заявок, проверки границ и источников, отчёт и API истории используют тот же VIEW. Защита связанного события сохраняет неизменность исходных статусов и вида заявки, поэтому его вычисляемый смысл также нельзя подменить. Технический порядок created_at и бизнес-время occurred_at не меняются.

Проверки V49: [history-operation-check.cjs](scripts/history-operation-check.cjs). capture на V48 и verify на V49 сравнивают все остальные бизнес-поля и последовательности, полную историю с вычисленным типом, исходные поставки и полный активный отчёт. api-capture/api-verify сравнивают побайтно историю каждого КТК с резервированиями и без них, отчёт API и полный CSV. Только эти читающие режимы разрешены для billing_next. matrix работает только на billing_history_operation_test: проверяет все 75 сочетаний трёх видов заявки и пяти значений каждого статуса (включая NULL), 13 допустимых и 62 недопустимых, а также неизвестные значения и противоречивый cancellation. Вставки проверяются с откатом.

## Статусы строк КТК

V37 добавляет status в receiving_order_container (автопоставка), waybill_container (ЖД-поставка) и shipping_order_container (вывоз). Допустимы только NULL — статус не установлен, UPLOADED — подтверждено, FINISHED — выполнено. Подтверждение рейса переводит строки его заявок в UPLOADED; выполнение заявки переводит её строки в FINISHED. В MVP это имитация задания внешней системе: интеграция ещё не подключена, отдельного выполнения одного КТК через интерфейс нет.

ContainerTaskRows проверяет исходный статус и однозначность строки по КТК. Только FINISHED может стать источником фактического приёма/вывоза и периода хранения. Статус строки, остатки, история, период, начисления и статус заявки меняются в одной транзакции; ошибка любой строки откатывает всю операцию. Повторное выполнение не создаёт повторных фактов.

При отмене подтверждённой или выполненной заявки status её строк сбрасывается в NULL. Отмена остаётся в статусе заявки и отдельной истории, CANCELED в перечисление строк не добавлен. При отмене ЖД-поставки сброс происходит до освобождения накладных; их повторное использование создаёт новый период с исходной строкой waybill_container и новым контекстом заявки. Ранее отменённый период и его история сохраняются.

## Периоды хранения КТК

Раздел /container-storage и GET /api/container-storage-periods показывают периоды хранения по собственникам. Реализация — [ContainerStorageService](backend/src/main/java/ru/billing/app/containerstock/ContainerStorageService.java), [отчёт](backend/src/main/java/ru/billing/app/containerstock/ContainerStorageController.java), схема границ — [V42](backend/src/main/resources/db/baseline/V42__storage_owner_periods.sql), текущие представления и поиск исходного приёма — [V52](backend/src/main/resources/db/baseline/V52__derive_storage_arrival_from_chain.sql), проверки границ — [V50](backend/src/main/resources/db/baseline/V50__remove_history_area_and_time_source.sql).

Один физический заезд может включать несколько записей container_storage_period. С V52 в таблице 7 полей: id, container_id, start_history_id, end_history_id, status, created_at, updated_at. start_history_id и end_history_id задают границы конкретного периода собственника. Физическая arrival_history_id удалена. HTTP API и CSV сохраняют прежний контракт; вычисленная arrival_history_id доступна в обычном container_storage_period_view. receiving_order_id, receiving_at, shipping_at, receiving_owner_id, receiving_client_id, is_empty и ссылки на строки КТК также вычисляются. Даты и собственник начала берутся из точных событий границ, клиент — из исходной поставки, порожность — из строки приёма. CLOSED означает завершение периода, не обязательно физический вывоз; OPEN — открыт, CANCELLED — физический приём аннулирован.

Исходный приём определяется по точной цепочке. Если start_history_id указывает на ARRIVAL, это исходное событие. Если на OWNER_CHANGE — предыдущий период находится по end_history_id=start_history_id текущего; обход продолжается до ARRIVAL. У всех периодов цепочки один физический КТК. Последняя поставка по дате не используется: повторные заезды и смены в один день остаются разными событиями. При отмене приёма аннулируются все периоды этого КТК с тем же вычисленным ARRIVAL. Отмена вывоза очищает только end_history_id и снова открывает последний период.

Обычный container_storage_period_origin выполняет рекурсивный обход набора периодов и возвращает id, receiving_order_id и вычисленную arrival_history_id, включая CANCELLED. UNION завершает обход даже при некорректном цикле; отложенные проверки записи запрещают такие графы. storage_arrival_history(id) обходит конкретную цепочку назад, отклоняя циклы, разрывы и переход на другой КТК; storage_receiving_order(id) возвращает заявку найденного события. Начало периода и его КТК неизменны после создания, чтобы удаление хранимого корня не разрешало перепривязку истории. Границы и связанные события, исходные документы и уникальность источников защищены существующими проверками.

V52 до удаления сверяет хранимые arrival_history_id с цепочками и проверяет все границы. После удаления сравнивает исходные события/поставки всех периодов и весь активный VIEW, включая кратность строк; при расхождении миграция откатывается одной транзакцией. Остальные поля, статусы, даты, события и последовательности сохраняются; старые смены собственника не разделяются задним числом. Новых таблиц, хранимых колонок и материализованных представлений нет.

VIEW находит автоприём по вычисленной паре (receiving_order_id, container_id), ЖД-приём — по той же паре через waybill → waybill_railway_carriage → waybill_container. Заявка вывоза определяется по точному событию DEPARTURE из end_history_id, строка вывоза — по паре (заявка вывоза, container_id). При OWNER_CHANGE строки вывоза нет. Всё рассчитывается одним SQL-запросом, без дополнительных HTTP-запросов для каждой записи. Собственник периода определяется new_client_id события начала; клиент поставки и собственник остаются разными ролями.

При новой смене собственника КТК в ON_TERMINAL или RESERVED_OUT старый период закрывается, новый открывается тем же моментом времени. Одно событие OWNER_CHANGE связано с end_history_id старого и start_history_id нового периода; его storage_period_id указывает на новый период. Предыдущий определяется по общей границе без отдельной колонки цепочки. API истории возвращает previousStoragePeriodId, интерфейс предлагает ссылки на оба периода. Раздельная уникальность ссылок истории и уникальный индекс одного OPEN на физический КТК сохраняются; площадка не дублируется в периоде.

Изменение собственника, истории и обеих записей хранения выполняется одной транзакцией под блокировкой КТК. Отложенные проверочные триггеры сверяют события, хронологию их occurred_at, площадку исходной заявки, собственников, исходные строки и соседние периоды после завершения всех записей. Новый период не создаётся в EXPECTED или DEPARTED: при ожидании первый период возникнет при фактическом приёме. Отсутствие однозначного OPEN у КТК на площадке блокирует смену. Новая смена не может быть раньше предыдущих операций КТК, выполнение вывоза и отмены фактов — раньше границ/последних событий периода. Повторное выполнение заявки на смену отклоняется без повторного разделения.

**Старые периоды и прежние события OWNER_CHANGE не пересчитываются и не разделяются задним числом.** V42 меняет ограничения и комментарии, не бизнес-записи. При первой новой смене старый открытый период закрывается, сохраняя прежние начало, собственника и источник; новый открывается с новым собственником. Для проверки прежнего собственника учитывается последняя записанная старая смена внутри такого периода. V44 перед удалением полей проверяет совпадение старых дат, владельцев, клиентов и площадок с источниками, а порожности — для отображаемых периодов; несовпадение останавливает миграцию без автоматической правки. Уже привязанные события границ защищены от изменения бизнес-реквизитов отдельным триггером. Дни старого периода остаются целиком при его исходном собственнике до дня новой границы.

| Действие | Изменение хранения |
| --- | --- |
| Подтверждение поставки | Периода нет |
| Выполнение поставки | Новый OPEN по событию ARRIVAL и точной FINISHED-строке |
| Резервирование/снятие резерва вывоза | Границы не меняются |
| Смена собственника на площадке | Закрывается прежний период, открывается следующий по одному OWNER_CHANGE |
| Выполнение вывоза | Закрывается последний OPEN, указывается точная строка вывоза |
| Отмена выполненного вывоза | Открывается последний период, ссылка на событие окончания очищается; исходное событие и отмена сохраняются |
| Отмена выполненной поставки | Вся цепочка этого заезда становится CANCELLED; границы смен собственника и история сохраняются |
| Повторный фактический заезд | Новая независимая цепочка по новому ARRIVAL |

Проверки зависимости заявок, рейсов, счетов и принадлежности текущего состояния сохраняются. Нельзя отменить вывоз после следующей поставки; также блокируется отмена вывоза после смены собственника вне площадки, чтобы не открыть хранение на неверного владельца. Отмены выполненной заявки CHANGE_OWNER нет. Подтверждённый вывоз сохраняет своего собственника даже при последующей смене на площадке; собственник периода может отличаться от собственника строки вывоза. Отмена поставки восстанавливает регистр по действующим правилам, аннулируя всю цепочку хранения, без удаления заявок смены собственника и их истории.

Дни не хранятся в БД. Используются календарные даты Europe/Moscow. Начальный день включается. При окончании DEPARTURE день вывоза также включается; при OWNER_CHANGE окончание расчёта — день перед сменой. День смены принадлежит новому собственнику; несколько смен за день дают промежуточным собственникам ноль дней, день получает последний. Приём и смена в один день дают прежнему собственнику ноль дней. Верхняя граница ограничена asOf, по умолчанию billing_today(); asOf не может быть позже рабочей даты. Более поздний приём не попадает в отчёт, отрицательные дни ограничены нулём. CANCELLED не имеет действующего количества дней. Дата расчёта не меняет текущий статус. Льготные дни, начисления и стоимость хранения пока не рассчитываются.

Отчёт, CSV и обычный container_storage_period_view показывают только OPEN/CLOSED; CANCELLED не выводится даже при API-фильтрах ALL/CANCELLED. При отмене выполненной поставки вся цепочка исчезает из вывода, но записи остаются в таблице и истории. При отмене вывоза очищается ссылка на событие окончания; дата, заявка и строка вывоза становятся NULL через VIEW. API сохраняет arrivalAt/departureAt, arrivalOperationType/departureOperationType и startOrderId/startOrderType/startOrderNumber, endOrderId/endOrderType/endOrderNumber. В UI основания начала/окончания являются ссылками на поставку, вывоз или смену собственника; CSV содержит типы и номера этих заявок. VIEW дополнительно предоставляет receiving_owner_change_order_id/number и shipping_owner_change_order_id/number. inStock означает открытость конкретного периода, не физический остаток после смены собственника. Грузоотправитель и клиент берутся из исходной поставки, грузополучатель и клиент вывоза — из фактического вывоза; собственник вывоза — из его строки КТК. Перевозчики авто — из рейсов.

V41 убрала cargo_name: груз читается из etsng_code через receiving_order_container_item либо waybill_railway_carriage → waybill_product. С V46 исходные строки КТК определяются самим VIEW. Несколько грузов объединяются через «; » без дублей, пустой состав не исключает период. API/CSV передают справочное значение с кодом, UI — наименование. Изменения справочника отражаются в прежних периодах. С V44 is_empty вычисляется как receiving_order_container.empty либо waybill_container.net_weight=0; состав подтверждённой/выполненной заявки не редактируется. При отмене поставки период полностью исключён из VIEW. Освобождённую накладную можно редактировать и использовать в новой поставке: новый период получает её текущий состав, отменённая цепочка остаётся скрытой.

V33 однократно восстановила фактические периоды из истории, V37 добавила ссылки на строки заданий, V38 удалила needs_review/review_reason/version периода, V39 — шесть служебных полей истории и endpoint /issues. V46 заменяет три ссылки периода вычислением через заявку и физический КТК; перед удалением сравнивает все значения старого и нового VIEW, включая кратность строк, и останавливается при расхождении. Для OPEN/CLOSED отложенные проверки требуют ровно одну выполненную строку источника и выполненную заявку. Изменения строк, накладных, связей вагонов и заявок блокируют физический КТК и проверяются в конце транзакции; потеря или неоднозначность источника отклоняется. CANCELLED не требует текущего источника, что позволяет повторно использовать освобождённую накладную. V47 удалила receiving_order_id; V48 ввела прямую связь с исходным ARRIVAL, а V52 заменила её вычислением по цепочке, сохранив поле VIEW. Проверки цепочек требуют достижения ARRIVAL, а удаление или замена идентификатора исходной заявки блокируются даже для отменённых периодов. Проверка существования поставки удерживает блокировку её ключа до завершения транзакции. Проверки границ и неизменности связанных бизнес-событий сохранены. Причина отмены хранится в order_cancellation. История хранит occurred_at, storage_period_id, прежнего/нового собственника и состояния; operation_type и cancellation вычисляются через container_owner_history_view по правилам V49/V51. Новые факты используют рабочую дату MVP и время ручного выполнения после блокировки; внешние события и частичное выполнение не подключены. Старые миграции не переписываются; ручного редактора дат и исправления неоднозначной истории нет.

Проверки: [storage-owner-check.cjs](scripts/storage-owner-check.cjs), по умолчанию billing_storage_owner_test и backend billing-next-storage-owner-test на 8202; регрессия V43 допускает STORAGE_TEST_DB=billing_stock_history_test на 8203. capture на V41 и migration на V42 сравнивают все бизнес-записи, последовательности и определения колонок. Основной сценарий проверяет авто/ЖД, старые периоды без пересчёта, день смены, повторные смены, отказы БД, откат пакета, параллельный повтор, отмены, CSV. Регрессии storage-period-check.cjs, container-task-check.cjs и order-cancellation-check.cjs также допускают эту изолированную БД. Изменяющие проверки на рабочей billing_next запрещены. Восстановление без таблицы резервов проверяет [stock-history-check.cjs](scripts/stock-history-check.cjs): миграция без изменения остальных данных/колонок, предыдущие неотменённые заявки, собственники, перевод календаря назад, старые будущие отметки, нехватка/дубли истории, откат пакета и параллельная отмена.

V53 добавляет только статистику планировщика по вычисляемому типу события и обновляет её через ANALYZE. Она помогает оценить размер рекурсивного результата; хранимые бизнес-поля не добавляются.

### Представление и историческая проверка скорости

`SELECT * FROM container_storage_period_view ORDER BY receiving_at DESC, id LIMIT 20` выводит действующие периоды и документы. Исходная поставка определяется через рекурсивный container_storage_period_origin в том же SQL-запросе. Дни считаются на asOf, по умолчанию billing_today(), по правилам Europe/Moscow; сам VIEW возвращает факты без привязки к системной дате.

[storage-arrival-check.cjs](scripts/storage-arrival-check.cjs) сравнивает V47/V48: режим capture сохраняет все бизнес-строки с нормализацией двух переименований, последовательности, точные события исходного приёма всех периодов и полный активный отчёт; verify проверяет совпадение и наличие ровно восьми колонок. api-capture/api-verify сравнивают SHA-256 первой/глубокой страницы API, фильтра CANCELLED и полного CSV. Рабочая billing_next допускается только в этих читающих режимах. На billing_storage_arrival_test режим integrity проверяет неизменность arrival_history_id, ошибочные ссылки при вставке, циклы, разрывы, удаление корня и ключей исходной заявки, включая CANCELLED; изменения откатываются.

Порядок изменяющих регрессий на billing_storage_arrival_test, backend billing-next-storage-arrival-test на 8207: storage-owner-check.cjs → storage-arrival-check.cjs integrity → stock-history-check.cjs → storage-source-integrity-check.cjs. Для всех задать STORAGE_TEST_DB=billing_storage_arrival_test. Проверяются авто/ЖД, прежние неразделённые периоды, несколько смен за день, резервирование вывоза, отмены, повторные заезды, календарь назад, параллельные повторы, откат пакета и переиспользование накладной. Сценарии оставляют фикстуры; для повторного полного прогона нужна свежая изолированная копия. [storage-arrival-migration-check.cjs](scripts/storage-arrival-migration-check.cjs) требует отдельную восстановленную V47 billing_storage_arrival_migration_test: искусственно неверный исходный приём и изменение значений отчёта приводят к полному откату V48. Проверка выпуска выполняется на billing_storage_arrival_release_test, backend на 8217. Старые сценарии переходов V43–V47 сохраняют свои ограничения версии.

# ТЗ для BE основной системы. Отчёт «Хранение КТК»

В ALIS реализовать отчёт о фактическом пребывании КТК на терминале. Основная строка — один визит от приёмки до вывоза. При раскрытии видны периоды собственников. Повторная поставка того же КТК образует отдельный визит. Отчёт рассчитывает календарные дни хранения. Стоимость и льготные дни в расчёт не входят.

[Проект API отчёта для ALIS с примерами JSON](alis-openapi.yaml) · [ТЗ для FE](frontend.md)

## Что уже предоставляет ALIS

Исходный контракт — [снимок OpenAPI основной системы](../../openapi%20%281%29.yaml). Для реализации сверены модели и обработчики `backend-stage` на коммите `08343f2`. Операции ниже опубликованы в снимке.

| Существующая операция | Что можно использовать для хранения |
| --- | --- |
| `POST /containermovement/page` | `ContainerMovementDto` содержит `eventDateTime`, `eventCode`, `containerCode`, ссылку на заявку и `etsngCodes`. Это источник для сверки физических границ и образец постраничного ответа. |
| `POST /container/{id}/owner-history/page` | `ContainerOwnerHistoryDto` содержит UUID записи, `createdAt`, `orderType`, `orderId`, `orderNumber`, `newClient` и складские статусы. История отбирает события по правилам карточки. У DTO отсутствуют бизнес-время передачи, UUID визита и периода. |
| `POST /container-owner/page` | `ContainerOwnerDto` описывает текущего собственника, состояние и связанные заявки. При повторном обороте эти ссылки меняются. |

В снимке отсутствует операция, возвращающая визиты с цепочкой владения и днями хранения. Существующие отчёты движения и остатков сохраняют свой контракт. Действующий `bil-mvp` демонстрирует расчёт и структуру строк через `GET /api/container-periods/visits`. ## Новые операции ALIS

Пути заданы относительно базового URL API. Обе операции предназначены для чтения. Формат тела запроса и ответа — `application/json`. Предусмотреть в модели прав новый ресурс `ContainerStorage` с действием `READ`. Проверять доступ на сервере при каждом вызове, применять одинаковую область видимости данных к списку номеров, визитам и счётчикам.

| Метод и путь | Тело | Успешный ответ |
| --- | --- | --- |
| `POST /container-storage/page` | `{pageInfo: {page, size}, filter: {...}}` в форме `FilterWithPaging`. Оба объекта обязательны. | `application/json`, `{content: [Visit], page: {number, size, totalElements, totalPages}}` по образцу `PagedModel`. Один элемент содержит весь массив `periods`. |
| `POST /container-storage/containers/all` | `{}` | `application/json`, массив `{id, code}`. Каждый КТК с хотя бы одним действительным визитом к рабочей дате возвращается один раз, в том числе после вывоза. Сортировка по `code`, затем по UUID. |

Операция `/container-storage/page` принимает в `filter` поля `query`, `month`, `storedFrom`, `storedTo`, `asOf` и `periodId`. При переходе из истории `periodId` выбирает целый визит. Точная схема, обязательные поля, примеры непустого и пустого результатов приведены в [проекте OpenAPI ALIS](alis-openapi.yaml).

Расширить существующий `ContainerOwnerHistoryDto` необязательным `storagePeriodId` (UUID). У фактической приёмки и действующей передачи это ID открытого ими периода, у фактического вывоза — ID закрытого им последнего периода. Заполнять поле только при однозначной связи с видимым периодом и доступе к отчёту. У резервов, отменённых и несопоставленных событий поле опускать. `ContainerOwnerHistoryDto.id` сохраняет значение UUID записи истории. Для граничных заявок возвращать UUID, тип и числовой бизнес-номер. Необязательные реквизиты без значения в JSON опускаются.

## Как сформировать визит

1. Один раз на запрос взять для расчёта переданный `asOf` либо рабочую дату сервера в `Europe/Moscow`. При отсутствии отдельного рабочего календаря использовать текущую московскую дату. `asOf` позже рабочей даты отклонить.
2. Проводить фактическую приёмку и вывоз в транзакции обработки результата конкретного КТК. На `UNLOAD_FINISH` открыть визит и первый период, на `LOAD_FINISH` закрыть визит и последний период. Обновить регистр и добавить событие истории до завершения заявки целиком. Для КП-ЖД время приёмки берётся из выгрузки КТК. [Построчное проведение, повторная доставка и критерии приёмки](database.md#фактическая-приёмка-и-вывоз-по-каждому-ктк)
3. Зафиксировать устойчивые UUID визита и периода, ссылку на КТК, начальное событие и заявку. Смена собственника в пределах этого визита завершает прежний период и открывает следующий. Фактический вывоз закрывает последний период и визит. Сохранять связь в транзакции обработки результата. Повтор обработки того же события сохраняет первоначальные границы и идентификаторы.
4. Источник передачи — `ServiceOrder` и её состав, точки записи — `ServiceOrderService.accept` и `ContainerOwnerService.changeOwners`. `ServiceOrder.transferredAt` в ALIS содержит календарную дату передачи. `completionAt` фиксирует завершение заявки. Для новых операций сохранять точный момент действия отдельно от технического `createdAt`. Бизнес-дата передачи должна совпадать с `transferredAt` по Москве. В день приёмки передача следует за приёмкой. При оформлении задним числом отнести передачу к визиту, в котором она действует. Периоды упорядочивать по моменту действия, при равенстве — по времени записи и UUID события.
5. На дату `asOf` отдавать только начавшиеся периоды. Будущая граница скрыта до её даты действия, предыдущий период до этого открыт. Черновик и отменённая передача не открывают период. В проверенном `backend-stage` у `ServiceOrderStatus` есть `DRAFT` и `DONE`. Если в контуре включено планирование, ожидающая подтверждённая передача влияет на отчёт с даты действия. `SCHEDULED` и `CANCELLED` — обозначения MVP. Расчёт не требует публичного поля с такими значениями от действующей ALIS.
6. При отмене вывоза открыть тот же визит и убрать реквизиты вывоза. При отмене фактической приёмки исключить весь визит и его периоды. Для отмен использовать источник операций `ContainerStatusService.cancelReceivingOrder / cancelShippingOrder`. Отчёт на прошлую дату отражает действующие исправления и отмены. Для открытого периода вернуть `status=OPEN` и опустить конечную границу, для закрытого — `CLOSED` и конечное событие.

В проверенной модели ALIS движения, история собственников и регистр имеют разные ключи. Для исторических данных связать приёмку, передачи и вывоз по физическому КТК, конкретным заявкам и подтверждённым событиям. При повторном заполнении сохранять присвоенные UUID и число визитов и периодов. Неоднозначные связи и случаи без надёжного времени вынести на сверку до приёмки исторической выборки. Целевая схема ALIS, включая новые таблицы, поля заявок и порядок переноса, определена в [блоке 1 ТЗ по смене собственника и хранению КТК](database.md).

## Дни хранения

Единица расчёта — календарная дата в `Europe/Moscow`. До вычитания дат перевести каждый момент в московское время. Включить первый и последний день. Начало визита — приёмка, начало периода — приёмка или передача. Конец — ближайшая видимая конечная граница, а у открытого интервала — `asOf`.

Для каждого визита и каждого периода рассчитать `storageDays` как разность календарных дат плюс один. При заданном фильтре хранения дополнительно рассчитать `storageDaysInPeriod` для пересечения с фильтром. Взять более позднюю из двух начальных дат и более раннюю из двух конечных дат. Если начало оказалось позже конца, результат равен нулю. При открытой границе фильтра применить только указанную границу. Без фильтра хранения свойство `storageDaysInPeriod` опускается.

В день передачи прежнему и новому собственникам засчитывается по одному дню. Несколько смен за одни сутки дают каждому промежуточному периоду один день. Итог визита считать отдельно по приёмке и вывозу. В нём каждую дату учитывать один раз.

## Отбор и порядок

| Условие | Результат |
| --- | --- |
| `query` | Поиск по подстроке `container.code` без учёта регистра. Убрать краевые пробелы. Пустая строка снимает отбор. |
| `month` или `storedFrom` / `storedTo` | `month` — полный месяц `YYYY-MM`. Границы диапазона — даты `YYYY-MM-DD` включительно, допускается одна граница. Использовать один из двух способов задания периода. |
| Пересечение | Включить визиты с хотя бы одним днём в заданном диапазоне к `asOf`. Внутри вернуть весь видимый визит, включая периоды с нулевым пересечением. Только будущий диапазон даёт пустой результат. |
| `periodId` | UUID видимого периода. Отобрать его визит с полной цепочкой и применить остальные фильтры. Неизвестный, ещё не начавшийся или недоступный период даёт пустой результат. |
| `pageInfo` | Отсчёт страниц от 0, размер от 1 до 100. FE явно передаёт 20. `page.totalElements` считает визиты, `totalPages` — число страниц с округлением вверх. За последней страницей вернуть пустой `content` и действительные счётчики. |
| Сортировка | Визиты по московской дате приёмки по убыванию, затем по UUID визита по возрастанию. Периоды внутри визита идут от первого к последнему. Считать визиты и читать детали страницы на одном согласованном снимке. |

Возвращать HTTP 400 при неверном формате даты, месяца или UUID, сочетании месяца и диапазона, обратном диапазоне, `asOf` в будущем либо недопустимой пагинации. Использовать штатную ошибку ALIS (`ApiErrorDto.errorMessage`, `errorCode` при наличии). Без права чтения вернуть HTTP 403. При корректном запросе без совпадений вернуть HTTP 200. Для страницы визитов ответ содержит пустой `content` и метаданные `page`. Для списка номеров ответ — `[]`.

## Реквизиты и груз

Собственник периода — клиент, назначенный начальным событием. Для `ownerName` разрешать отображаемое имя клиента по UUID. Блок поставки у всех периодов одного визита берётся из его исходной заявки. Блок вывоза заполняется только у периода, который заканчивает `SHIPPING_ORDER`. Номера, клиенты и грузы поставки и вывоза могут различаться.

| Выходные поля периода | Источники в основной системе |
| --- | --- |
| `receivingClientName`, `receivingOwnerName` | Клиент поставки и собственник автостроки `ReceivingOrderContainer.ownerContainer` или ЖД-строки `WaybillContainer.ownerContainer` в модели BE. При отсутствии собственника строки использовать `ReceivingOrder.defaultContainerOwner`. В опубликованном `WaybillContainerDto.owner` передаётся текст накладной. Ключ клиента брать из модели строки. |
| `shippingClientName`, `shippingOwnerName` | Клиент вывоза и сохранённый `ShippingOrderContainer.containerOwner` строки конкретного КТК. |
| `arrivalTransport`, `departureTransport` | Вид транспорта соответствующей заявки. В контракте отчёта значения `VEHICLE` и `RAILWAY`. |
| `arrivalParty`, `departureParty` | Экспедитор из `Route.clientRelatedEntity` соответствующей заявки. Вторая сторона — `ReceivingOrder.shipper` у поставки, `ShippingOrder.consignee` у вывоза. |
| `arrivalCargo` | Для авто взять `ReceivingOrderContainerItem.etsngCode` грузовых позиций строки КТК. Для ЖД найти КТК в вагоне накладной исходной поставки и взять все `WaybillProduct.etsngCode` этой накладной. |
| `departureCargo` | Для авто и ЖД взять `ShippingOrderContainerItem.etsngCode` грузовых позиций этого КТК в фактическом вывозе. |

`EtsngCodeDto` в ALIS содержит `code` и `name`. Сохранить ведущие нули кода. При наличии названия выводить «код — название», для кода с уже включённой подписью сохранить одну подпись, при отсутствии названия — код. Дедуплицировать по коду, отсортировать по коду и собрать в одну ячейку через `; `. Например, `011005 — Пшеница; 161128 — Лесоматериалы`. Отсутствие позиций оставляет поле груза пустым и сохраняет строку периода. У нескольких КТК одной ЖД-накладной один и тот же набор грузов этой накладной. Массу в подпись не включать.

`arrivalParty` и `departureParty` — готовые пары «экспедитор / контрагент». При пустой стороне поставить «—» на её месте, при отсутствии обеих опустить поле. Имена клиента и собственника заявки возвращать отдельными полями.

## Критерии приёмки

| Исходные данные и запрос | Ожидаемый результат |
| --- | --- |
| Приёмка 10 ноября, передача 12 ноября, вывоз 15 ноября. `asOf` не раньше 15 ноября. | У визита 6 дней, у первого периода 3, у второго 4. Для фильтра на 12 ноября — по 1 дню у визита и у обоих периодов. Для фильтра на 15 ноября — 1, 0 и 1 соответственно, обе строки собственников сохранены. |
| Та же цепочка с `asOf` 11 ноября. | Виден один открытый период, в визите 2 дня. Сведения о последующих границах отсутствуют. |
| Приёмка и вывоз в один московский день. Другая проверка — приёмка в 21:30 UTC накануне и вывоз в 00:30 UTC следующей даты. | В обоих случаях 1 день. |
| Контрольный ноябрьский визит `TKRU9000460` в согласованном наборе данных. | `storageDaysInPeriod` равен 30 у визита, 1 у прежнего и 30 у нового собственника. |
| Повторный заезд одного КТК, `pageInfo.size=1`, поиск по фрагменту номера в нижнем регистре. | Два отдельных визита на двух страницах, каждый со своей поставкой. Для промежуточного `filter.periodId` в таблице возвращается вся видимая цепочка соответствующего визита. |
| В ЖД-накладной одного КТК два груза, «211009 — Уголь каменный» и «161128 — Лесоматериалы». В вывозе указан иной груз. | `arrivalCargo` равно `161128 — Лесоматериалы; 211009 — Уголь каменный`. `departureCargo` содержит значение вывоза. Число визитов и периодов неизменно при добавлении позиции груза. |
| Ожидающая передача с будущей датой. Отмена вывоза. Отмена приёмки. | До даты передачи её период скрыт. После отмены вывоза последний период открыт. После отмены приёмки визит отсутствует в отчёте. |
| Запросить список номеров. В данных есть КТК с двумя визитами, КТК с завершённым визитом и КТК только с отменённой приёмкой. | Первые два номера представлены по одному разу в массиве `{id, code}`. КТК только с отменённой приёмкой отсутствует. |
| Один КТК фактически принят, остальные строки заявки ещё ожидают приёмки. Повторно обработать тот же результат TOS. | Визит и его первый период видны до завершения заявки и сохраняют UUID, время начала и количество строк после повтора. |
| Открыть из истории событие со `storagePeriodId` и передать его значение в `filter.periodId` запроса страницы. | Страница содержит все видимые периоды одного визита. UUID события истории и UUID периода разрешаются независимо. |
| Отправить конфликтующие фильтры, затем корректный запрос без права чтения. | В первом случае пользователь с правом получает 400. Во втором обе операции возвращают 403. Корректный фильтр без совпадений у пользователя с правом возвращает 200. |

Даты, номера документов и участники в примерах условны. В ноябрьском примере передача в `2026-10-31T21:00:00Z` приходится на 1 ноября по Москве. Это даёт **30 / 1 / 30** в границах месяца, при полной длительности визита 31 день. Приёмочные сценарии с созданием или изменением данных выполнять в отдельной тестовой БД.

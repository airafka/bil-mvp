# ТЗ на backend отчёта хранения КТК

Сервер предоставляет отчёт о фактическом пребывании каждого КТК на терминале и распределении дней хранения между собственниками. Единица основной выдачи — визит от приёмки КТК до его вывоза. Единица детализации и выгрузки — период владения внутри визита. Повторная поставка того же КТК создаёт самостоятельный визит.

[Контракт HTTP с примерами запросов и ответов](openapi.yaml) · [Требования к экрану отчёта](frontend.md)

## Операции

Основной префикс — `/api/container-periods`. Сохранить действующий эквивалентный префикс `/api/container-storage-periods`. Все операции выполняются методом GET и доступны для чтения без создания или обновления складских данных.

| Операция | Результат |
| --- | --- |
| `/visits` | Страница визитов с полными цепочками периодов на дату расчёта. Это источник данных экрана. |
| `/containers` | Массив вариантов для фильтра по номеру КТК. |
| `/export` | Файл CSV со всеми подходящими периодами владения за все страницы. |
| GET на самом префиксе | Совместимая с прежними клиентами плоская страница периодов владения. |

Вернуть идентификаторы КТК, визита, периодов и граничных заявок как UUID. Для ссылки на документ вернуть UUID и тип заявки, для отображения — её числовой номер. Одноимённые номера документов разных типов допустимы. Моменты событий передаются с часовым смещением. Неопределённые свойства объектов в JSON опускаются.

## Построение визита на дату расчёта

1. Использовать переданный `asOf` либо рабочую дату приложения `billing_today()`. Более поздний `asOf` отклонять с HTTP 400. Один запрос рассчитывается на одну рабочую дату.
2. Включать визит по фактическому событию приёмки конкретного КТК. Резервирование контейнера и подтверждение поставки сами по себе его не открывают. При частичном исполнении поставки принятый КТК попадает в отчёт независимо от готовности остальных строк. Идентификатор прибытия и исходную поставку определять по `container_visit.receiving_container_owner_history_id`.
3. Первое назначение собственника открывается событием поставки. Следующая действующая передача этого визита закрывает предыдущий период и открывает собственный. Бизнес-время границы — `container_owner_history.occurred_at`. Так учитывается и передача, оформленная задним числом. При совпадении бизнес-времени порядок задают `created_at`, затем UUID события, по возрастанию.
4. Черновик смены не создаёт период. Подтверждённая будущая передача (`SCHEDULED`) уже имеет запись периода. Записи с датой действия позже `asOf` пропускаются. Отчёт на более раннюю дату возвращает открытый предыдущий период и скрывает будущую конечную границу. После наступления даты учитывать действующую передачу по дате события. Отменённая смена (`CANCELLED`) исключается из цепочки.
5. Закрывать последний период фактическим вывозом этого визита. Приёмка, передача и вывоз дают граничные типы `RECEIVING_ORDER`, `SERVICE_ORDER` и `SHIPPING_ORDER`. В `periods[].status` возвращать `OPEN` либо `CLOSED` на дату расчёта. Для открытой границы опускать дату и реквизиты конечной заявки. Граница самого визита может быть только вывозом.
6. Отмена приёмки исключает весь визит со всеми его периодами. Отмена вывоза вновь открывает тот же визит и удаляет реквизиты вывоза из выдачи. Для расчёта на прошлую дату учитывается действующая история с внесёнными отменами и задними датами.

В MVP источниками являются `container_visit`, `container_period` и события `container_owner_history`. Записи истории связываются с документами по типу и идентификатору. Текущие остатки могут уже относиться к более поздней поставке. Реквизиты предыдущего визита должны по-прежнему разрешаться по событиям именно этого визита.

## Дни хранения

Единица расчёта — календарная дата в `Europe/Moscow`. До вычитания дат перевести каждый момент в московское время. Включить первый и последний день. Начало визита — приёмка, начало периода — приёмка или передача. Конец — ближайшая видимая конечная граница, а у открытого интервала — `asOf`.

Для каждого визита и каждого периода рассчитать `storageDays` как разность календарных дат плюс один. При заданном фильтре хранения дополнительно рассчитать `storageDaysInPeriod` для пересечения с фильтром. Взять более позднюю из двух начальных дат и более раннюю из двух конечных дат. Если начало оказалось позже конца, результат равен нулю. При открытой границе фильтра применить только указанную границу. Без фильтра хранения свойство `storageDaysInPeriod` опускается.

В день передачи прежнему и новому собственникам засчитывается по одному дню. Несколько смен за одни сутки дают каждому промежуточному периоду один день. Итог визита считать отдельно по приёмке и вывозу. В нём каждую дату учитывать один раз.

## Выборка и стабильный порядок

| Условие | Требование |
| --- | --- |
| `query` | Отбирать по вхождению подстроки в номер КТК без учёта регистра. Крайние пробелы игнорируются. Пустое значение снимает условие. |
| `month` | Календарный месяц `YYYY-MM` целиком. |
| `storedFrom`, `storedTo` | Включительный диапазон. Допускается одна граница. Месяц и границы диапазона взаимоисключающие. |
| Пересечение с визитом | В отбор попадают визиты с хотя бы одним днём хранения в диапазоне по `asOf`. Если выбран только будущий диапазон, выдача пустая. Внутри отобранного визита сохранить полную цепочку на `asOf`, включая периоды с нулём дней в диапазоне. |
| `periodId` в `/visits` | Найти целый визит по действующему периоду, уже начавшемуся к `asOf`. Остальные фильтры сохраняют действие. При неизвестном или невидимом периоде вернуть пустую страницу. |
| `page`, `size` | По умолчанию страница 0, размер 20. Отрицательную страницу привести к 0, размер ограничить диапазоном 1–100. `totalElements` считает визиты, `totalPages` — округлённое вверх частное. За пределами выборки вернуть пустой `items` и действительные счётчики. |
| Порядок и целостность | Отбирать визиты по московской дате приёмки по убыванию, затем по UUID визита по возрастанию. В пределах страницы загружать все видимые периоды каждого визита, упорядоченные по `occurred_at`, `created_at`, UUID события. Идентификаторы страницы, счётчик и детали читать на одном согласованном снимке. |
| Список номеров | `/containers` возвращает каждый физический КТК один раз как `{id, name}`, где `name` — номер. Достаточен хотя бы один неотменённый визит с датой приёмки не позднее `billing_today()`, в том числе завершённый. Сортировка по номеру, затем по UUID. Список не зависит от месяца, страницы и `asOf` отчёта. |

При `month` вместе с любой границей диапазона, обратном диапазоне хранения либо `asOf` позже рабочей даты вернуть HTTP 400 и бизнес-код `INVALID_STORAGE_FILTER`. При неверном формате параметра вернуть HTTP 400. Отсутствие подходящих строк — обычный успешный результат.

## Источники реквизитов и груза

В каждом элементе `periods` возвращать собственника периода из `new_client_id` точного начального события. Блок поставки для всех периодов визита относится к одной исходной поставке. Блок вывоза заполнять только в периоде, на конечной границе которого есть действующая заявка `SHIPPING_ORDER`. При переносе собственности экспорт продолжает показывать поставку визита, а для конца периода указывает заявку на смену.

| Реквизит | Для поставки | Для вывоза |
| --- | --- | --- |
| Клиент | `receiving_order.client_id` | `shipping_order.client_id` |
| Собственник КТК в заявке | Собственник строки этого КТК в автопоставке или в ЖД-накладной. При отсутствии — `receiving_order.default_container_owner_id`. | Сохранённый собственник строки этого КТК в заявке на вывоз. |
| Транспорт | `receiving_order.transport_type` | `shipping_order.transport_type` |
| Экспедитор и контрагент | Экспедитор связанного рейса и грузоотправитель поставки (`receiving_order.shipper_id`). | Экспедитор связанного рейса и грузополучатель вывоза (`shipping_order.consignee_id`). |
| Груз | Авто — позиции `receiving_order_container_item` этой строки КТК. ЖД — все `waybill_product` той накладной исходной поставки, в которой найден КТК через вагон. | Авто и ЖД — позиции `shipping_order_container_item` именно этого КТК в заявке на вывоз. |

Экспедитор определяется по `route.client_related_entity_id` соответствующей заявки. В JSON клиент и собственник заявки — отдельные поля. Для `arrivalParty`, `departureParty` и для пар в CSV выводить два имени через « / ». Если заполнена только одна сторона, поставить «—» на месте второй. При отсутствии обеих сторон значение отсутствует. Транспорт в JSON передавать как `VEHICLE` либо `RAILWAY`.

Для `arrivalCargo` и `departureCargo` брать полное справочное значение `etsng_code.code`, включая подпись, если она входит в значение. Удалить повторы, отсортировать значения по возрастанию и объединить разделителем `; `. При отсутствии позиций опустить поле груза и сохранить строку отчёта. Вес и признак порожнего КТК в формировании подписи не участвуют. Состав вывоза определяется независимо от поставки.

При оформлении ЖД-накладной допускаются несколько грузов при одном КТК и указанной массе каждой позиции. Груз относится ко всей накладной. Для нескольких КТК в одной накладной с одним грузом значение у всех этих КТК одинаково. Проверка допустимого состава выполняется при сохранении накладной. В отчёте несколько позиций формируют одну строку груза. [Проверки состава накладной](../../backend/src/main/java/ru/billing/app/waybill/WaybillValidator.java)

## Плоская выдача и CSV

GET на префиксе поддерживает `query`, `status`, `clientId`, `periodId`, `arrivalFrom`, `arrivalTo`, `asOf`, `page` и `size`. `clientId` относится к клиенту исходной поставки, `periodId` выбирает ровно указанный период. `arrivalFrom` и `arrivalTo` задают включительные **UTC-даты начала периода**, включая начало по смене собственника. Порядок — по моменту начала по убыванию, затем по UUID периода по возрастанию. Счётчики отражают число периодов. `status=ACTIVE` по умолчанию и `ALL` включают открытые и закрытые периоды. `OPEN` и `CLOSED` отбирают состояние на `asOf`. `CANCELLED` даёт пустую выборку. Неизвестный статус и обратный диапазон дат начала дают HTTP 400 с `INVALID_STORAGE_FILTER`.

Выгрузка `/export` применяет те же фильтры периодов и сортировку. Параметры `month`, `storedFrom`, `storedTo` дополнительно отбирают целые визиты. Для выгрузки всей цепочки по ссылке на период использовать `visitPeriodId`. Параметр `periodId` в этом методе сохраняет смысл точного периода. Все указанные условия применяются совместно. В файл записывать по одной строке на период, без суммарных строк визитов. При отсутствии совпадений файл содержит заголовок.

Имя файла — `container-storage.csv`, тип — `text/csv` с UTF-8 и начальным BOM. Разделитель полей — точка с запятой, строк — CRLF. Каждая ячейка заключена в двойные кавычки, внутренние кавычки удваиваются. Для отсутствующего значения записать пустую ячейку. Если первый символ после пропуска начальных пробельных символов — `=`, `+`, `-` или `@`, перед всей ячейкой добавить апостроф. Бизнес-номера заявок сохранить как текстовое представление числа. Даты выводить в UTC с точностью до минуты в формате `dd.MM.yyyy HH:mm UTC`, транспорт — «Авто» или «ЖД», границы — «Поставка», «Смена собственника», «Вывоз».

| Позиции за всё время | Заголовки в точном порядке |
| --- | --- |
| 1–3 | Номер КТК · Собственник КТК · Дней хранения |
| 4–6 | Начало периода · Событие · Заявка |
| 7–9 | Конец периода · Событие · Заявка |
| 10–13 | Клиент/Собственник поставки · Транспорт поставки · Экспедитор/грузоотправитель поставки · Груз поставки |
| 14–17 | Клиент/Собственник вывоза · Транспорт вывоза · Экспедитор/грузополучатель вывоза · Груз вывоза |

При выбранном периоде хранения вставить колонку «Дней хранения в периоде» на четвёртую позицию. Остальные колонки сдвигаются на одну позицию. Это даёт 17 колонок за всё время и 18 при заданном месяце или диапазоне.

## Критерии приёмки

| Исходные данные и запрос | Ожидаемый результат |
| --- | --- |
| Приёмка 10 ноября, передача 12 ноября, вывоз 15 ноября. `asOf` не раньше 15 ноября. | У визита 6 дней, у первого периода 3, у второго 4. Для фильтра на 12 ноября — по 1 дню у визита и у обоих периодов. Для фильтра на 15 ноября — 1, 0 и 1 соответственно, обе строки собственников сохранены. |
| Та же цепочка с `asOf` 11 ноября. | Виден один открытый период, в визите 2 дня. Сведения о последующих границах отсутствуют. |
| Приёмка и вывоз в один московский день. Другая проверка — приёмка в 21:30 UTC накануне и вывоз в 00:30 UTC следующей даты. | В обоих случаях 1 день. |
| Контрольный ноябрьский визит `TKRU9000460` в согласованном наборе данных. | `storageDaysInPeriod` равен 30 у визита, 1 у прежнего и 30 у нового собственника. |
| Повторный заезд одного КТК, `size=1`, поиск по фрагменту номера в нижнем регистре. | Два отдельных визита на двух страницах, каждый со своей поставкой. Для промежуточного `periodId` в `/visits` возвращается вся видимая цепочка соответствующего визита. |
| В ЖД-накладной одного КТК два груза, «211009 — Уголь каменный» и «161128 — Лесоматериалы». В вывозе указан иной груз. | `arrivalCargo` равно `161128 — Лесоматериалы; 211009 — Уголь каменный`. `departureCargo` содержит значение вывоза. Число визитов и периодов неизменно при добавлении позиции груза. |
| Ожидающая передача с будущей датой. Отмена вывоза. Отмена приёмки. | До даты передачи её период скрыт. После отмены вывоза последний период открыт. После отмены приёмки визит отсутствует в отчёте и CSV. |
| Две выгрузки одной выбранной цепочки, за всё время и за месяц. | По строке на каждый видимый период, 17 и 18 колонок соответственно. Проверить совпадение дней, границ, источников груза и ролей с API. В ячейке с несколькими грузами разделитель внутри значения не разбивает строку на дополнительные колонки. |

Приёмочные сценарии, создающие документы, выполнять на отдельной тестовой базе.

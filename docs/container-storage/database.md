# Блок 1. Доработка БД для смены собственника и хранения КТК и вагонов

**Цель.** Учитывать хранение каждого КТК и каждого вагона, включая порожние вагоны. Для вагона считать дни от фактического прибытия до выезда с КП-ЖД и показывать периоды его собственников. По физическому КТК должна восстанавливаться цепочка «фактическая приёмка → смены собственника → фактический вывоз». Одна поставка открывает отдельный визит для каждого принятого КТК. Каждая подтверждённая передача внутри визита открывает период нового собственника. Текущий остаток, история на выбранную дату и расчёт дней опираются на одни и те же события.

**Исходная схема** — PostgreSQL основной системы ALIS по снимку `backend-stage`. **Целевая модель для КТК** сверена с `bil-mvp` V87. Для вагонов целевая схема расширяет существующий в ALIS учёт остатка и смены собственника. [Хранение вагонов на КП-ЖД](#19-хранение-вагонов-на-кп-жд). [Исходники ALIS, архив на 08343f2](https://github.com/airafka/dev_back/blob/08343f22af5413321dd3136f1336c4f2f37b8c8a/backend-stage%20%281%29.zip) · [Снимок OpenAPI ALIS](../../openapi%20%281%29.yaml) · [Сопоставление моделей](../../BACKEND_ALIGNMENT.md)

Итого по КТК и вагонам — **4 новые таблицы и 14 новых колонок в 5 существующих таблицах**. Вагонная часть добавляет две таблицы и одну колонку в существующую историю. Порядок полей регистра меняется отдельно. Ниже `NULL` означает допустимое отсутствие значения, `NOT NULL` — обязательность на уровне БД. Ссылки ведут на `id` указанной таблицы, если не назван составной ключ.

## 1.2. Новая таблица `container_visit` — физический визит

| Поле | Тип | Обязательность и связь | Как заполнять |
| --- | --- | --- | --- |
| `id` | `uuid` | PRIMARY KEY | Присвоить при фактической приёмке. Использовать тот же UUID при повторе сообщения и при отмене вывоза. |
| `container_id` | `uuid` | NOT NULL, FK → `container.id` | Физический КТК из выполненной строки поставки или ЖД-накладной. |
| `receiving_container_owner_history_id` | `uuid` | NOT NULL, UNIQUE, FK → `container_owner_history.id` | Событие фактической приёмки (`ARRIVAL`) этого КТК. |
| `shipping_container_owner_history_id` | `uuid` | NULL, UNIQUE, FK → `container_owner_history.id` | Событие фактического вывоза (`DEPARTURE`). У открытого визита — `NULL`. При отмене вывоза очистить ссылку, сохранив историю. |
| `cancellation_container_owner_history_id` | `uuid` | NULL, FK → `container_owner_history.id` | Событие отмены фактической приёмки (`CANCEL_ARRIVAL`). Такой визит исключается из расчёта. |

Добавить `UNIQUE (id, container_id)` для составной ссылки из строки передачи. Частичный уникальный индекс по `container_id` с условием `shipping_container_owner_history_id IS NULL AND cancellation_container_owner_history_id IS NULL` допускает один действующий открытый визит. Предусмотреть индекс для выборки визитов по КТК. Все граничные события должны принадлежать этому КТК и соответствовать своему виду операции. Приёмка после вывоза открывает строку с новым UUID.

## 1.3. Новая таблица `container_period` — период владения

| Поле | Тип | Обязательность и связь | Как заполнять |
| --- | --- | --- | --- |
| `id` | `uuid` | PRIMARY KEY | Устойчивый идентификатор периода для связи со строкой передачи и историей КТК. |
| `container_visit_id` | `uuid` | NOT NULL, FK → `container_visit.id` | Визит, в котором действует назначение собственника. Индексировать для чтения всех периодов визита. |
| `client_id` | `uuid` | NOT NULL, FK → `client.id` | Собственник с начала периода. Совпадает с `new_client_id` начального события. |
| `start_container_owner_history_id` | `uuid` | NOT NULL, UNIQUE, FK → `container_owner_history.id` | Для первого периода — то же событие приёмки, что у визита. Для следующего — событие `OWNER_CHANGE` этого КТК по заявке на смену. |
| `service_order_id` | `uuid` | NULL, FK → `service_order.id` | Для приёмки — `NULL`. Для передачи записать `order_id` начального события и проверить совпадение со строкой заявки. |

Конец соседнего периода определяется при чтении. Обеим новым таблицам достаточно указанных пяти полей. Время, автор и документ операции доступны через связанную историю. ## 1.4. Существующая таблица `container_owner` — текущий остаток

В ALIS уже есть собственник, уникальный КТК, обе ссылки на заявки, статус и четыре поля аудита. Обеспечить следующий **физический порядок колонок**. Типы строки статуса и аудита ниже приведены для основной системы.

| № | Поле | Тип в ALIS | Ограничение и назначение |
| --- | --- | --- | --- |
| 1 | `id` | `uuid` | PRIMARY KEY. Сохранить существующий идентификатор записи регистра. |
| 2 | `client_id` | `uuid` | NOT NULL, FK → `client.id`. Текущий собственник. |
| 3 | `container_id` | `uuid` | NOT NULL, UNIQUE, FK → `container.id`. Одна запись на физический КТК. |
| 4 | `receiving_order_id` | `uuid` | NULL, FK → `receiving_order.id`. Текущая поставка. Ссылку сохранять при приёмке, передаче и вывозе. |
| 5 | `shipping_order_id` | `uuid` | NULL, FK → `shipping_order.id`. Связанный вывоз при резерве и выбытии. После следующей поставки сохранять предыдущий действительный вывоз, если он был. |
| 6 | `status` | `varchar(12)` | NOT NULL. Допустимы `EXPECTED`, `ON_TERMINAL`, `RESERVED_OUT`, `DEPARTED`. Сохранить существующий DEFAULT `'ON_TERMINAL'`. |
| 7 | `created_at` | `timestamp` | NOT NULL. Время создания записи. |
| 8 | `created_by` | `varchar(50)` | NOT NULL. Автор создания. |
| 9 | `updated_at` | `timestamp` | NULL. Время изменения. |
| 10 | `updated_by` | `varchar(50)` | NULL. Автор изменения. |

В составе регистра `version` отсутствует. В ALIS его уже нет, в MVP оно удалено миграцией V87. Проверка конкурентных операций выполняется блокировкой строк КТК в стабильном порядке. Сохранить UUID, значения, входящие и исходящие зависимости, индексы по обеим заявкам, права и триггеры при перестановке колонок. Проверять последовательность по `ordinal_position`. ## 1.5. Существующие таблицы — новые атрибуты

### `container_owner_history` — история событий КТК

| Поле | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |
| `occurred_at` | `timestamptz` | NULL для исторических строк с неустановленным временем. Обязательно для новых событий, задающих границы визита или периода. | Точный момент действия. Для приёмки и вывоза брать время подтверждённого события TOS по конкретному КТК. Для передачи фиксировать момент на московскую дату `service_order.transferred_at`. |

Уже существуют `id`, `container_id`, `old_client_id`, `new_client_id`, `order_type`, `order_id`, `old_status`, `new_status` и аудит. `created_at` сохраняет время записи. В паре `(order_type, order_id)` тип определяет таблицу документа — `receiving_order`, `shipping_order` или `service_order`. Проверять существование документа и принадлежность КТК его составу при записи. Для передачи записывать обоих собственников и складские состояния до и после неё. Для новых событий проверять допустимость перехода и соответствие типу заявки.

Обеспечить однозначность фактической приёмки по паре `(order_id, container_id)` для событий `ARRIVAL`. Обеспечить `UNIQUE (container_id, created_at)` и индекс по моменту действия. Новую запись истории создавать под блокировкой физического КТК. Если техническое время совпало с предыдущим или оказалось раньше, взять предыдущее `created_at` плюс одну микросекунду. Это правило применяется к новым записям. Последовательность событий задана ключом `(occurred_at, created_at, id)`. Вид операции, признак отмены и ссылка на период для чтения из истории выводятся по типу документа, переходу состояний и связям с визитом и периодом. ### `service_order` — шапка заявки на смену собственника

| Поле | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |
| `is_deferred` | `boolean` | NOT NULL, DEFAULT `false` | Признак отложенной передачи, выбранный при оформлении. Историческое значение сохраняется после проведения. |
| `execution_error` | `text` | NULL | Причина, по которой подтверждённая заявка не проведена. После успешного проведения очистить. |

Использовать существующие `number`, `old_client_owner_id`, `new_client_owner_id`, `transferred_at` (`date`), `completion_at`, `type_equipment`, `quantity` и `comment`. При передаче КТК заполнять двух разных собственников и `type_equipment = 'CONTAINER'`. Дата действия и время завершения заявки имеют разное назначение. Расширить ограничение существующего `status` со значений `DRAFT`, `DONE` до `DRAFT`, `SCHEDULED`, `DONE`, `CANCELLED`. `SCHEDULED` означает подтверждённую будущую передачу, `CANCELLED` — окончательно отменённую. При расширении ограничения сохранить действующие заявки по вагонам.

### `service_order_container` — состав и результат передачи по КТК

В ALIS уже есть `id`, `service_order_id`, `container_id`, аудит и уникальность пары «заявка + КТК». Добавить следующие поля.

| Поле | Тип | Обязательность и связь | Что записать |
| --- | --- | --- | --- |
| `container_visit_id` | `uuid` | NULL, FK → `container_visit.id` | Визит выбранного КТК. Зафиксировать при подборе и перепроверить при подтверждении. |
| `expected_client_id` | `uuid` | NULL, FK → `client.id` | Прежний собственник непосредственно перед этой передачей в цепочке визита на дату действия. |
| `expected_status` | `varchar(20)` | NULL | Складское состояние, проверенное при подтверждении передачи, — `ON_TERMINAL`. |
| `result_status` | `varchar(20)` | NOT NULL, DEFAULT `'DRAFT'` | Состояние строки. `DRAFT` — черновик, `PLANNED` — ожидает проведения, `APPLIED` — проведена, `CANCELLED` — отменена. Для исторических результатов сохранить `WITHDRAWN` (отозвана) и `SKIPPED` (пропущена). |
| `result_reason` | `text` | NULL | Причина отмены или пропуска этой строки. |
| `container_period_id` | `uuid` | NULL, FK → `container_period.id` | Период нового собственника, созданный при подтверждении. Для проведённой строки обязателен. У окончательно отменённой сохранить ссылку на уже созданный период для аудита. |
| `plan_at` | `timestamptz` | NULL | Момент действия, закреплённый при подтверждении. Совпадает с `occurred_at` события передачи. |
| `plan_client_id` | `uuid` | NULL, FK → `client.id` | Новый собственник строки на момент подтверждения. Совпадает с `new_client_owner_id` шапки. |
| `withdrawn_at` | `timestamptz` | NULL | Момент отзыва исторической строки или окончательной отмены запланированной строки. |

Проверять составной FK `(container_visit_id, container_id) → container_visit(id, container_id)`. У вновь подтверждаемых строк в состояниях `PLANNED` и `APPLIED` должны быть заполнены визит, ожидаемый и новый собственники, момент и связанный период. Проверить совпадение визита, КТК, заявки и нового собственника между строкой, начальным событием и периодом. При переносе старых отозванных попыток применять уникальность `(service_order_id, container_id) WHERE result_status <> 'WITHDRAWN'` вместо прежней безусловной уникальности. Для очереди наступивших передач создать индекс по `(plan_at, container_id)` для `PLANNED`.

Пример различия собственников. Сегодня оба КТК у А. Для первого уже подтверждена передача Б на 17-е. В заявке на 19-е для обоих выбран переход от А к В. В шапке `old_client_owner_id` равен А. В строке первого КТК `expected_client_id` равен Б, второго — А. У обоих `plan_client_id` равен В. Это позволяет восстановить верную цепочку каждого визита. ## 1.6. Запись и чтение связанных данных

| Событие | Что должно быть зафиксировано одной транзакцией |
| --- | --- |
| Резерв поставки | Записать в регистр `EXPECTED` со ссылкой на поставку и событие резерва в историю. Визит появляется после фактической приёмки. |
| Фактическая приёмка одного КТК | По `UNLOAD_FINISH` и строке `FINISHED` записать событие, визит с этим событием, первый период и состояние `ON_TERMINAL`. Обрабатывать КТК отдельно, в том числе при частично выполненной заявке. Повтор результата сохраняет исходные UUID и время. |
| Подтверждение передачи | Заблокировать заявку и КТК по возрастанию их UUID. Проверить открытый визит, фактическую приёмку, занятость и собственников. Для каждой строки создать одно событие передачи и один период. Закрепить их связь с заявкой. Ошибка одного КТК откатывает изменения всей заявки. |
| Передача сегодня или задним числом | Установить `DONE` / `APPLIED`. Расположить событие на дату действия внутри открытого визита после приёмки. Пересчитать текущего собственника по всей действующей цепочке, включая более поздние передачи. |
| Передача в будущем | При подтверждении установить `SCHEDULED` / `PLANNED`. Сохранить событие, период и сообщение с пустым `ready_at`. До даты действия в регистре остаётся действующий собственник. При наступлении даты провести цепочку в порядке действия, обновить регистр, шапку, строки и разрешить отправку. Повтор обработки использует те же записи. |
| Резерв и фактический вывоз | Резерв меняет состояние на `RESERVED_OUT`. Визит остаётся открытым. По фактическому `LOAD_FINISH` записать событие вывоза и его ссылку в визите, установить `DEPARTED`. Последний период заканчивается этим событием. Блокировать вывоз при действующем ожидающем назначении для КТК. |
| Отмены | При отмене ожидающей передачи сохранить событие и период для аудита, исключить назначение из действующей цепочки. Если от него зависит более поздняя передача, сначала снять зависимость. При отмене фактического вывоза открыть прежний визит. При отмене приёмки записать событие отмены в визит, исключить его периоды, аннулировать зависимые будущие передачи и восстановить действующие ссылки регистра из истории. |

Подготовить SQL-представления или эквивалентные выборки для чтения фактов визита, действующих назначений по визиту и периодов на дату расчёта. Поставку и вывоз визита получать по соответствующим граничным событиям и их `order_id`. Справочники `container` и `client` дают номер КТК и наименование собственника. Реквизиты перевозки и груз получать из связанных документов и строк именно этого КТК и визита. Для ЖД-поставки использовать состав накладной. Для автопоставки и вывоза — грузовые позиции соответствующей строки. Число грузовых позиций не должно менять число визитов и периодов.

Даты начала и конца, открытость, количество дней, номера заявок, груз и отображаемые имена вычисляются при чтении. У периода конец — ближайшее следующее действующее начало в том же визите или его фактический вывоз. Сначала выбрать действующие события на `asOf`, затем внутри каждого визита найти следующее начало. Только после этого применять отбор по месяцу или диапазону к пересечению всего визита. Для выбранного визита вернуть все начавшиеся к `asOf` периоды, включая периоды с нулём дней в выбранном диапазоне. Для открытого интервала расчёт заканчивается на `asOf`. Переводить моменты в `Europe/Moscow` до вычитания дат. Учитывать обе граничные даты, при отборе за месяц брать пересечение интервала с месяцем. День передачи засчитывается обоим собственникам и один раз в длительности визита. [Правила расчёта и граничные случаи](backend.md#дни-хранения)

### Фактическая приёмка и вывоз по каждому КТК

**Задача разработчику ALIS.** Для контейнерной площадки проводить складскую операцию по каждой фактически выполненной строке заявки на поставку или вывоз. При первом подтверждённом результате для КТК в одной транзакции сохранить `FINISHED` у строки, изменить её КТК в `container_owner` и добавить событие в `container_owner_history`. Бизнес-время события (`occurred_at`) взять из `eventDateTime` этого результата TOS. Остальные строки заявки ждут собственных результатов.

В исходном `backend-stage` обработчики `TosReceivingResultAction` и `TosShipmentResultAction` уже пишут `FINISHED` по заданиям. Вызовы `ContainerStatusService.markReceived` и `markShipped` находятся в ветках завершения всей заявки и получают весь состав. Перенести проведение КТК в обработку его результата. В ветке завершения оставить проверку полноты и переход шапки в `DONE`. Складские границы вагона определяются его собственными событиями из раздела 1.9. [Исходники ALIS](https://github.com/airafka/dev_back/blob/08343f22af5413321dd3136f1336c4f2f37b8c8a/backend-stage%20%281%29.zip)

| Операция | Событие и строка, которую завершить | Что записать для этого КТК |
| --- | --- | --- |
| Поставка, КП-Авто | `UNLOAD_FINISH`. `_id` — идентификатор `receiving_order_container` указанной поставки. Сохранить фактическое количество из результата по действующим правилам. | `EXPECTED → ON_TERMINAL`. В регистре установить `receiving_order_id`. В истории указать `RECEIVING_ORDER` и ID поставки. Открыть визит и первый период собственника. |
| Поставка, КП-ЖД | `UNLOAD_FINISH`. `_id` — идентификатор `waybill_container`. Проверить связь через вагон накладной и накладную с поставкой `_order`. | Тот же переход `EXPECTED → ON_TERMINAL` и событие приёмки по поставке. Начало хранения — время выгрузки конкретного КТК. |
| Вывоз, КП-Авто | `LOAD_FINISH`. Для `ALL` завершить строку `shipping_order_container` по `_id`. Для `NONE_CONTAINER` определить порожний КТК по `cargoNumber` единственного `cargoResult`, создать или обработать его фактическую строку с `id = _id`. | Установить `DEPARTED` и `shipping_order_id`, сохранить ссылку на поставку. В истории указать `SHIPPING_ORDER` и ID вывоза. Закрыть открытый визит и последний период. |
| Вывоз, КП-ЖД | `LOAD_FINISH`. Для `ALL` завершить номерную строку `shipping_order_container`. Для поддерживаемых вариантов `CONTAINER`, `RAILWAY_CARRIAGE` и `NONE` провести каждый КТК, для которого обработчик привязал вагон или создал фактическую строку сразу с `FINISHED`. | Тот же переход в `DEPARTED` и событие по заявке вывоза для каждого фактически погруженного КТК. Завершение строки вагона само по себе состояние его КТК не меняет. |

**Прибытие и выгрузка на ЖД.** В `CarriageArrivedAction.handleContainerArrived` исключить присвоение `FINISHED` строке `waybill_container` по `VH_ARRIVED`. Сохранить регистрацию прибытия и фактического времени прибытия заявки. Обработку `VH_ARRIVED` по строке самого вагона сохранить. Пока пришло только прибытие, КТК остаётся `EXPECTED`, визит и период хранения ещё не открыты. При обновлении системы у действующей заявки уже может быть строка `FINISHED`, выставленная прежним обработчиком. Первый достоверный `UNLOAD_FINISH` должен провести такой КТК, если факт приёмки по этой поставке ещё отсутствует. При сверке незавершённых заявок использовать результаты выгрузки по КТК.

**Правила записи.**

1. Проводить положительный результат погрузки или выгрузки с идентифицированным КТК. Сообщение только о дополнительных услугах, результат с `active=false` и команда о смене статуса шапки сами по себе не подтверждают движение. До записи проверить площадку, допустимый статус заявки, принадлежность задания `_id` к `_order` и фактический `container_id`. Для номерной строки с разрешённой заменой провести КТК, закреплённый за строкой после проверки замены, и корректно снять её прежний резерв. При несовпадении номера без разрешённой замены, чужом идентификаторе или противоречии зафиксированному факту отклонить обработку целиком.
2. Повторно использовать переходы `ContainerStatusService` для конкретного КТК. При номерном вывозе проверить `RESERVED_OUT` именно этой заявки. Когда номер впервые определён при погрузке, проверить свободный `ON_TERMINAL` по фактическому КТК, закрепить резерв этой заявки и провести вывоз в одной транзакции. Запись резерва отличать от единственного события фактического вывоза. Сохранить действующего собственника, одну запись регистра на `container_id` и её `id`.
3. В строку истории записать `container_id`, `order_type`, `order_id`, `old_status`, `new_status`, `old_client_id`, `new_client_id` и `occurred_at`. У обычной приёмки и вывоза сохраняется тот же собственник. Поля аудита заполнять штатным механизмом. Связь визита и периода с этим событием записать в той же транзакции по разделам 1.2–1.3.
4. Под блокировкой заявки и затронутых КТК отличать уже проведённый факт по типу операции, заявке и физическому КТК. Точный повтор после проведения, включая параллельную доставку и повтор после `DONE`, сохраняет время первого события, UUID, количество строк истории и текущее состояние регистра. Для пакета с несколькими фактическими КТК различать строки по КТК внутри задания. В ветках ЖД-вывоза `RAILWAY_CARRIAGE` и `NONE` текущий обработчик присваивает всем создаваемым строкам пакета один `id = taskId`. Для нескольких КТК назначать каждой новой строке собственный UUID и при повторе находить её по заявке и физическому КТК. Для варианта `CONTAINER` задание указывает на уже существующую строку состава. При ошибке откатить также статус строки и новые записи визита.
5. После проведения результата проверить полноту заявки под той же блокировкой. На переходном этапе строку ЖД-поставки, ранее завершённую по `VH_ARRIVED`, учитывать как выгруженную только при наличии факта приёмки по этой заявке и КТК. Для номерного состава проверить все действующие строки КТК. Для безномерных вариантов учитывать требуемое заявкой количество и фактически выполненный состав по правилам варианта. `DONE` ставить один раз при полном выполнении. Для отмены частично выполненной заявки разделять факты и резервы по КТК. У уже принятого КТК аннулировать визит, у уже вывезенного — открыть прежний визит. У остальных снять только резерв этой заявки. До изменений проверить последующие операции по всему затронутому составу.

**Приёмка на отдельной БД.** Проверять SQL-строки регистра и истории по заявке, КТК и переходу статусов. В исходной ALIS список истории карточки фильтрует заявки по `DONE` и не годится для проверки частичного результата.

| Сценарий | Ожидаемый результат после фиксации транзакции |
| --- | --- |
| В номерной поставке пять КТК. Обработать `UNLOAD_FINISH` для двух. Повторить для КП-Авто и КП-ЖД. | Две строки `FINISHED`, у двух КТК `ON_TERMINAL`, два новых события фактической приёмки и два визита. Ещё у трёх `EXPECTED` и только резерв. Заявка открыта. После результатов по оставшимся трём — `DONE` и всего пять фактов приёмки. |
| В номерном вывозе пять зарезервированных КТК. Обработать `LOAD_FINISH` для двух. Повторить для обоих видов транспорта. | Два КТК `DEPARTED`, два новых события фактического вывоза, два визита закрыты. Ещё три КТК в `RESERVED_OUT` с открытыми визитами. После последних трёх результатов заявка в `DONE` и всего пять фактов вывоза. |
| Для ЖД-поставки прислать `VH_ARRIVED` по вагону и по его КТК 10 ноября, `UNLOAD_FINISH` этого КТК 11 ноября. Повторить выгрузку. | После прибытия фактов приёмки — 0. После выгрузки — 1. Визит и первый период начинаются 11 ноября по Москве. Повтор сохраняет исходные UUID и время. |
| Проверить безномерный автовывоз одного порожнего КТК и ЖД-вывоз с фактическими строками. Затем доставить результат повторно и конкурентно. | На каждый фактически определённый КТК одна завершённая строка и одно событие вывоза. Вагон с несколькими КТК даёт столько фактов, сколько физических КТК погружено. |
| Передать `_id` строки другой заявки. Отдельно отменить поставку и вывоз после выполнения двух строк из пяти. | Чужая строка, регистр и история сохраняют прежние значения. При допустимой отмене изменяются ровно два состоявшихся визита, а по трём оставшимся строкам снимаются только резервы. |

## 1.7. Миграция существующих данных

1. Подготовить изменения в новых Liquibase changeset основной системы. Взять свежую резервную копию, проверить восстановление в отдельной БД и выполнить на ней весь перенос. Зафиксировать исходные UUID регистра, заявок, их строк и истории, состояния заявок, действующих собственников, аудит и состояние очереди.
2. Создать таблицы и добавить поля, допускающие переходное заполнение. Построить хронологию **для каждого КТК** по фактически завершённым строкам авто- и ЖД-поставок, вывозов, их отменам, сообщениям TOS и истории подтверждённых смен. Отличать повторное сообщение по той же операции от нового заезда. Хронологию вагонов той же ЖД-заявки восстанавливать отдельно по правилам раздела 1.9.
3. Заполнить `occurred_at` у достоверных событий, назначить UUID визитам и периодам по идентификатору начального события. Связать строки ранее исполненных передач с конкретным визитом и периодом, установить `APPLIED`, сохранить историческое завершение заявки. Черновики остаются черновиками. Для очереди сохранить отметки доставки, допустить к отправке прежние действительно ожидающие проведённые сообщения. Повторный перенос не должен повторно ставить доставленную заявку в очередь.
4. Выдать перечень неоднозначных записей с UUID КТК, документа и события, причиной и недостающим источником. В старой ALIS у передачи могут отсутствовать оба складских статуса. Для части старых заявок миграция заполняла `transferred_at` по `created_at`. Сверять эти строки с первичными событиями. Резерв, техническое время записи и сегодняшняя ссылка в регистре сами по себе недостаточны для восстановления факта. До создания уникальных индексов проверить дубли `(container_id, created_at)` и фактов приёмки. При конфликте сохранить исходный аудит и вынести записи на сверку. Для проверки допустимых переходов `CHECK … NOT VALID` позволяет защитить новые записи во время разбора старых. Выполнить `VALIDATE CONSTRAINT` после устранения нарушений во всей таблице.
5. Проверить внешние ключи, уникальность, порядок колонок и согласованность исторических цепочек. Для текущего остатка сравнить состояние до и после переноса по КТК. Повторить заполнение на той же восстановленной базе и сверить UUID, количество строк, границы, аудит и очередь. Рабочую БД обновлять после приёмки переноса и проверки восстановления свежей копии.

Исходные поля ALIS проверяются в архиве по `db-layer/src/main/resources/db/changelog`. Базовые таблицы введены миграцией от 07.07.2026 в `v.1.34.0`. В `v.1.35.0` миграция KIS-4661 от 15.09.2026 добавила статусы и ссылки на транспортные заявки, KIS-4935 от 04.11.2026 перенесла собственников шапки, а миграция от 18.11.2026 привела `transferred_at` к типу `date`. [Инструкция по резервному копированию](../../database/README.md#резервная-копия-перед-изменениями)

## 1.9. Хранение вагонов на КП-ЖД

**Единица учёта — один визит физического вагона** (`railway_carriage.id`) на контейнерной площадке. Начало — `eventDateTime` события `VH_ARRIVED` по вагону в ЖД-поставке. Конец — `eventDateTime` события `VH_DEPARTURE` по этому вагону в ЖД-вывозе. У порожнего вагона тот же порядок. Один вагон с несколькими КТК даёт один вагонный визит. Для каждого КТК на нём продолжают действовать собственные границы `UNLOAD_FINISH` и `LOAD_FINISH`.

### Существующие источники в ALIS

| Объект | Что использовать |
| --- | --- |
| `railway_carriage`, `railway_carriage_owner` | `railway_carriage.id` идентифицирует вагон, `code` содержит его номер. В регистре уже есть уникальный `railway_carriage_id`, собственник `client_owner_id`, складской `status` и ссылки на поставку и вывоз. |
| `railway_carriage_owner_history` | Существующие UUID события и вагона, `order_type`, `order_id`, `old_status`, `new_status`, `old_client_owner_id`, `new_client_owner_id` и аудит. Для физической границы требуется точное время действия. |
| `waybill_railway_carriage`, `shipping_order_railway_carriage` | На входе проверить строку вагона через накладную и поставку. Взять заявленного собственника вагона, при пустом значении — собственника вагонов по умолчанию из поставки. На выходе проверить фактическую строку вагона и её заявку. В ALIS ссылка на собственника этой строки — `owner_railway_carriage_id_new`. |
| `service_order`, `service_order_railway_carriage` | Существующая заявка с `type_equipment = 'RAILWAY_CARRIAGE'` и её состав по `(service_order_id, railway_carriage_id)`. Проведённая смена собственника вагона записывает своё событие в вагонную историю. |

В ALIS `RailwayCarriageOwnerService` ведёт отдельный регистр вагонов. Миграция KIS-4935 от 05.11.2026 восстанавливала текущий остаток по заявкам. В MVP V87 `railway_carriage_owner` — представление над журналом с числовым ключом. Ниже задана **целевая схема ALIS** с UUID её существующей вагонной истории. [Снимок исходников ALIS](https://github.com/airafka/dev_back/blob/08343f22af5413321dd3136f1336c4f2f37b8c8a/backend-stage%20%281%29.zip) · [Вагонный журнал MVP](../../backend/src/main/resources/db/baseline/V71__unnumbered_shipment_owners.sql)

Создать частичный уникальный индекс по `railway_carriage_visit.railway_carriage_id` для строк, в которых ссылки на выезд и отмену прибытия обе равны `NULL`. Создать индекс периодов по `railway_carriage_visit_id`. При записи проверять, что ссылки ведут на события того же физического вагона и соответствующей операции. Для передачи сверять состав заявки, новый `client_owner_id` и `new_client_owner_id` события. Защитить факт от повторной записи по паре `(order_id, railway_carriage_id)` отдельно для прибытия по поставке, выезда по вывозу и проведённой передачи по услуге. Резервы и их отмены сохраняют собственные записи истории. Момент выезда должен быть не раньше прибытия, а событие передачи должно попадать внутрь своего визита. Для событий с одним моментом использовать техническое время записи и UUID как устойчивый порядок. Началом первого периода служит то же событие, что открыло визит. Повторный заезд после выезда получает новый UUID.

### Проведение вагонных событий

1. **Прибытие.** В `CarriageArrivedAction.handleRailwayCarriageArrived` для ЖД-поставки разрешить `_id` в строку `waybill_railway_carriage`, проверить принадлежность этой строки заявке `_order` и взять `railway_carriage_id`. Для этого вагона провести `EXPECTED → ON_TERMINAL`, создать запись истории, визит и первый период. Несколько строк одного физического вагона в разных накладных одной поставки дают один факт. Противоречащих друг другу собственников направить на сверку. `VH_ARRIVED` по заданию КТК или подача вагона под погрузку в заявке вывоза не открывают второй визит.
2. **Подготовка вывоза.** Для `ALL` и `RAILWAY_CARRIAGE` номер вагона известен при подтверждении заявки — использовать существующий резерв `RESERVED_OUT`. Для `CONTAINER` и `NONE` изначально задано количество вагонов. Когда определён реальный номер, проверить доступность, тип, собственника и лимит заявки под блокировкой, сохранить фактическую строку вагона и закрепить резерв. Сейчас `markUnnumberedCarriageShipped` при таком подборе может списать вагон уже на `LOAD_FINISH`. Перенести окончательное списание на вагонный выезд. До него визит открыт, в том числе после погрузки последнего КТК.
3. **Выезд.** Доработать обработку `VH_DEPARTURE` для ЖД-вывоза контейнерной площадки. Сейчас `VhDepartureAction` обновляет дату шапки и не устанавливает, какой вагон выбыл. Целевое сообщение содержит `_order`, `eventDateTime` и однозначный идентификатор вагона в составе этого вывоза. Основной вариант — `_id = shipping_order_railway_carriage.id`. Для ранее безномерного вагона разрешить согласованный с TOS физический номер вместе с `_order`, только если найдена ровно одна соответствующая строка или вагон однозначно определяется в количественном плане и может быть закреплён этой заявкой. Во втором случае зарегистрировать фактическую строку и резерв в той же транзакции. Поддержать порожний вагон без `cargoResult`. Если сообщение содержит и идентификатор строки, и номер вагона, проверить их совпадение. При отсутствии или неоднозначности идентификатора оставить визит открытым и вернуть причину для сверки. Перед вводом проверить на примерах от TOS, какой идентификатор передаётся и как настроена маршрутизация этого события на КП-ЖД.
4. **Запись факта.** На физический выезд перевести один вагон в `DEPARTED`, связать регистр с вывозом, записать историю и закрыть визит ссылкой на неё. Начало и конец хранения брать из `occurred_at` соответствующих событий. Оформлять регистр, историю, визит и период в одной транзакции под блокировкой вагона. Сверять тип документа, заявку, вагон и вид факта. Повтор события, в том числе с другим UUID строки накладной того же вагона или параллельно, сохраняет первоначальные UUID и время. Пакетные `markReceived` и `markShipped` при `DONE` не должны создавать или подменять физические границы. Если шапка уже закрыта по грузовым операциям, разрешить последующее достоверное подтверждение выезда закреплённого вагона. Отменённая заявка и конфликт с более поздним визитом требуют сверки.
5. **Смена собственника.** При проведении существующей вагонной заявки в `RailwayCarriageOwnerService.changeOwners` открыть следующий период в действующем визите по событию передачи именно этого вагона. Записать в `occurred_at` момент вступления проведённой передачи в силу. `transferred_at` хранит календарную дату передачи, `completion_at` — завершение заявки. Сверять их назначение при восстановлении хронологии. Черновик и само наступление указанной в нём даты не создают период. Для хранения достаточно подтверждённого факта смены. Передача вагона не меняет периоды перевозимых КТК, передача КТК не меняет периоды вагона.
6. **Отмена и история.** При отмене проверять тип и UUID заявки, вагон и его фактическую связь с визитом. Для поставки различать отмену резерва `EXPECTED → DEPARTED` и аннулирование прибытия `ON_TERMINAL → DEPARTED`. Для вывоза различать снятие резерва `RESERVED_OUT → ON_TERMINAL` и отмену состоявшегося выезда `DEPARTED → ON_TERMINAL`. Снятие резерва оставляет действующие границы визита. При допустимой отмене состоявшегося выезда записать обратное событие, снять ссылку на выезд и снова открыть тот же визит и последний период. При отмене физического прибытия пометить визит ссылкой на событие отмены, исключить его периоды из расчёта. Если уже есть зависимая передача, следующий заезд или другой вывоз, проверить цепочку до изменения. Для частично выполненной заявки различать факты и резервы по каждому вагону.

### Расчёт, перенос и приёмка

Считать московские календарные дни с включением обеих границ. Открытый визит ограничивать датой расчёта `asOf`. У периода собственника конец определяется следующим действующим началом в том же визите либо фактическим выездом. День передачи входит в оба периода и один раз в итог визита. При отборе за месяц или диапазон брать пересечение с интервалом. Длительность вагона рассчитывать отдельно от числа и дней хранения его КТК.

На восстановленной копии сопоставить по каждому физическому вагону успешно обработанные события TOS, строки заявок и накладных, отмены и историю передач. В старом учёте `DEPARTED` мог появиться при погрузке, а время шапки может относиться к другому вагону. Для исторической строки с неподтверждённой границей выдать на сверку UUID вагона и заявки и недостающий факт. Вагон с подтверждённым нахождением на площадке имеет открытый визит. Архивную цепочку с неизвестным выездом и спорным остатком оставить в перечне расхождений до сверки, чтобы дни по ней не продолжали начисляться. Повтор переноса сохраняет UUID и количество визитов и периодов.

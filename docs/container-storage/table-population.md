# Блок 2. Правила заполнения истории, визитов и периодов хранения

**Цель.** По записям ALIS должно быть возможно определить, когда конкретный КТК или вагон находился на площадке, кто владел им на выбранную дату и какой документ изменил его состояние. Физический объект определяется UUID из справочника, каждый его заезд получает отдельный UUID визита.

История содержит запись о каждом складском переходе или назначении собственника. Визит объединяет события одного пребывания. Период связывает одного собственника с частью визита. **Фактическое прибытие создаёт и визит, и первый период. Передача создаёт следующий период в том же визите. Выбытие закрывает визит и последний период через одну ссылку в визите.** [Блок 1. Схема и ограничения БД](database.md)

## 2.1. Таблицы и источники полей

Значения ссылок в таблице ниже берутся из сохранённых строк той же операции.

| Что записать | Для КТК | Для вагона | Источник значения |
| --- | --- | --- | --- |
| Строка истории | `container_owner_history` | `railway_carriage_owner_history` | Новый `id` (UUID) для отдельного события каждой единицы оборудования. `container_id` или `railway_carriage_id` взять из проверенной строки документа. |
| Основание события | `order_type`, `order_id` | `order_type`, `order_id` | `RECEIVING_ORDER` + UUID поставки, `SHIPPING_ORDER` + UUID вывоза, `SERVICE_ORDER` + UUID заявки смены. Для отмены указать исходный документ, действие которого отменяется. |
| Стороны и состояние | `old_client_id`, `new_client_id` | `old_client_owner_id`, `new_client_owner_id` | В `old_status` записать состояние до операции, в `new_status` — состояние после неё по разделам 2.2–2.4. Для обычного движения сохранять фактического собственника. Для передачи записать прежнего и нового владельцев на момент действия. |
| Время | `occurred_at` | `occurred_at` | Для физического движения — подтверждённое время события (`eventDateTime`). Для резерва и отмены — время вступления операции в силу. Для передачи — время действия назначения. `created_at` и `created_by` заполняются штатным аудитом при создании, `updated_at` и `updated_by` — по действующим правилам изменения. Отмена движения добавляет собственную запись истории и сохраняет исходное событие. |
| Визит | `container_visit` | `railway_carriage_visit` | Новый `id` и FK на физический объект. При создании в `receiving_container_owner_history_id` / `receiving_railway_carriage_owner_history_id` записать UUID события прибытия. Ссылки на выезд и отмену прибытия первоначально `NULL`. |
| Период | `container_period` | `railway_carriage_period` | Новый `id`, FK `container_visit_id` / `railway_carriage_visit_id` на этот визит. `client_id` / `client_owner_id` равен новому собственнику начального события. `start_container_owner_history_id` / `start_railway_carriage_owner_history_id` равен UUID этого события. `service_order_id` у первого периода равен `NULL`, у периода передачи — UUID заявки смены. |

В строке периода хранятся его начало и собственник. Конец определяется следующим действующим началом в том же визите либо фактическим выбытием. До наступления конечной границы период открыт. UUID визита, истории и периода принадлежат разным строкам. Повторный приезд того же оборудования образует новый визит со своей поставкой.

## 2.2. Поставка и вывоз

**Как определить оборудование и границу хранения**

| Оборудование и операция | Факт и источник оборудования |
| --- | --- |
| КТК, поставка КП-Авто или КП-ЖД | `UNLOAD_FINISH` по КТК. Для авто проверить `receiving_order_container` указанной поставки, для ЖД — `waybill_container` через вагон накладной, накладную и поставку. Собственник — заявленный и проверенный для этого КТК при резерве. `VH_ARRIVED` по вагону или по заданию КТК хранения КТК не открывает. |
| КТК, вывоз КП-Авто или КП-ЖД | `LOAD_FINISH` по фактически погруженному КТК из `shipping_order_container`. При разрешённой замене использовать подтверждённый фактический КТК. При безномерной операции проверить номер и привязать фактическую строку к заявке. Правило действует и при создании строки сразу с `FINISHED`. |
| Вагон, ЖД-поставка | `VH_ARRIVED` по строке `waybill_railway_carriage` этой поставки. Собственник — из строки вагона, при отсутствии — собственник вагонов по умолчанию из поставки. Один вагон в нескольких накладных одной поставки даёт один факт. |
| Вагон, ЖД-вывоз | `VH_DEPARTURE` по однозначно установленному вагону этого вывоза. Факт допустим и для порожнего вагона. Подача вагона под погрузку, погрузка последнего КТК и завершение заявки сами по себе не закрывают вагонный визит. |

**Что изменить при успешной операции**

| Событие и предусловие | Запись в историю соответствующего оборудования | Изменение визита | Изменение периода |
| --- | --- | --- | --- |
| Резерв поставки. Новый объект либо разрешён повторный заезд после выбытия. | Добавить `RECEIVING_ORDER`. При первом резерве прежние статус и собственник — `NULL`, при повторном — `DEPARTED` и прежний собственник. Новые значения — `EXPECTED` и заявленный собственник. | Нет записи. | Нет записи. |
| Фактическое прибытие. Есть резерв этой поставки. | Добавить `RECEIVING_ORDER`, `EXPECTED → ON_TERMINAL` с временем движения. | Создать визит, сослаться на эту запись истории. | Создать первый период, сослаться на **то же событие**. Собственник берётся из события. |
| Резерв вывоза. Идентифицирован объект в действующем визите. | Добавить `SHIPPING_ORDER`, `ON_TERMINAL → RESERVED_OUT`. Количественный план без физического номера событий по оборудованию не создаёт. | Остаётся открытым. | Продолжается текущий период. |
| Фактическое выбытие. Объект относится к текущему визиту и вывозу. | Добавить `SHIPPING_ORDER`, `RESERVED_OUT → DEPARTED`. Если при допустимом безномерном вывозе объект определился только сейчас, сначала подтвердить его доступность и зафиксировать резерв этой заявки в той же транзакции. | В существующем визите установить `shipping_container_owner_history_id` / `shipping_railway_carriage_owner_history_id` в UUID события выбытия. | Новых строк — 0. Последний период оканчивается в `occurred_at` события выбытия. |

При результате по двум КТК из пяти провести только эти два КТК. У остальных сохраняются прежние записи и границы. Для вагона с несколькими КТК состояние каждого объекта изменяется по собственному событию. Присвоение `DONE` шапке заявки само по себе не добавляет историю, визит или период. [Подробные правила для четырёх транспортных сценариев](database.md#фактическая-приёмка-и-вывоз-по-каждому-ктк) · [Вагоны на КП-ЖД](database.md#19-хранение-вагонов-на-кп-жд)

## 2.3. Смена собственника внутри визита

**Предусловия для КТК.** В заявке определены физический КТК и его открытый визит, фактическая приёмка подтверждена, КТК доступен для передачи. Дата действия попадает в этот визит. Новый собственник отличается от действующего на момент передачи. При подтверждении повторно проверить весь состав и сопоставить выбранный визит с текущим. При несовпадении отклонить операцию.

| Сценарий | История | Визит и периоды |
| --- | --- | --- |
| Черновик | Новых событий передачи — 0. | Новых визитов и периодов — 0. Выбранный КТК может быть привязан к визиту в строке черновика. |
| Подтверждение передачи КТК сегодня или задним числом | По каждому КТК добавить одну запись с `order_type = 'SERVICE_ORDER'`, `order_id` — UUID заявки. `old_client_id` взять из цепочки визита непосредственно перед новым назначением, `new_client_id` — из заявки. Для передачи записать одинаковые `old_status` и `new_status` на момент действия. | В существующий визит добавить период нового собственника. Начальное событие — созданная запись истории. Записать UUID периода в `service_order_container.container_period_id` соответствующего КТК. Предыдущий период заканчивается на этой границе при чтении. |
| Подтверждение будущей передачи КТК | При подтверждении создать одну запись назначения с `occurred_at = plan_at`. Новый и прежний собственники соответствуют `plan_client_id` и `expected_client_id` строки. Если сегодня КТК у А, на 17-е подтверждена передача Б, а на 19-е оформлена передача В, событие 19-го записывает Б → В. | В этом же визите сразу создать один период и сохранить ссылку в строке заявки. До даты действия период скрыт в фактическом хранении, собственник в текущем остатке прежний. При проведении `PLANNED → APPLIED` остаются те же UUID истории и периода. |
| Проведённая передача вагона | По `type_equipment = 'RAILWAY_CARRIAGE'` и вагону из состава добавить одно событие в `railway_carriage_owner_history`. Указать собственников до и после передачи, одинаковый складской статус и фактический момент действия. | Найти визит этого вагона, добавить в `railway_carriage_period` период нового собственника, связанный с событием и заявкой. Строки КТК на вагоне сохраняются. Для вагона основанием служит проведённая смена. |

Складской факт датируется временем движения. Значения `created_at` и `occurred_at` у будущей или оформленной задним числом передачи могут приходиться на разные даты. Для КТК календарная дата `occurred_at` в `Europe/Moscow` должна совпадать с `service_order.transferred_at`. При нескольких событиях в один день поместить передачу после приёмки и уже действующего назначения на эту дату. При равенстве бизнес-времени порядок чтения задают `created_at` и UUID события. При вставке задним числом добавить новое событие и период в хронологию визита. Сохранить исходные UUID, время и участников ранее записанных событий. Например, если передача Б на 18-е уже оформлена, а затем внесена передача В на 17-е, последовательность периодов станет А → В → Б. На 20-е собственником останется Б.

## 2.4. Отмена и повторное поступление

До записи определить исходное событие по типу заявки, её UUID, оборудованию и визиту. Проверить последующие операции. Если операция с другой заявкой или следующим визитом не позволяет выполнить отмену, отклонить всю отмену. При частично выполненной заявке различать фактическое движение и резерв **для каждой строки**.

| Что отменяется | Запись в историю | Действие с визитом и периодами |
| --- | --- | --- |
| Резерв поставки | Добавить событие `RECEIVING_ORDER`, `EXPECTED → DEPARTED`. | У этой поставки ещё нет визита. Не создавать визит или период. |
| Фактическое прибытие | Добавить событие `RECEIVING_ORDER`, `ON_TERMINAL → DEPARTED`. Указать собственника до отмены и собственника, восстановленного по резерву поставки. Если прежнего собственника до первой поставки не было, сохранить клиента отменяемой поставки. | У исходного визита заполнить `cancellation_container_owner_history_id` / `cancellation_railway_carriage_owner_history_id` новым событием отмены. Визит и периоды сохранить с их UUID и исключить из действующего хранения. Зависимые будущие передачи КТК аннулировать согласно правилам заявки. |
| Резерв вывоза | Добавить событие `SHIPPING_ORDER`, `RESERVED_OUT → ON_TERMINAL` с действующим собственником. | Визит и текущий период продолжаются. Ссылку на фактический вывоз не создавать. |
| Фактический вывоз | Добавить событие `SHIPPING_ORDER`, `DEPARTED → ON_TERMINAL` с действующим собственником. | Проверить, что визит закрыт именно вывозом этой заявки. Очистить ссылку `shipping_container_owner_history_id` / `shipping_railway_carriage_owner_history_id`. Открываются прежние визит и последний период с теми же UUID. Исходное событие вывоза и событие отмены сохраняются. |
| Подтверждённая будущая передача КТК | Сохранить исходное событие назначения. Отмена ожидающей заявки сама по себе не создаёт обратную смену собственника. | Сохранить период и связь со строкой заявки. После `CANCELLED` исключить назначение из действующей цепочки. Если есть зависимая более поздняя передача, сначала отменяется она. |

Повтор уже проведённой операции, в том числе после следующего заезда, не должен менять текущий регистр или переносить старое событие в новый визит. Для действительно новой поставки создать новые UUID визита и первого периода, даже когда КТК и собственник прежние.

## 2.5. Целостность записи

- Обрабатывать один подтверждённый физический факт по конкретной единице оборудования. Различать движение, резерв и отмену по виду операции, типу документа, UUID документа и оборудования. Несколько накладных, строк груза или повторных сообщений по одному факту не умножают историю. Несколько физических КТК в одном пакете дают самостоятельные события.
- В рамках одной транзакции проверить документ и исходное состояние под блокировкой, сохранить событие, затем визит и зависимый период либо обновить соответствующую ссылку визита. Обновление состояния оборудования фиксировать вместе с этими записями. Для передачи или отмены нескольких единиц проверять весь состав и блокировать оборудование в стабильном порядке.
- Точный повтор использует уже сохранённый результат. Противоречие между номером, оборудованием, заявкой или ранее подтверждённым временем передать на сверку. При ошибке ни одна таблица не получает частичный результат. При параллельной обработке допускается один действующий открытый визит данного объекта и один период на начальное событие.
- Для каждой связи проверять совпадение оборудования между историей и визитом, а также совпадение нового собственника начального события с собственником периода. Поздно пришедший результат относится к исходной заявке. Для исторической строки с неподтверждённым фактом или временем зафиксировать расхождение с UUID объекта и документа. Техническая дата записи не заменяет время физического движения.

## 2.6. Сквозной пример и критерии приёмки

Один КТК `C1`, собственники А и Б. `R1` — заявка поставки, `S1` — заявка смены, `D1` — заявка вывоза. Обозначения `H`, `V` и `P` ниже заменяют реальные UUID строк. Все даты указаны по Москве.

| Шаг | `container_owner_history` | `container_visit` | `container_period` |
| --- | --- | --- | --- |
| Резерв первой поставки `R1` | `H1`: КТК `C1`, `NULL → EXPECTED`, собственник `NULL → А` | 0 строк | 0 строк |
| Приёмка 31 октября | `H2`: `R1`, `EXPECTED → ON_TERMINAL`, А → А | Создать `V1` со ссылкой на `H2`. Обе необязательные ссылки пусты. | Создать `P1`: визит `V1`, собственник А, начальное событие `H2`, `service_order_id = NULL`. |
| Передача 1 ноября | `H3`: `S1`, `ON_TERMINAL → ON_TERMINAL`, А → Б | `V1` | Создать `P2`: визит `V1`, собственник Б, начальное событие `H3`, `service_order_id = S1`. |
| Резерв вывоза `D1` | `H4`: `ON_TERMINAL → RESERVED_OUT`, Б → Б | `V1` открыт | Два прежних периода |
| Фактический вывоз 30 ноября | `H5`: `D1`, `RESERVED_OUT → DEPARTED`, Б → Б | В `V1` записать `shipping_container_owner_history_id = H5`. | Всего две строки. Конец `P2` определяется по `H5`. |
| Допустимая отмена этого вывоза | `H6`: `D1`, `DEPARTED → ON_TERMINAL`, Б → Б | У `V1` очистить ссылку на `H5`. | `P2` снова открыт. Его UUID и ссылка на `H3` сохранены. |

**Проверки на отдельной тестовой БД**

| Сценарий | Ожидаемый результат |
| --- | --- |
| Пример `C1` после вывоза, до его отмены. | 5 событий истории, 1 визит, 2 периода. За ноябрь на 30 ноября — **30 дней у визита, 1 у А, 30 у Б**. При отсутствии передачи за визит была бы ровно одна строка периода. |
| В заявке 5 КТК, завершены 2. Повторить для обеих операций и обоих видов транспорта. | После приёмки — 2 новых события приёмки, 2 открытых визита, 2 первых периода. По трём ожидающим строкам есть только резерв. После вывоза двух из пяти ранее принятых КТК — 2 события выбытия, закрыты только 2 визита, новых периодов 0. |
| Вагон прибыл 10 ноября, КТК выгружен 11-го и погружен 14-го, вагон выехал 15-го. Вагон передан новому собственнику 12-го. | Вагон — 1 визит, 2 периода, **6 дней** за визит и **3 / 4** дня по собственникам. У КТК — 1 визит, 1 период, **4 дня**. Отмена вагонного выезда открывает только вагонный визит. Порожний вагон, прибывший и выехавший в тот же день, даёт 1 день и 0 визитов КТК. |
| Подтвердить будущую передачу, затем провести её. Для второй такой заявки проверить отмену до даты действия. | Снять UUID истории и периода при подтверждении. Проведение сохраняет оба UUID и не увеличивает число строк. При отмене второго назначения записи остаются для аудита, а действующего периода по отменённой передаче нет. |
| Повторить факт дважды, в том числе параллельно. Передать результат по чужому оборудованию. Затем выполнить новый заезд после закрытия предыдущего. | Дубль сохраняет время и UUID. Чужая строка не изменяется. Новый заезд получает новые UUID визита и первого периода. |
| Отменить поставку, у которой часть строк выполнена, часть зарезервирована. | У каждой принятой единицы заполнена ссылка на отмену именно её визита. У ожидавших единиц добавлены только события снятия резерва. При недопустимой отмене весь исходный набор сохраняется. |

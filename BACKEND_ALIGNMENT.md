# Бизнес-логика и устройство backend

Учёт собственников вынесен в [CONTAINER_STOCK.md](CONTAINER_STOCK.md), развёртывание и схема — в [database/README.md](database/README.md).

## Рабочая дата и время

[ApplicationClockController](backend/src/main/java/ru/billing/app/system/ApplicationClockController.java) предоставляет GET/PUT /api/application-clock. Настройка одна на БД: дата либо NULL (системный режим), версия для защиты от одновременного изменения. PUT принимает date и version; конфликт возвращает 409. Дата хранится в application_clock, диапазон лет 1–9999.

Функции billing_now() и billing_today() объединяют выбранную дату с текущим временем суток системных часов PostgreSQL в Europe/Moscow. В локальном Compose часы берутся с компьютера, на удалённом сервере — с сервера. Режим SYSTEM следует реальной дате, FIXED сохраняет день до нового выбора. Технические логи, health, Flyway и application_clock.changed_at используют реальное время.

Автоматические бизнес-даты created_at/updated_at и факты выполнения и отмены используют billing_now(). Исключение с V43 — container_owner_history.created_at: это строго возрастающий порядок записи для одного КТК, независимо от календаря. Триггер выбирает максимум реального времени UTC и предыдущего created_at плюс микросекунда; старые значения сохраняются, включая будущие. Ручное событие получает occurred_at через billing_now(), результат TOS получает время из eventDateTime; запланированная смена собственника использует дату действия по правилам ниже; по нему определяются границы хранения и время движения. Колонки timestamp без часового пояса сохраняют прежнее соглашение UTC, timestamptz — момент времени. Автоподготовка транспорта использует рабочую дату и текущее время с точностью до минуты. Введённые вручную плановые даты, сроки договоров и сохранённая история не переписываются при смене календаря. Перевод даты назад не откатывает операции; проверки последовательности приёма/вывоза продолжают действовать.

С V49 тип события истории operation_type вычисляется единственной SQL-функцией по order_type и old_status/new_status и доступен через container_owner_history_view. С V51 cancellation также вычисляется в VIEW по четырём типам отмен; физический флажок удалён, API и отметки отмен сохраняются. С V50 в физической истории также нет terminal_area_id и time_source: площадка и источник времени удалены из истории и отчёта, даты и остальные значения сохранены. Допустимые переходы, ограничения записи и проверки старой истории описаны в [CONTAINER_STOCK.md](CONTAINER_STOCK.md#тип-события-истории-ктк-v49).

Первое обращение к billing_now()/billing_today() удерживает общую транзакционную блокировку настройки, а изменение календаря — исключительную: день не меняется посреди операции, уже использующей рабочую дату. Новые автоматические бизнес-даты в коде и миграциях должны использовать эти функции, а не прямые now()/LocalDate.now(). Технический порядок истории КТК — описанное выше исключение.

Подтверждение закрепляет заезд, прежнего и нового собственников и момент действия в `service_order_container`. Для текущей и прошедшей даты приложение сразу записывает `OWNER_CHANGE`, открывает фактический период и связывает его со строкой заявки. Будущие строки ждут в `PLANNED`. Смена рабочего календаря или первый запрос к API нового рабочего дня проводит наступившие передачи в порядке их действия. Подбор для вывоза получает обновлённый регистр этим же путём. Правила подбора и расчёта дней приведены в [учёте КТК](CONTAINER_STOCK.md#смена-собственника).

Строки КТК поставки/вывоза и ЖД-накладной имеют status NULL / UPLOADED / FINISHED. Как в `TosReceivingResultAction` и `TosShipmentResultAction` из dev_back, backend принимает результат отдельного КТК и проверяет выполнение всех строк перед завершением заявки. Кнопка имитирует такие результаты по оставшимся строкам. Формат события и поведение при повторе приведены в разделе ниже. Правила и отмены — в [учёте КТК](CONTAINER_STOCK.md#статусы-строк-ктк).

## Входящие результаты TOS

`POST /datareon/event` принимает JSON через frontend или напрямую на backend. Заголовок `External-ID` необязателен. Внешний отправитель передаёт `_order` (UUID заявки), `_id` (UUID задания), `orderNumber`, `source`, `site` (имя площадки), `eventName`, `eventCode` и `eventDateTime` с часовым поясом. UUID и название площадки определяют заявку. Номер документа и название события сохраняются для сверки.

Пример автопоставки с условными идентификаторами:

```json
{
  "_order": "b2f3466a-3092-4be0-b256-bd875fc82eca",
  "_id": "eb3436bf-0a53-4c18-b27c-a651f00d5755",
  "orderNumber": "1238383", "source": "TOS", "site": "Контейнерная площадка",
  "eventName": "Выгрузка завершена", "eventCode": "UNLOAD_FINISH",
  "eventDateTime": "2026-11-23T23:55:00+03:00",
  "cargoResult": [{
    "cargoNumber": "MSCU1234566", "cargoType": "Контейнер 40", "qty": 1,
    "transportType": "АВТО", "transportNumber": "А001АА", "active": true
  }]
}
```

| Сценарий | Что определяет задание и что делает обработчик |
| --- | --- |
| `UNLOAD_FINISH`, автомобиль | `_id` указывает на `receiving_order_container.id`. Строка получает `FINISHED` и фактическое количество из первой строки результата. |
| `UNLOAD_FINISH`, ЖД | `_id` указывает на `waybill_container.id` накладной этой поставки. Завершается эта строка. |
| `LOAD_FINISH`, `ALL` | `_id` указывает на номерную строку `shipping_order_container`. Она задаёт КТК, который будет вывезен. |
| `LOAD_FINISH`, `NONE_CONTAINER` | Безномерный автовывоз. Один результат содержит один порожний КТК. По `_id` и `cargoNumber` создаётся фактическая строка. |

Известные КТК резервируются при подтверждении. Для КТК, который становится известен из пакета, обработчик под блокировкой проверяет свободный остаток, фиксирует резерв и вывоз одной транзакцией.

В подтверждённом безномерном автовывозе кнопка **«Отправить пакет TOS»** отправляет один `LOAD_FINISH` на `POST /datareon/event`. Форма показывает свободные КТК нужного типоразмера у выбранного собственника и подставляет номер автомобиля из рейса. Время вывоза можно задать по Москве. После успешного пакета карточка показывает фактический КТК и статус.

Для безномерного автовывоза (`NONE_CONTAINER`) план содержит один порожний КТК. В черновике можно изменить собственника. При подтверждении сервер требует собственника и проверяет, что у него есть свободный КТК указанного типоразмера. Конкретный номер до погрузки остаётся свободным. При внешнем `LOAD_FINISH` фактический собственник определяется по складскому остатку `cargoNumber`, даже когда в плане указан другой клиент. Оба значения доступны в заявке.

Для ЖД-вывоза доступен только режим «Заданы номера вагонов и КТК» (`ALL`). Каждый вагон содержит хотя бы один номерной КТК. Подтверждение резервирует вагоны и КТК заявки. Пакет завершает строку по `_id`. После завершения всех строк выполняется заявка. [Учёт вагонов](CONTAINER_STOCK.md#учёт-вагонов).

Каждая доставка имеет запись в `inbound_event`. Некорректная структура обязательных полей даёт HTTP 400. По умолчанию принятый пакет получает HTTP 200 с пустым телом. Форма MVP добавляет заголовок `Prefer: return=representation` и получает статус обработки и причину ошибки в JSON. Результат обработки виден в журнале: `DONE` — выполнено, `INVALID` — ошибка заявки или задания, `FAILED` — ошибка обработки, `SKIPPED` — код вне поддерживаемых. Изменения пакета и отметка `DONE` фиксируются одной транзакцией. Ошибка откатывает весь пакет. Повтор ранее выполненного задания сохраняет первую дату и складской факт. Параллельные пакеты одной заявки сериализуются блокировкой документа.

**Особенность биллинга MVP.** В `dev_back` складской статус партии меняется по завершении заявки. В MVP каждый успешный результат сразу открывает или закрывает заезд именно этого КТК. В `container_owner_history.occurred_at` события `ARRIVAL` или `DEPARTURE` записывается исходный момент TOS. День для хранения определяется по Москве. `created_at` служит для порядка записи. Таблицы `container_movement` в этой схеме нет.

Обмен охватывает результаты КТК. В `inbound_event_config` коду события назначено действие `TOS_RECEIVING_RESULT` или `TOS_SHIPMENT_RESULT`. Журнал сохраняет выбранное действие. Публикация исходящих заданий, складские события WMS, замена предварительно выбранного случайного КТК и перенос количеств дополнительных услуг в строки заказанных услуг относятся к моделям основной системы. Для проверки без внешней шины пакеты отправляются непосредственно на endpoint. См. [интеграционный сценарий](scripts/tos-results.cjs).

## Документы и хранение

| Документ / данные | Таблицы / назначение |
| --- | --- |
| Комплексная заявка | comprehensive_service_order; клиент, договор, workflow |
| Заявка на смену собственника КТК | service_order, service_order_container; service=CHANGE_OWNER |
| Поставка | receiving_order; для авто — receiving_order_container и items; ЖД-состав — связанные накладные |
| Вывоз | shipping_order, shipping_order_container, items и связи с исходными КТК/вагонами |
| Рейс | route; объединяет транспортные заявки |
| Заезд КТК | `container_visit` связывает КТК с событиями приёмки, вывоза и отмены приёмки. Заявка каждой операции определяется по `order_id` события. |
| Владение и хранение КТК | container_period; границы связаны с историей, совместимый VIEW container_storage_period |
| Текущее складское состояние | container_owner с client_id, receiving_order_id (текущая поставка) и shipping_order_id (вывоз) |
| Накладная | waybill, waybill_railway_carriage, waybill_container, waybill_product, waybill_zpu |

comprehensive_service_order и service_order — разные документы. UUID используются для связей; номера — для отображения. У поставок и вывозов общий transport_order_number_seq, у комплексных заявок — comprehensive_service_order_number_seq, у рейсов — route_code_seq. Последовательности могут иметь пропуски; текущие значения не являются константами проекта.

## Создание комплексной заявки

Обязательны клиент, принадлежащий ему договор, собственник КТК по умолчанию и совместимые свободные накладные. Накладные отбираются по станции отправления, станции назначения и плательщику.

Одна транзакция создаёт:

1. ЖД-поставку с ролью INITIAL_RECEIVING и привязывает её накладные.
2. Комплексную заявку.
3. Отдельный автовывоз на каждый уникальный КТК STANDARD_20 или STANDARD_40.

Индивидуальные собственники из containerOwners применяются к исходной поставке в этой же транзакции. Переход между шагами мастера не записывает их в БД. Возвраты при создании заявки не создаются. По умолчанию возврат каждого КТК требуется; исключения задаются действием «Возврат не нужен» после создания вывоза.

Для нераспределённых КТК, включая замену отменённого вывоза, доступен ручной выбор одного КТК40 либо одного или двух КТК20 в автовывоз. Повторное активное распределение одного исходного КТК запрещено.

Код: [ComprehensiveServiceOrderService](backend/src/main/java/ru/billing/app/comprehensiveserviceorder/ComprehensiveServiceOrderService.java), [планирование состава](backend/src/main/java/ru/billing/app/comprehensiveserviceorder/ComprehensiveServiceOrderCargoPlanner.java).

## Возврат

Действие «Создать возврат» доступно из комплексной заявки и связанного вывоза. Текущий UI использует массовый endpoint заявки: на каждый выбранный КТК создаётся отдельная порожняя автопоставка RETURN_RECEIVING. Нельзя создать второй активный возврат одного КТК из одного вывоза. После отмены возврата доступно новое оформление; исходная отменённая поставка сохраняется в истории.

- Та же пара клиент/договор: возврат принадлежит исходной комплексной заявке.
- Другая пара: выбранный набор в рамках одного массового запроса относится к одной новой заявке на возврат с типом AUTO_RETURN со ссылкой source_service_order_id.
- Выполнить возврат можно только после выполнения исходного вывоза.
- КТК с отметкой «Возврат не нужен» исключаются из выбора возврата; оба endpoint создания возврата отклоняют такие КТК.
- UI предлагает либо флажок «Использовать текущего клиента и договор», либо другого клиента с договором. Флажок изначально выключен.
- Backend также различает вариант «тот же клиент, другой договор», хотя форма отдельно его не предлагает.
- Правила собственника возврата — в [учёте КТК](CONTAINER_STOCK.md).

Низкоуровневый endpoint возврата по вывозу принимает список КТК в одну поставку. Это отличается от массового endpoint, который используется текущим UI и создаёт по одной поставке на КТК. Не приписывать обоим endpoint одинаковую группировку.

Код: [ReturnReceivingService](backend/src/main/java/ru/billing/app/comprehensiveserviceorder/ReturnReceivingService.java), [ServiceReturnsController](backend/src/main/java/ru/billing/app/comprehensiveserviceorder/ServiceReturnsController.java), [ReturnReceivingController](backend/src/main/java/ru/billing/app/comprehensiveserviceorder/ReturnReceivingController.java).

## Статусы и выполнение

Транспортные заявки: DRAFT → CONFIRMED → COMPLETED; из каждого состояния разрешена отмена в CANCELLED при выполнении проверок остатков и зависимостей.

Подтверждение выполняется **через рейс**. Нужна хотя бы одна связанная заявка; все заявки должны быть черновиками. Проверяются дата/время, отправитель у поставки или получатель у вывоза. Реквизиты логистики проверяются при создании/редактировании рейса. Пакет подтверждается транзакционно. Складское резервирование выполняется в той же операции.

Подтверждение поставки фиксирует ожидание в container_owner.receiving_order_id, без создания container_visit или container_period. При `FINISHED` строки КТК событие `ARRIVAL` открывает заезд и первый период хранения. Завершённая строка вывоза даёт событие `DEPARTURE`, которое закрывает этот же заезд. Строки проверяются по заявке события и КТК. После отмены ЖД-поставки освобождённую накладную можно использовать в следующей поставке, а событие исходной приёмки сохраняет ссылку на исходную заявку.

После подтверждения оператор выполняет заявки. В одной транзакции фиксируются складское событие и обновление статусов. Рейс завершается после выполнения всех неотменённых заявок; если отменены все, получает CANCELLED.

Комплексная ЖД-заявка завершается после выполнения собственных активных поставок/вывозов, распределения всех исходных КТК и выполнения возврата каждого КТК, которому он требуется, включая возвраты в другой комплексной заявке. КТК с отметкой «Возврат не нужен» завершает свой цикл выполнением автовывоза; заявка может завершиться вообще без возвратных поставок. AUTO_RETURN завершается после выполнения своих возвратных поставок. Самостоятельное ручное изменение статуса комплексной заявки запрещено.

Массовые действия транспортной вкладки заявки:

- Подготовка заполняет текущие дату/время, недостающие сведения о контрагентах и создаёт недостающие рейсы.
- Действие статуса сначала подтверждает рейсы; следующее нажатие выполняет заявки. Оба этапа не объединяются в одно нажатие.

В transportOrders ответа заявки передаются краткие сведения только о её собственных транспортных заявках. Счётчики возвратов также показывают собственные возвраты; returnMissing считает КТК, которым возврат требуется, но ещё не оформлен, включая проверку возвратов другой заявки. КТК с отметкой «Возврат не нужен» в этот счётчик не входят. Его нельзя заменять разностью общего количества КТК и собственных возвратов.

Код: [OrderStatusService](backend/src/main/java/ru/billing/app/order/OrderStatusService.java), [RouteService](backend/src/main/java/ru/billing/app/route/RouteService.java), [ServiceSectionCompletion](backend/src/main/java/ru/billing/app/comprehensiveserviceorder/ServiceSectionCompletion.java).

## Отмена и связанные документы

В карточках транспортных заявок и рейсов доступна отмена без причины. API: POST /api/receiving-orders/{id}/cancellation, /api/shipping-orders/{id}/cancellation, /api/routes/{id}/cancellation; тело — только expectedStatus. GET отмены удалён. Статус CANCELLED сохраняется в самом документе; отдельного архива причины и состава нет. Складские переходы и история — в [CONTAINER_STOCK.md](CONTAINER_STOCK.md).

Документы комплексной заявки отменяются в обратном порядке: возвраты → вывозы → первоначальная поставка. Даже черновой зависимый документ нужно отменить явно. Отмена не создаёт каскад по разным рейсам и комплексным заявкам. Отмена всего рейса явно включает все его заявки и откатывается целиком при конфликте.

Отменённые транспортные заявки видны в карточке заявки, но исключаются из активного распределения, счётчиков возврата и массового выполнения. Можно создать замену вывоза или возврата. Выполненная комплексная заявка при отмене возврата становится CONFIRMED; когда отменены все её собственные транспортные заявки — CANCELLED. Возврат другой заявки обновляет также исходную ЖД-заявку. Прямое произвольное изменение статуса заявки по-прежнему запрещено.

Реализация разделена: OrderCancellationService управляет документами, ContainerStockPolicy задаёт чистые правила состояний, ContainerStockService изменяет регистр, RouteCancellationService выполняет пакет рейса. С V58 таблицы order_cancellation, container_movement и outbound_data удалены; события и обратные складские переходы сохраняются в container_owner_history. С V43 таблица container_stock_reservation удалена: прежний собственник и предыдущая неотменённая заявка восстанавливаются по container_owner_history, без новых колонок. Проверки полноты истории, состава, статусов, последовательности, транзакции и блокировки сохранены; алгоритм описан в CONTAINER_STOCK.md.

## КТК без возврата

Для комплексной заявки с workflow=RAILWAY_RETURN в разделе автовывозов доступно действие «Возврат не нужен». Выбираются отдельные КТК активных автовывозов без оформленных возвратов, в том числе один КТК из двух в одной заявке. Отметка хранится в shipping_order_container.return_required=false (V32) и относится к конкретному вывозу. Новые строки по умолчанию требуют возврат. Выбор не меняет складские состояния и собственников.

GET /api/comprehensive-service-orders/{id}/no-return/available-containers возвращает доступные КТК с номером/статусом вывоза и текущим признаком. POST /api/comprehensive-service-orders/{id}/no-return принимает containerIds и сохраняет отметку для выбранных строк одним пакетом. Повторный запрос не создаёт дублей. Снятие сохранённой отметки этим действием не предусмотрено. КТК с активным возвратом, чужие КТК и отменённые вывозы отклоняются; ошибка откатывает весь пакет. После отмены возврата выбор снова возможен. Создание возврата и выбор «Возврат не нужен» используют блокировку исходной заявки и не могут успешно выполниться одновременно для одного КТК.


Сохранённый выбор виден по отмеченным флажкам в форме «Возврат не нужен»; в столбце номера КТК дополнительных подписей нет. Отмеченные КТК исключены из доступных возвратов, returnMissing и ожидания возврата при завершении заявки. После отмены вывоза его история сохраняет отметку, активное распределение освобождается. Вывоз-замена требует возврат по умолчанию; при необходимости его КТК выбираются заново.

Код: [ServiceNoReturnService](backend/src/main/java/ru/billing/app/comprehensiveserviceorder/ServiceNoReturnService.java), [ServiceCompletion](backend/src/main/java/ru/billing/app/comprehensiveserviceorder/ServiceCompletion.java).

## Состав, накладные и массы

Поставка использует номерной состав. ЖД-вывоз использует `ALL`, автовывоз поддерживает `ALL` и `NONE_CONTAINER`. Комплексная заявка формирует номерные связанные заявки по своему источнику.

Редактор размещения КТК (`/api/waybills/placement`) выбирает несколько свободных накладных или накладных поставок в DRAFT. После подтверждения поставки изменения запрещены. API и интерфейс группируют состав по физическому вагону без дублей: на одной карточке показаны все его КТК из выбранных накладных, каждый со своим номером накладной. Связи разных накладных с одним вагоном в БД остаются отдельными. Схема, проверка вместимости, поиск повторного КТК и версия редактирования учитывают только выбранные накладные. Для одного физического вагона длина суммируется по всем выбранным накладным. Существующие накладные с несколькими КТК тоже поддерживаются. При переносе и обмене КТК сохраняет исходную накладную, меняется только физический вагон. API принимает wagonId; необязательный waybillId должен совпадать с исходной накладной строки, попытка смены отклоняется с WAYBILL_IDENTITY_CHANGED. Сохранение сначала определяет итоговые пары «накладная + вагон» для всех выбранных КТК и резервирует необходимые существующие связи. При полном переносе связи, если готовой целевой пары ещё нет, изменяется waybill_railway_carriage.railway_carriage_id; идентификатор записи, waybill_id и ссылки её КТК сохраняются. Если часть КТК остаётся на исходном вагоне, исходная связь сохраняется, а переносимым КТК назначается существующая или новая запись этой же накладной для целевого вагона через waybill_container.waybill_railway_carriage_id. Один физический вагон может одновременно присутствовать в разных накладных: это отдельные записи с одинаковым railway_carriage_id и разными waybill_id. Новые таблицы и миграции не требуются. Накладные и атрибуты остальных КТК не меняются. Грузы, массы, собственники, ЗПУ и связь накладной с поставкой сохраняются. Состав каждой накладной по КТК остаётся прежним; обновляется распределение по вагонам. Освободившиеся при переносе связи выбранной накладной с вагоном удаляются; существовавшие изначально пустые связи сохраняются. Генератор продолжает создавать прежний состав документов.

Сохранение всего размещения атомарно. Проверяются полный набор выбранных строк, отсутствие повторного физического КТК, суммарная длина КТК относительно длины платформы (STANDARD_20 = 20 футов, STANDARD_40 = 40 футов). Число мест и грузоподъёмность не ограничивают размещение: на платформе 80 футов допустимы 4×20, 2×40 или 40+20+20. КТК невыбранных накладных не загружаются в схему, не занимают в ней места и не блокируют сохранение независимо от статуса их поставки. Изменения невыбранных накладных не делают версию выбранной схемы устаревшей; их строки не изменяются. Неизвестная длина платформы или тип КТК блокирует сохранение, поскольку футовость нельзя проверить. API предварительного просмотра поддерживает добавление вагона из справочника, в том числе пустого; упрощённая форма показывает вагоны выбранных накладных и не предлагает отдельного добавления. Список выбора передаёт количество уникальных вагонов и количество КТК без номеров состава. Накладные без КТК также доступны для выбора и открытия, включая накладные без вагонов. Существовавшие до сохранения пустые связи накладной с вагоном сохраняются; удаляются только освободившиеся в результате переноса связи, на которых ранее были КТК. Перенос на вагон пустой накладной сохраняет исходную накладную КТК.

Версия схемы и блокировки защищают от сохранения устаревшего размещения и изменения после подтверждения поставки. Успешные перемещения фиксирует waybill_container_relocation (V30–V31): пакет, исходная waybill_id и целевая to_waybill_id накладные, строка и физический КТК, прежний/новый вагон, время. V31 заполняет целевую накладную прежних записей исходной и разрешает перенос между накладными при неизменном физическом вагоне. В новых перемещениях исходная и целевая накладные одинаковы; прежние записи смены накладной сохраняются как история. Перенос между КТК внутри одного физического вагона ничего не меняет. Неизменившиеся строки не создают запись аудита. Складские состояния и резервы редактор не меняет. Проверки с изменением данных: scripts/waybill-placement-check.cjs и scripts/waybill-placement-ui.cjs, только в отдельной billing_wagon_test на портах 8194/3194; браузерный сценарий использует фикстуры первого и проверяет реальное перетаскивание/обмен между вагонами с сохранением исходных накладных в БД. Проверки API также покрывают изменение railway_carriage_id с сохранением идентификаторов связей, частичный обмен с сохранением неподвижных КТК, обратное объединение связей, запрет смены накладной, область выбранных накладных и аудит. Сценарии пустых накладных проверяют выбор документа с нулём КТК, открытие с пустым вагоном и без вагонов, перенос на пустой вагон с сохранением исходной накладной КТК и существовавшей пустой связи. scripts/waybill-placement-length-check.cjs и scripts/waybill-placement-length-ui.cjs проверяют исходные шесть КТК, уменьшение до пяти/четырёх, рост карточек, четыре вагона в ряд и сохранение 4×20 на 80-футовой платформе независимо от массы.

В накладной обязателен хотя бы один груз, даже при порожнем КТК. Несколько грузов допустимы только при ровно одном КТК; для каждого груза тогда нужна масса. Массы хранятся в кг с точностью до 0,001. container.weight — тара, waybill_container.weight — брутто, net_weight — сохранённое нетто. При отсутствии явного нетто оно фиксируется при создании по текущей таре. Изменение справочной тары впоследствии не пересчитывает сохранённое нетто. В item-таблицах сохранено историческое имя wight_net.

Исходный owner накладной — текст. Выбранный клиент-собственник заявки хранится отдельно. В грузе накладной выбирается danger_product_id, показывается danger_product.name; класс получается через danger_product.danger_class_id. В строках поставки/вывоза используется прямая ссылка на danger_class. Тип ЗПУ — ссылка seal_type, номера сохраняются строками с ведущими нулями.

Код: [WaybillValidator](backend/src/main/java/ru/billing/app/waybill/WaybillValidator.java), [WaybillStore](backend/src/main/java/ru/billing/app/waybill/WaybillStore.java), [WaybillReferenceValidator](backend/src/main/java/ru/billing/app/waybill/WaybillReferenceValidator.java). Генератор — [отдельное описание](docs/equipment-number-formats.md).

Реализация редактора: [WaybillPlacementService](backend/src/main/java/ru/billing/app/waybill/WaybillPlacementService.java), [WaybillPlacementPolicy](backend/src/main/java/ru/billing/app/waybill/WaybillPlacementPolicy.java), [WaybillPlacementController](backend/src/main/java/ru/billing/app/waybill/WaybillPlacementController.java).

## Реквизиты и ограничения модели

Грузоотправитель и грузополучатель выбираются из справочника client, произвольное имя отклоняется. receiving_order.consignor хранится строкой; shipping_order.consignee_id остаётся ссылкой на client_related_entity. Служебное представление клиента создаёт PartyReferences; оно скрыто из справочника перевозчиков.

Плановые даты поставки/вывоза передаются как LocalDateTime. Не преобразовывать их повторно как UTC timestamp. Поле contract.valid_from может быть NULL; неизвестную дату показывать прочерком. V28 заполнила существовавшие договоры датой 01.01.2026 по отдельному решению, но не назначает её всем новым договорам.

Метаданные черновых вывозов и возвратов заявки редактируются пакетно через transport-metadata с проверкой принадлежности и исходных значений. Конфликт откатывает пакет. Начальная поставка редактируется через собственную карточку.

Особенности MVP, которые нельзя принимать за полную модель основной системы:

- etsng_code.code может содержать код вместе с подписью; чтение разделяет строку. Для внешнего обмена это потребовало бы отдельного согласования контракта.
- Для ручной порожней строки класс опасности не подставляется автоматически только из признака empty. Проверки и нормализацию основной системы не считать уже реализованными.
- Роли и полномочия пользователей, внешние интеграции, банковский обмен и полный производственный жизненный цикл не реализованы.

Каждый фактический период относится к одному заезду и одному собственнику. Начало определяется по `occurred_at` события `ARRIVAL` или `OWNER_CHANGE`, конец — по следующей фактической передаче либо вывозу этого заезда. День передачи относится к новому собственнику, день вывоза входит в хранение. Отмена поставки исключает заезд из активного отчёта, отмена вывоза снова открывает его последний период. Отчёт показывает дни по заезду и по каждому периоду собственника. [Правила отчёта](CONTAINER_STOCK.md#текущий-отчёт)

## Карта API

Поставки и вывозы используют общий [OrderRowMapper](backend/src/main/java/ru/billing/app/order/OrderRowMapper.java) для чтения реквизитов списка, КТК и площадки. SQL-запросы, состав документов и правила записи остаются в соответствующих ReceivingOrderStore и ShippingOrderStore; поставка возвращает fillingType=ALL, вывоз сохраняет прочитанное значение с прежним значением ALL при NULL.

Базовый путь — /api. Точные DTO и методы определяются контроллерами и request-классами, а не историческими примерами запросов.

| Ресурс | Назначение |
| --- | --- |
| /receiving-orders, /shipping-orders | Транспортные заявки, состав и метаданные |
| /comprehensive-service-orders | Комплексные заявки, транспортные действия, возвраты и прогресс |
| /routes | Рейсы и подтверждение |
| /container-owners, /service-orders | Регистр и смена собственника |
| /container-storage-periods | Отчёт периодов по точным событиям границ с реквизитами исходной поставки и конечного вывоза; /export — CSV с теми же 17 колонками |
| /waybills | Накладные, выбор, группировка, генерация |
| /references, /transport-catalogs | Справочные данные |

Сверять маршруты с [контроллерами backend](backend/src/main/java/ru/billing/app) и [frontend API](frontend/src/api.ts). Меняющие данные сценарии проверять на отдельной тестовой БД.

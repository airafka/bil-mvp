Основная бизнес-логика сверена с кодом 10.11.2026; раздел редактора накладных повторно сверен 16.11.2026, правила начисления без возврата добавлены и проверены 16.11.2026. Документ описывает MVP; полное соответствие основной системе не заявляется. Учёт собственников вынесен в [CONTAINER_STOCK.md](CONTAINER_STOCK.md), развёртывание и схема — в [database/README.md](database/README.md).

## Рабочая дата и время

[ApplicationClockController](backend/src/main/java/ru/billing/app/system/ApplicationClockController.java) предоставляет GET/PUT /api/application-clock. Настройка одна на БД: дата либо NULL (системный режим), версия для защиты от одновременного изменения. PUT принимает date и version; конфликт возвращает 409. Дата хранится в application_clock, диапазон лет 1–9999.

Функции billing_now() и billing_today() объединяют выбранную дату с текущим временем суток системных часов PostgreSQL в Europe/Moscow. В локальном Compose часы берутся с компьютера, на удалённом сервере — с сервера. Режим SYSTEM следует реальной дате, FIXED сохраняет день до нового выбора. Технические логи, health, Flyway и application_clock.changed_at используют реальное время.

Автоматические бизнес-даты created_at/updated_at и факты выполнения, отмены, фиксации тарифов, начисления и оплаты используют billing_now(). Исключение с V43 — container_owner_history.created_at: это строго возрастающий порядок записи для одного КТК, независимо от календаря. Триггер выбирает максимум реального времени UTC и предыдущего created_at плюс микросекунда; старые значения сохраняются, включая будущие. Бизнес-время обычного события записывается в существующее occurred_at через billing_now(); запланированная смена собственника использует дату действия по правилам ниже; по нему определяются границы хранения и время движения. Колонки timestamp без часового пояса сохраняют прежнее соглашение UTC, timestamptz — момент времени. Автоподготовка транспорта использует рабочую дату и текущее время с точностью до минуты. Введённые вручную плановые даты, сроки договоров и сохранённая история не переписываются при смене календаря. Перевод даты назад не откатывает операции; проверки последовательности приёма/вывоза продолжают действовать.

С V49 тип события истории operation_type вычисляется единственной SQL-функцией по order_type и old_status/new_status и доступен через container_owner_history_view. С V51 cancellation также вычисляется в VIEW по четырём типам отмен; физический флажок удалён, API и отметки отмен сохраняются. С V50 в физической истории также нет terminal_area_id и time_source: площадка и источник времени удалены из истории и отчёта, даты и остальные значения сохранены. Допустимые переходы, ограничения записи и проверки старой истории описаны в [CONTAINER_STOCK.md](CONTAINER_STOCK.md#тип-события-истории-ктк-v49).

Первое обращение к billing_now()/billing_today() удерживает общую транзакционную блокировку настройки, а изменение календаря — исключительную: день не меняется посреди операции, уже использующей рабочую дату. Новые автоматические бизнес-даты в коде и миграциях должны использовать эти функции, а не прямые now()/LocalDate.now(). Технический порядок истории КТК — описанное выше исключение.

С V54 запланированная смена собственника использует effective_date заявки: наступление определяется по billing_today(), occurred_at — по дате передачи, а не по дню запоздалого запуска обработчика. При подтверждении на текущий день граница не раньше времени подтверждения, сохранённого в updated_at. Подтверждение переводит заявку в SCHEDULED; история и периоды меняются только при выполнении. Схема, повторные запуски, ошибки и ограничения описаны в [CONTAINER_STOCK.md](CONTAINER_STOCK.md#смена-собственника).

Строки КТК поставки/вывоза и ЖД-накладной имеют status NULL / UPLOADED / FINISHED. Действия подтверждения и выполнения пока применяются ко всем строкам заявки; фактический период ссылается на конкретную выполненную строку. Правила и отмены — в [учёте КТК](CONTAINER_STOCK.md#статусы-строк-ктк).

## Каталог услуг

Состав рабочей БД проверен 10.11.2026:

| Услуга | workflow | Применение |

| Комплексная услуга по приему контейнера в составе поезда | RAILWAY_RETURN | Первоначальная ЖД-поставка, автовывоз, возврат |
| Комплексная услуга по приему контейнера при повагонной отправке | RAILWAY_RETURN | Тот же набор этапов, отдельно выбранная каталожная услуга и тариф |

## Создание комплексной услуги

Обязательны клиент, принадлежащий ему договор, выбранная ЖД-услуга, собственник КТК по умолчанию и совместимые свободные накладные. Накладные отбираются по станции отправления, станции назначения и плательщику. Нужен ровно один активный тариф выбранной услуги для клиента и договора.

Одна транзакция создаёт:

1. ЖД-поставку с ролью INITIAL_RECEIVING и привязывает её накладные.
2. Комплексную заявку и снимок тарифа.
3. Отдельный автовывоз на каждый уникальный КТК STANDARD_20 или STANDARD_40.

Индивидуальные собственники из containerOwners применяются к исходной поставке в этой же транзакции. Переход между шагами мастера не записывает их в БД. Возвраты при создании услуги не создаются. По умолчанию возврат каждого КТК требуется; исключения задаются действием «Возврат не нужен» после создания вывоза.

Для нераспределённых КТК, включая замену отменённого вывоза, доступен ручной выбор одного КТК40 либо одного или двух КТК20 в автовывоз. Повторное активное распределение одного исходного КТК запрещено.

Код: [ComprehensiveServiceOrderService](backend/src/main/java/ru/billing/app/comprehensiveserviceorder/ComprehensiveServiceOrderService.java), [планирование состава](backend/src/main/java/ru/billing/app/comprehensiveserviceorder/ComprehensiveServiceOrderCargoPlanner.java).

## Возврат

Действие «Создать возврат» доступно из услуги и связанного вывоза. Текущий UI использует массовый endpoint услуги: на каждый выбранный КТК создаётся отдельная порожняя автопоставка RETURN_RECEIVING. Нельзя создать второй активный возврат одного КТК из одного вывоза. После отмены возврата доступно новое оформление; исходная отменённая поставка сохраняется в истории.

- Та же пара клиент/договор: возврат принадлежит исходной услуге.
- Другая пара: выбранный набор в рамках одного массового запроса относится к одной новой AUTO_RETURN-услуге со ссылкой source_service_order_id. Для неё требуется активный тариф.
- Выполнить возврат можно только после выполнения исходного вывоза.
- КТК с отметкой «Возврат не нужен» исключаются из выбора возврата; оба endpoint создания возврата отклоняют такие КТК.
- UI предлагает либо флажок «Использовать текущего клиента и договор», либо другого клиента с доступным тарифом автоуслуги. Флажок изначально выключен.
- Backend также различает вариант «тот же клиент, другой договор», хотя форма отдельно его не предлагает.
- Правила собственника возврата — в [учёте КТК](CONTAINER_STOCK.md).

Низкоуровневый endpoint возврата по вывозу принимает список КТК в одну поставку. Это отличается от массового endpoint, который используется текущим UI и создаёт по одной поставке на КТК. Не приписывать обоим endpoint одинаковую группировку.

Код: [ReturnReceivingService](backend/src/main/java/ru/billing/app/comprehensiveserviceorder/ReturnReceivingService.java), [ServiceReturnsController](backend/src/main/java/ru/billing/app/comprehensiveserviceorder/ServiceReturnsController.java), [ReturnReceivingController](backend/src/main/java/ru/billing/app/comprehensiveserviceorder/ReturnReceivingController.java).

## Статусы и выполнение

Транспортные заявки: DRAFT → CONFIRMED → COMPLETED; из каждого состояния разрешена отмена в CANCELLED при выполнении проверок остатков и зависимостей.

Подтверждение выполняется **через рейс**. Нужна хотя бы одна связанная заявка; все заявки должны быть черновиками. Проверяются дата/время, отправитель у поставки или получатель у вывоза. Реквизиты логистики проверяются при создании/редактировании рейса. Пакет подтверждается транзакционно. Складское резервирование выполняется в той же операции.

После подтверждения оператор выполняет заявки. В одной транзакции фиксируются складское событие, начисление при возврате и обновление статусов. Рейс завершается после выполнения всех неотменённых заявок; если отменены все, получает CANCELLED.

ЖД-услуга завершается после выполнения собственных активных поставок/вывозов, распределения всех исходных КТК и выполнения возврата каждого КТК, которому он требуется, включая возвраты в другой услуге. КТК с отметкой «Возврат не нужен» завершает свой цикл выполнением автовывоза; услуга может завершиться вообще без возвратных поставок. AUTO_RETURN завершается после выполнения своих возвратных поставок. Самостоятельное ручное изменение статуса комплексной услуги запрещено.

Массовые действия транспортной вкладки услуги:

- Подготовка заполняет текущие дату/время, недостающие сведения о контрагентах и создаёт недостающие рейсы.
- Действие статуса сначала подтверждает рейсы; следующее нажатие выполняет заявки. Оба этапа не объединяются в одно нажатие.

В transportOrders ответа услуги передаются краткие сведения только о её собственных транспортных заявках. Счётчики возвратов также показывают собственные возвраты; returnMissing считает КТК, которым возврат требуется, но ещё не оформлен, включая проверку возвратов другой услуги. КТК с отметкой «Возврат не нужен» в этот счётчик не входят. Его нельзя заменять разностью общего количества КТК и собственных возвратов.

Код: [OrderStatusService](backend/src/main/java/ru/billing/app/order/OrderStatusService.java), [RouteService](backend/src/main/java/ru/billing/app/route/RouteService.java), [ServiceSectionCompletion](backend/src/main/java/ru/billing/app/comprehensiveserviceorder/ServiceSectionCompletion.java).

## Отмена и связанные документы

В карточках транспортных заявок и рейсов доступна отмена с обязательной причиной. API: POST /api/receiving-orders/{id}/cancellation, /api/shipping-orders/{id}/cancellation, /api/routes/{id}/cancellation; тело — expectedStatus и reason. GET по тому же адресу возвращает причину, время и исходный статус явно выполненной отмены. Автоматически отменённый из-за отсутствия активных заявок рейс может не иметь отдельной записи причины. Складские переходы и история — в [CONTAINER_STOCK.md](CONTAINER_STOCK.md).

Документы услуги отменяются в обратном порядке: возвраты → вывозы → первоначальная поставка. Даже черновой зависимый документ нужно отменить явно. Отмена не создаёт каскад по разным рейсам и услугам. Отмена всего рейса явно включает все его заявки и откатывается целиком при конфликте.

Отменённые транспортные заявки видны в карточке услуги, но исключаются из активного распределения, счётчиков возврата и массового выполнения. Можно создать замену вывоза или возврата. Выполненная услуга при отмене возврата становится CONFIRMED; когда отменены все её собственные транспортные заявки — CANCELLED. Возврат другой услуги обновляет также исходную ЖД-услугу. Прямое произвольное изменение статуса услуги по-прежнему запрещено.

При отмене выполненного возврата свободные начисления и исполнения обеих затронутых услуг, созданные этим возвратом, снимаются с активного учёта. При отмене выполненного автовывоза аналогично снимаются его начисления по КТК без возврата; начисления других документов сохраняются. Их полный снимок, включая тариф и суммы, сохраняется в order_cancellation.billing_snapshot. После нового возврата начисление создаётся заново. Перед отменой строки начислений блокируются в том же порядке, что при включении в счёт.

Если хотя бы одно начисление находится в любом счёте, отмена блокируется с номерами счетов; изменения склада, документов и истории откатываются. Из чернового счёта начисление можно предварительно исключить или удалить сам черновой счёт. Оплаченные счета не изменяются. Автоматических корректировочных счетов и отмены оплаты нет.

Реализация разделена: OrderCancellationService управляет документами, ContainerStockPolicy задаёт чистые правила состояний, ContainerStockService изменяет регистр, BillingCancellationService проверяет счета и снимает начисления, RouteCancellationService выполняет пакет рейса. order_cancellation сохраняет аудит отмены. С V43 таблица container_stock_reservation удалена: прежний собственник и предыдущая неотменённая заявка восстанавливаются по container_owner_history, без новых колонок. Проверки полноты истории, состава, статусов, последовательности, счетов, транзакции и блокировки сохранены; алгоритм описан в CONTAINER_STOCK.md.

## Тарифы, начисления и счета

При создании услуги в comprehensive_service_order_tariff сохраняются базовые цены с НДС/без НДС, коэффициент и итоговые цены, округлённые до двух знаков. Последующее изменение каталога или тарифа не меняет этот снимок.

Начальная ЖД-поставка фиксирует факт приёмки, но не начисляет стоимость. Автовывоз проверяет выполнение исходной поставки и начисляет стоимость только по своим КТК с отметкой «Возврат не нужен». Для остальных КТК при выполнении возврата:

- создаётся исполнение и начисление исходной ЖД-услуги на возвращённый КТК;
- если возврат принадлежит отдельной AUTO_RETURN-услуге, создаётся также её собственное исполнение и начисление на этот КТК.

Это две разные услуги с отдельными тарифами и плательщиками. Старое разделение на начисления «А/Б» внутри прежнего алгоритма не применяется. Количество в начислении — 1 КТК, валюта — RUB. Уникальность по паре услуга/КТК и по исполнению защищает от дублей при повторном выполнении.

Счёт формируется из выбранных свободных начислений одного клиента, договора и календарного месяца. Часовой пояс расчётного периода по умолчанию Europe/Moscow. Одно начисление нельзя включить в два счёта. Названия и суммы строк сохраняются снимком.

Создание счёта защищено requestKey от повторной отправки; повтор ключа с другим составом отклоняется. Изменение и отметка оплаты используют version для обнаружения конфликта. Удаление блокирует счёт и проверяет его статус, но не принимает version. Состояния счёта — DRAFT и PAID; оплаченный счёт нельзя редактировать или удалить. Отметка оплаты локальная.

Код: [ServiceTariffSnapshot](backend/src/main/java/ru/billing/app/comprehensiveserviceorder/ServiceTariffSnapshot.java), [BillingService](backend/src/main/java/ru/billing/app/billing/BillingService.java), [PaymentInvoiceService](backend/src/main/java/ru/billing/app/billing/PaymentInvoiceService.java).

## КТК без возврата

Для обеих услуг с workflow=RAILWAY_RETURN в разделе автовывозов доступно действие «Возврат не нужен». Выбираются отдельные КТК активных автовывозов без оформленных возвратов, в том числе один КТК из двух в одной заявке. Отметка хранится в shipping_order_container.return_required=false (V32) и относится к конкретному вывозу. Новые строки по умолчанию требуют возврат. Выбор не меняет складские состояния и собственников.

GET /api/comprehensive-service-orders/{id}/no-return/available-containers возвращает доступные КТК с номером/статусом вывоза и текущим признаком. POST /api/comprehensive-service-orders/{id}/no-return принимает containerIds и сохраняет отметку для выбранных строк одним пакетом. Повторный запрос не создаёт дублей. Снятие сохранённой отметки этим действием не предусмотрено. КТК с активным возвратом, чужие КТК и отменённые вывозы отклоняются; ошибка откатывает весь пакет. После отмены возврата выбор снова возможен. Создание возврата и выбор «Возврат не нужен» используют блокировку исходной услуги и не могут успешно выполниться одновременно для одного КТК.

Если вывоз ещё не выполнен, начисление возникает при его выполнении. Если он уже выполнен, начисление создаётся сразу при сохранении выбора, с текущими датой/временем оказания, без заднего числа. Используется неизменяемый снимок тарифа услуги. У такого service_execution указан shipping_order_id, а receiving_order_id=NULL; V32 разрешает отсутствие возвратной поставки. Уникальность по услуге/КТК и по исполнению сохраняется.

Сохранённый выбор виден по отмеченным флажкам в форме «Возврат не нужен»; в столбце номера КТК дополнительных подписей нет. Отмеченные КТК исключены из доступных возвратов, returnMissing и ожидания возврата при завершении услуги. После отмены вывоза его история сохраняет отметку, начисление снимается с аудитом и проверкой счетов, активное распределение освобождается. Вывоз-замена требует возврат по умолчанию; при необходимости его КТК выбираются заново.

Код: [ServiceNoReturnService](backend/src/main/java/ru/billing/app/comprehensiveserviceorder/ServiceNoReturnService.java), [ServiceCompletion](backend/src/main/java/ru/billing/app/comprehensiveserviceorder/ServiceCompletion.java). Проверки: scripts/no-return-check.cjs и scripts/no-return-ui.cjs, только billing_no_return_test, backend billing-next-no-return-test на 8195, frontend на 3195. Браузерный сценарий использует фикстуру первого; повторный запуск требует новой фикстуры. Проверяются оба тарифа, смешанный состав, поздний выбор, защита от дублей/одновременного возврата, отмена и счета, замена вывоза, выбор и ошибки формы.

## Состав, накладные и массы

Только номерные вагоны и КТК, fillingType=ALL. Безномерные и количественные режимы отклоняются. КП-ЖД получает состав из накладных; КП-Авто — из строк поставки. Состав связанных заявок меняется через источник.

Редактор размещения КТК (`/api/waybills/placement`) выбирает несколько свободных накладных или накладных поставок в DRAFT. После подтверждения поставки изменения запрещены. API и интерфейс группируют состав по физическому вагону без дублей: на одной карточке показаны все его КТК из выбранных накладных, каждый со своим номером накладной. Связи разных накладных с одним вагоном в БД остаются отдельными. Схема, проверка вместимости, поиск повторного КТК и версия редактирования учитывают только выбранные накладные. Для одного физического вагона длина суммируется по всем выбранным накладным. Существующие накладные с несколькими КТК тоже поддерживаются. При переносе и обмене КТК сохраняет исходную накладную, меняется только физический вагон. API принимает wagonId; необязательный waybillId должен совпадать с исходной накладной строки, попытка смены отклоняется с WAYBILL_IDENTITY_CHANGED. Сохранение сначала определяет итоговые пары «накладная + вагон» для всех выбранных КТК и резервирует необходимые существующие связи. При полном переносе связи, если готовой целевой пары ещё нет, изменяется waybill_railway_carriage.railway_carriage_id; идентификатор записи, waybill_id и ссылки её КТК сохраняются. Если часть КТК остаётся на исходном вагоне, исходная связь сохраняется, а переносимым КТК назначается существующая или новая запись этой же накладной для целевого вагона через waybill_container.waybill_railway_carriage_id. Один физический вагон может одновременно присутствовать в разных накладных: это отдельные записи с одинаковым railway_carriage_id и разными waybill_id. Новые таблицы и миграции не требуются. Накладные и атрибуты остальных КТК не меняются. Грузы, массы, собственники, ЗПУ и связь накладной с поставкой сохраняются. Состав каждой накладной по КТК остаётся прежним; обновляется распределение по вагонам. Освободившиеся при переносе связи выбранной накладной с вагоном удаляются; существовавшие изначально пустые связи сохраняются. Генератор продолжает создавать прежний состав документов.

Сохранение всего размещения атомарно. Проверяются полный набор выбранных строк, отсутствие повторного физического КТК, суммарная длина КТК относительно длины платформы (STANDARD_20 = 20 футов, STANDARD_40 = 40 футов). Число мест и грузоподъёмность не ограничивают размещение: на платформе 80 футов допустимы 4×20, 2×40 или 40+20+20. КТК невыбранных накладных не загружаются в схему, не занимают в ней места и не блокируют сохранение независимо от статуса их поставки. Изменения невыбранных накладных не делают версию выбранной схемы устаревшей; их строки не изменяются. Неизвестная длина платформы или тип КТК блокирует сохранение, поскольку футовость нельзя проверить. API предварительного просмотра поддерживает добавление вагона из справочника, в том числе пустого; упрощённая форма показывает вагоны выбранных накладных и не предлагает отдельного добавления. Список выбора передаёт количество уникальных вагонов и количество КТК без номеров состава. Накладные без КТК также доступны для выбора и открытия, включая накладные без вагонов. Существовавшие до сохранения пустые связи накладной с вагоном сохраняются; удаляются только освободившиеся в результате переноса связи, на которых ранее были КТК. Перенос на вагон пустой накладной сохраняет исходную накладную КТК.

Версия схемы и блокировки защищают от сохранения устаревшего размещения и изменения после подтверждения поставки. Успешные перемещения фиксирует waybill_container_relocation (V30–V31): пакет, исходная waybill_id и целевая to_waybill_id накладные, строка и физический КТК, прежний/новый вагон, время. V31 заполняет целевую накладную прежних записей исходной и разрешает перенос между накладными при неизменном физическом вагоне. В новых перемещениях исходная и целевая накладные одинаковы; прежние записи смены накладной сохраняются как история. Перенос между КТК внутри одного физического вагона ничего не меняет. Неизменившиеся строки не создают запись аудита. Складские состояния и резервы редактор не меняет. Проверки с изменением данных: scripts/waybill-placement-check.cjs и scripts/waybill-placement-ui.cjs, только в отдельной billing_wagon_test на портах 8194/3194; браузерный сценарий использует фикстуры первого и проверяет реальное перетаскивание/обмен между вагонами с сохранением исходных накладных в БД. Проверки API также покрывают изменение railway_carriage_id с сохранением идентификаторов связей, частичный обмен с сохранением неподвижных КТК, обратное объединение связей, запрет смены накладной, область выбранных накладных и аудит. Сценарии пустых накладных проверяют выбор документа с нулём КТК, открытие с пустым вагоном и без вагонов, перенос на пустой вагон с сохранением исходной накладной КТК и существовавшей пустой связи. scripts/waybill-placement-length-check.cjs и scripts/waybill-placement-length-ui.cjs проверяют исходные шесть КТК, уменьшение до пяти/четырёх, рост карточек, четыре вагона в ряд и сохранение 4×20 на 80-футовой платформе независимо от массы.

В накладной обязателен хотя бы один груз, даже при порожнем КТК. Несколько грузов допустимы только при ровно одном КТК; для каждого груза тогда нужна масса. Массы хранятся в кг с точностью до 0,001. container.weight — тара, waybill_container.weight — брутто, net_weight — сохранённое нетто. При отсутствии явного нетто оно фиксируется при создании по текущей таре. Изменение справочной тары впоследствии не пересчитывает сохранённое нетто. В item-таблицах сохранено историческое имя wight_net.

Исходный owner накладной — текст. Выбранный клиент-собственник заявки хранится отдельно. В грузе накладной выбирается danger_product_id, показывается danger_product.name; класс получается через danger_product.danger_class_id. В строках поставки/вывоза используется прямая ссылка на danger_class. Тип ЗПУ — ссылка seal_type, номера сохраняются строками с ведущими нулями.

Генератор — [отдельное описание](docs/equipment-number-formats.md).

Реализация редактора: [WaybillPlacementService](backend/src/main/java/ru/billing/app/waybill/WaybillPlacementService.java), [WaybillPlacementPolicy](backend/src/main/java/ru/billing/app/waybill/WaybillPlacementPolicy.java), [WaybillPlacementController](backend/src/main/java/ru/billing/app/waybill/WaybillPlacementController.java).

## Реквизиты и ограничения модели

Грузоотправитель и грузополучатель выбираются из справочника client, произвольное имя отклоняется. receiving_order.consignor хранится строкой; shipping_order.consignee_id остаётся ссылкой на client_related_entity. Служебное представление клиента создаёт PartyReferences; оно скрыто из справочника перевозчиков.

Плановые даты поставки/вывоза передаются как LocalDateTime. Не преобразовывать их повторно как UTC timestamp. Поле contract.valid_from может быть NULL; неизвестную дату показывать прочерком. V28 заполнила существовавшие договоры датой 01.01.2026 по отдельному решению, но не назначает её всем новым договорам.

Метаданные черновых вывозов и возвратов услуги редактируются пакетно через transport-metadata с проверкой принадлежности и исходных значений. Конфликт откатывает пакет. Начальная поставка редактируется через собственную карточку.

Особенности MVP, которые нельзя принимать за полную модель основной системы:

- etsng_code.code может содержать код вместе с подписью; чтение разделяет строку. Для внешнего обмена это потребовало бы отдельного согласования контракта.
- Для ручной порожней строки класс опасности не подставляется автоматически только из признака empty. Проверки и нормализацию основной системы не считать уже реализованными.
- Роли и полномочия пользователей, внешние интеграции, банковский обмен и полный производственный жизненный цикл не реализованы.

Хранение разделяется новыми сменами собственника без изменения исходной поставки и без новых транспортных документов; день смены относится новому собственнику. Старые периоды не пересчитываются. С V52 период хранит семь полей; start_history_id/end_history_id определяют границы периода собственника, а исходный приём вычисляется обходом общих границ до ARRIVAL. При смене собственника периоды связывает общее событие; при отмене поставки аннулируются все периоды этого приёма, при отмене вывоза очищается end_history_id последнего периода. Учёт хранения не зависит от каталога услуг и не создаёт начислений. Отчёт считает календарные дни по событиям границ; льготные дни, тарифы хранения и начисления по дням пока не применяются. Жизненный цикл периодов и отмены описаны в [CONTAINER_STOCK.md](CONTAINER_STOCK.md).

## Карта API

Поставки и вывозы используют общий [OrderRowMapper](backend/src/main/java/ru/billing/app/order/OrderRowMapper.java) для чтения реквизитов списка, КТК и площадки. SQL-запросы, состав документов и правила записи остаются в соответствующих ReceivingOrderStore и ShippingOrderStore; поставка возвращает fillingType=ALL, вывоз сохраняет прочитанное значение с прежним значением ALL при NULL.

Базовый путь — /api. Точные DTO и методы определяются контроллерами и request-классами, а не историческими примерами запросов.

| Ресурс | Назначение |

| /receiving-orders, /shipping-orders | Транспортные заявки, состав и метаданные |
| /comprehensive-service-orders | Услуга, доступные услуги, транспортные действия, возвраты и прогресс |
| /routes | Рейсы и подтверждение |
| /container-owners, /service-orders | Регистр и смена собственника |
| /container-storage-periods | Отчёт периодов по точным событиям границ с реквизитами исходной поставки и конечного вывоза; /export — CSV с теми же 17 колонками |
| /waybills | Накладные, выбор, группировка, генерация |

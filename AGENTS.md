# Правила работы над MVP

Сначала читать [README.md](README.md), затем относящиеся к задаче [BACKEND_ALIGNMENT.md](BACKEND_ALIGNMENT.md) и [CONTAINER_STOCK.md](CONTAINER_STOCK.md). Перед изменениями frontend читать [FRONTEND_STANDARD.md](FRONTEND_STANDARD.md), перед работой с окружением или БД — [database/README.md](database/README.md).

## Область работы

- Работать в актуальном клоне репозитория airafka/bil. Перед операциями определить корень через git rev-parse --show-toplevel и проверить origin; каталог чата может отличаться от каталога приложения. Не переносить абсолютные пути между компьютерами.
- Окружение проекта: Compose billing-next, порты по умолчанию frontend 3001 / backend 8081 / PostgreSQL 5433, БД billing_next. Проверять реальные параметры перед запуском команд.
- Исторические инструкции о сохранении исходной копии «Билинг 2.0» и Compose billing больше не применяются на этом компьютере: они удалены.
- Сверять документацию с текущим кодом. Различать согласованное требование, фактическую реализацию MVP и примеры основной системы; при расхождении указывать конкретные файлы и поведение. Не считать архивы основной системы обязательным функционалом MVP.
- Сохранять работу пользователя. Не применять reset, clean, принудительное переключение или массовое добавление файлов поверх посторонних изменений.

## Синхронизация разработки между компьютерами

- Перед изменениями проверить git status --short --branch, HEAD и origin. Общая ветка — main, origin — https://github.com/airafka/bil.git.
- Выполнить git fetch origin main. Безопасно обновить локальную main через git merge --ff-only origin/main. При расхождении истории или пересечении с незакоммиченными правками сначала изучить различия и сохранить работу пользователя.
- После успешных проверок автоматически создать коммит только с изменениями текущей задачи и выполнить git push origin main. Отдельное подтверждение не требуется. Указание пользователя оставить изменения локально или выполнить только анализ имеет приоритет.
- Перед публикацией проверить состав коммита и отсутствие посторонних локальных коммитов в origin/main..HEAD. Добавлять файлы или фрагменты выборочно.
- Если main обновилась на другом компьютере, получить изменения и безопасно перенести поверх них только неопубликованные коммиты текущей задачи. Повторить относящиеся к изменению проверки. Если безопасное объединение невозможно, сохранить работу и объяснить препятствие. Не применять force push и не переписывать опубликованную историю.
- Снимок БД обновлять и публиковать только по отдельному запросу. Не добавлять .env, секреты, локальные дампы, резервные копии, логи, скриншоты и диагностические отчёты.
- После push сверить удалённый HEAD и сообщить хеш. Если отправка не состоялась, сообщить причину и хеш локального коммита.

Это порядок действий агента при выполнении задачи, а не фоновая синхронизация файлов. Работа на двух компьютерах последовательная; локальные БД автоматически не объединяются.

## Данные и проверки

- Перед миграциями и изменением данных сделать свежую резервную копию billing_next. Применённые миграции Flyway не переписывать; добавлять следующую миграцию в db/baseline.
- Изменяющие тесты запускать в отдельной тестовой БД. Проверить её имя, подключение backend, контейнеры и порты до выполнения сценария.
- Исторические seed/cleanup/renumber и прочие scripts не запускать без проверки содержимого и отдельной задачи. Завершённые разовые операции не повторять.
- Применять минимально достаточные изменения и подходящие проверки. Для документации достаточно сверки с кодом, проверки ссылок и diff; сборку приложения выполнять при изменениях, требующих её.
- В конце сообщать, что изменено, какие проверки реально прошли и что осталось непроверенным.

## Поддержание документации

После каждой доработки проверять актуальность затронутой документации и обновлять её в рамках той же задачи, до коммита и публикации. Если описание остаётся верным, менять файлы не требуется. Использовать существующие Markdown-файлы; новые создавать только при необходимости отдельной темы, которую нельзя разумно разместить в существующих документах, не дублируя их содержание.

У каждого правила один основной документ: карта приведена в README. Обновлять соответствующий раздел целиком, убирая отменённые формулировки. Не дописывать цепочки датированных уточнений с противоположными правилами. История хранится в Git; отдельные журналы передачи и копии документов не создавать без необходимости.

Не записывать текущие количества заявок, следующий номер документа, временный UUID или состояние контейнера как постоянное свойство системы. Версию схемы сверять с активными миграциями; дату и состав опубликованного снимка — с его JSON-манифестом. Не смешивать проверку исходников, тестовую проверку и состояние работающего приложения.

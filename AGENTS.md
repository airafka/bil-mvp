# Рабочая копия для доработок

Сначала читать COPY_INFO.md, затем HANDOFF.md, README.md, BACKEND_ALIGNMENT.md и DESIGN.md.
Все новые изменения выполнять в этом каталоге bil-next. Исходный проект bil и контейнеры billing-* сохранять без изменений. Использовать только compose-проект billing-next, frontend3001/backend8081/БД5433. Не запускать исторические scripts без проверки жёстко заданных путей, портов и имён контейнеров. Не повторять одноразовые скрипты. Перед миграциями и изменениями данных делать свежую резервную копию БД. Изменяющие тесты выполнять на отдельной тестовой БД.

## Синхронизация разработки между компьютерами

- Перед изменениями проверь `git status --short --branch`, текущий HEAD и адрес `origin`. Общая ветка проекта — `main` в `github.com/airafka/bil`. Выполни `git fetch origin main`. Обнови локальную `main` через `git merge --ff-only origin/main`, если это безопасно для имеющихся правок. При расхождении истории или пересечении с незакоммиченными правками сначала разберись в различиях и сохрани работу пользователя.
- После успешных проверок автоматически создай коммит только с изменениями текущей задачи и отправь его командой `git push origin main`. Отдельное подтверждение для такого commit/push не требуется. Указание пользователя оставить изменения локально или выполнить только анализ имеет приоритет.
- Перед публикацией проверь состав коммита и убедись, что в диапазоне `origin/main..HEAD` нет посторонних локальных коммитов. Добавляй файлы выборочно, особенно если в рабочем дереве уже были правки. При необходимости выделяй только относящиеся к задаче фрагменты.
- Если другой компьютер обновил `main`, получи свежие коммиты и перенеси поверх них только неопубликованные коммиты текущей задачи, когда это можно сделать без потери локальных правок. Повтори относящиеся к изменению проверки перед отправкой. Если безопасно объединить изменения не получается, сохрани локальную работу и сообщи, что мешает публикации. Принудительную отправку и переписывание опубликованной истории не применять.
- Снимки БД обновляй и публикуй только по отдельному запросу. `.env`, секреты, локальные дампы, резервные копии, логи и результаты диагностических проверок не добавляй в Git.
- После отправки проверь, что GitHub принял коммит, и сообщи его хеш. Если отправка не состоялась, укажи причину и хеш сохранённого локального коммита.

Перед изменениями frontend читать [FRONTEND_STANDARD.md](FRONTEND_STANDARD.md). Использовать общие компоненты/токены; таблицы сохраняют колонки и иерархию с горизонтальной прокруткой. Не добавлять локальные размеры или необязательные фильтры.
